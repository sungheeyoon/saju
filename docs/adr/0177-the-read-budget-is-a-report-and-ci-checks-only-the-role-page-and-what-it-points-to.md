# 읽기량 예상치는 붉지 않는 보고이고, CI 는 역할 문서의 한 화면과 가리킨 자리가 있는지만 잰다

> **운영자 승인 2026-10-12**(시스템 점검 라운드, 조율자 브리프로 전함 — 「추천대로」) — 「CI 를 붉게 하는 것은 역할 문서 자체의
> 한 화면 상한과, 역할 문서가 가리키는 링크 · 절이 실제로 있는지 둘만 남긴다. 읽기량 예상치 표는 붉음이 없는 보고로 돌린다.
> 깎거나 쪼갠 문서를 되돌리는 일은 하지 않는다.」 G-107 의 답이다.

ADR 0145 · 0147 · 0162 · 0169 의 **읽기량 대목**을 통째로 대체한다 — 회귀 상한과 천장(눈금 · 여유의 바닥 · 붉어지는 여유 ·
ADR 의 `| 역할 | … | 천장 |` 줄), 역할마다 잠근 동적 라우트 · 선택 묶음 목록, 노트 차례 「최근」 여덟 줄의 시험, 각 ADR 의 「다시
정한 천장」 표와 덧, 천장에 걸렸을 때의 절차. 그대로 서는 것 — 역할 문서는 Router 다(ADR 0145), 「닿을 때 여는 것」 칸과 무엇을
그리로 옮기는가의 기준(ADR 0147), 셈의 규칙(고정 · 절 · 동적 라우트 · 선택 묶음, `scripts/read-budget.mjs`)과 그 수의 이름
「읽기량 예상치」(ADR 0162), 화면 문서는 무리마다 한 파일이고 대장의 새 절은 파일 이름을 단 번호다(ADR 0162 · 0169).

## 잰 것 (2026-10-12, main `bccc0ff4`)

- **천장은 실제 제약이 아니었다.** 그날의 예상치에 5,000 을 더해 5,000 의 배수로 올린 값이었다(옛 `scripts/read-budget.mjs` 의
  `CEILING_STEP` · `HEADROOM` · `MAX_SLACK` · `ceilingFor`). 에이전트가 실제로 얼마를 읽어 일을 그르쳤다는 근거에서 나온 수가 아니다.
- **그래서 문서를 깎고 쪼갤 유인이 생겼다.** #540(노트 차례의 남의 줄 설명을 줄였다) · #566 · #657(매칭 대장 03 · 04 의 설명과 자리
  이름을 줄였다) · PRD `chat.md` 분리 · 문구 대장 `credits.md` 가 그 셈을 맞추려 글을 줄이거나 옮겼다(점검 보고).
- **남의 파일이 자라면 상관없는 PR 이 붉었다.** reviewer 는 예상치 94,898 / 천장 95,000 — 102 바이트 남았다. 프런트 관점의 가장 큰
  후보(`docs/product/copy-ledger/matching.md` · `docs/product/prd/screens/first.md`)에 한 줄이 붙으면 그 줄과 무관한 PR 이 붉어진다.
  feature 도 950 바이트 남았다(99,050 / 100,000).
- **갈 길이 막혔다.** `docs/agents/delegation/done.md` 「읽기량 천장에 걸리면」은 G-107 이 닫힐 때까지 천장 올리기를 막았고, 운영자는
  문서 깎기를 막았다(G-107, 2026-10-11). 넘으면 멈추는 수밖에 없었다.
- **바이트가 「먼저 읽는 것 / 닿을 때」의 경계를 옮겼다.** ADR 0169 는 ui 의 대장 무리 파일을 바이트 때문에 「닿을 때」로 옮겼다
  (「ui 역할이 99,944 / 100,000」). 같은 `done.md` 의 넷째 걸음은 「읽어야 할 링크를 「닿을 때 여는 것」으로 옮겨 맞추지 않는다」였다.

## 정한 것

- **읽기량에 걸린 CI 의 붉음은 둘뿐이다**(`scripts/code-rules.test.ts` 「역할 문서」).
  1. 역할 문서 한 장이 한 화면(8,000 바이트) 안이다 — 넘으면 원본으로 옮길 것을 옮겨 적고 있다는 뜻이다(ADR 0140).
  2. 역할 문서 · 입구가 가리킨 파일 · 「절」 · 앵커가 있다. 셈(`readBudgetOf`)이 모든 역할에서 끝까지 돈다 — 없는 절 · 꼴이 틀린
     선택 묶음에서 던지고, 디렉터리 링크는 고를 후보가 있는 폴더를 가리켜야 한다.

  칸의 차례 · 「이 저장소의 방식」의 링크 꼴 같은 역할 문서의 모양 시험은 읽기량이 아니라 그대로다.
- **예상치 표는 보고다.** `npm run read-budget` 이 역할마다 고정 · 동적 · 묶음 · 예상치를 찍고, 문턱이 없다. 역할 문서의 가리킴을
  바꾼 PR 은 그 역할의 전후 예상치를 「잰 값」 칸에 적는다 — 판단의 재료이지 막는 값이 아니다(`docs/agents/delegation/done.md`
  「읽기량 예상치는 보고다」).
- **걷은 시험** — 예상치 ≤ 천장 · 천장이 예상치보다 15,000 넘게 남으면 붉음 · 천장이 5,000 의 배수 · ADR 의 천장 줄 · 잠근 라우트 ·
  묶음 목록(`code-rules.test.ts`), 천장 눈금의 셈(`read-budget.test.ts`), 노트 차례 「최근」 여덟 줄(`code-rules.test.ts`).
  `READ_BUDGET` 표와 `CEILING_STEP` · `HEADROOM` · `MAX_SLACK` · `ceilingFor` 도 걷었다.
- **경계는 일의 쓰임으로 정한다.** 「먼저 읽는 것」과 「닿을 때 여는 것」 사이로 줄을 옮기는 까닭은 ADR 0147 「무엇을 옮기는가의
  기준」 하나다 — 그 역할의 일 대부분이 손대기 전에 쓰나. 바이트는 까닭이 아니다. 「닿을 때」에 둔 원본을 매번 열었다는 보고가
  쌓이면 되돌린다(ADR 0147 「잠그지 않은 것」).
- **바이트를 맞추려고 문서를 깎거나 쪼개지 않는다.** 원본을 나누는 것은 한 파일이 여러 작업의 것을 한데 들어 한 일이 남의 것을
  함께 읽을 때다 — 그 일의 뜻이 까닭이다.
- **이미 깎거나 쪼갠 문서는 그대로 둔다** — 되돌리는 일은 이 결정의 범위 밖이다. 노트 차례의 「최근」 · 「차례」 가름도 꼴로 남는다
  (줄 수는 재지 않는다).

## 치르는 값

- 역할이 손대기 전에 읽는 양이 다시 자라도 CI 는 모른다. 가리킴을 바꾼 PR 의 「잰 값」과 조율자가 라운드 끝에 거두는 「헤맨 것」
  (ADR 0146)이 그 자리를 본다.
- 큰 원본을 절 없이 통째로 가리키는 줄이 붉음 없이 들 수 있다. 셈은 그대로라 표에서 보인다.

## 버린 것

- **천장을 또 올린다** — 2026-10-10 · 10-11 에 운영자가 막았고, 대장 절 몇 개면 다시 닿는다(ADR 0169 「버린 것」).
- **문서를 줄여 맞춘다** — 운영자가 막았다(G-107). 결정 · 요구의 문장이 바이트 때문에 사라진다.
