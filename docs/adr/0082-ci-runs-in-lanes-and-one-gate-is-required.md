# 검사는 차선으로 돌고 필수 검사는 gate 하나다

## 무엇이 났나

`verify` 워크플로가 PR 마다 9분이었다. 이슈 #93 은 병목을 「로그인 e2e 106건이 `--workers=1` 로
직렬」이라고 적었고, 그 위에 `test:flow` 를 얹으면 한 번 도는 값만 커진다며 #91 에서 CI 배선을
미뤘다. 그리고 main 에 보호 규칙이 없어 `gh pr merge --auto` 가 검사를 안 기다리고 즉시 머지했다
— 그것은 검사 전 배포다.

## 후보 문장이 또 반쯤 틀렸다 — 워커가 아니라 서버다

먼저 쟀다. 로컬(12코어)에서는 이슈의 말이 맞았다 — `signed-in.spec.ts` 76건이 6 워커로 50초,
한 워커로 돌리던 것의 몇 분의 일이다. 그런데 **공유 러너에서는 워커 수가 거의 안 먹힌다.**

| signed-in 76건, 공유 러너(4 vCPU) | 걸린 시간 |
|---|---|
| `--workers=1` | 3.0분 |
| `--workers=2` | 2.7분 |
| `--workers=4` | 2.9분 · flaky 1건(`toHaveURL`, 재시도로 통과) |

느린 것은 시험이 아니라 **한 벌뿐인 dev 서버**다. 워커가 넷이어도 같은 서버가 같은 라우트를
차례로 짓는다. 그래서 줄이는 길은 워커가 아니라 **서버를 여럿 세우는 것**이고, 그것은 곧 스택을
여럿 띄우는 것이다 — 저장소가 공개라 Actions 분은 공짜이고, 줄일 것은 총 사용 분이 아니라 PR
벽시계다(#93 의 전제).

`match.spec.ts` 는 여러 워커로 못 돈다. `onlyTheseParticipate` 가 **전역** 참여 표를 제 쌍으로
좁히므로 나란히 돌면 서로 지운다 — 로컬에서 두 워커로 돌리자 30건 중 7건이 「매칭 참여를 먼저 켜
주세요」로 죽었고, 한 워커로는 29건 초록(1.6분). 안내 관문(`notice.spec.ts`)은 전역 일정 표를 두고
반대를 요구하는 시험이 있어 처음부터 혼자였다.

## 무엇을 정했나

### 차선 다섯, 스택 다섯

`authed` 한 job 을 매트릭스 다섯으로 가른다 — `signed-in:desktop` · `signed-in:mobile` ·
`match:desktop` · `match:mobile` · `notice`. **차선마다 제 Supabase 를 띄운다.** 데스크톱과
모바일을 스택째 가르는 것이 요점이다 — 서버가 둘이면 궁합도 한 워커인 채로 절반이 된다.

워커 수는 잰 대로다: signed-in 은 2(4 는 더 느리고 흔들렸다), 궁합은 1, 안내 관문은 1. 이 수는
`package.json` 의 차선 스크립트에 있고 YAML 은 스크립트 이름만 안다. `test:e2e:authed` 는 그대로
남는다 — 로컬에서 「전부」를 한 번에 부르는 이름이고, 셋을 한 프로세스에서 안전하게 돌리는 길은
아직 한 워커뿐이다(Playwright 의 project 의존은 앞이 실패하면 뒤를 건너뛰어 쓸 수 없다).

pgTAP 과 생성 타입 diff 는 가장 짧은 차선(`notice`)에만, e2e 앞에 둔다 — 순서의 뜻은 옛 워크플로
주석 그대로다.

### `test:flow` 는 넷째 병렬 job

브라우저 e2e 와 나란히 돈다. 첫 실행에서 일곱 벌 391건이 그대로 통과했다(1분 42초, 스택 띄우기
90초 별도). 워크플로 주석의 「아직 여기서 안 돈다」는 지웠다 — 안 돌던 이유는 비용이 아니라 배선을
안 한 것뿐이었다는 그 주석의 말이 맞았다.

### 무엇을 돌릴지는 `scripts/ci-plan.mjs` 한 곳이 정한다

세 단계뿐이다.

| 변경이 이 안에만 있으면 | 도는 것 |
|---|---|
| 문서(`docs/**` · `*.md`) | `gate` 만 |
| 엔진(`src/lib/saju/**`) · 엔진을 그리는 칸(`app/saju/**`) | `verify`(단위·타입·린트·빌드 + 익명 e2e) |
| 그 밖 전부 · **모르는 파일** · 빈 목록 | 전부 |

셋뿐인 까닭은 최근 PR 여섯 중 넷이 스무 디렉터리를 건드리는 횡단 변경이라서다. 잘게 나눈
매트릭스는 아끼는 PR 이 드물고, 나눈 만큼 「이 경로는 저 검사에 안 걸린다」는 문장이 늘어난다 —
그 문장은 파일이 옮겨지는 날 조용히 거짓이 된다.

**엔진 단계도 재서 좁혔다.** 이슈는 홈(`app/page.tsx`)과 출생 폼(`app/birth-form*`)을 익명 화면으로
적었는데, 홈은 로그인 e2e 세 건이 회원으로 열고 폼은 온보딩·수정·사람 관리가 함께 쓴다 — 둘 다
목록에서 뺐다. `src/lib/saju` 는 모든 층이 읽지만 로그인 뒤 화면과 흐름 검사는 같은 엔진으로
기대값을 지으므로 엔진이 달라져도 함께 달라진다. 빨개질 수 있는 자리는 **DB 의 검사식이 모양을
보는 곳**뿐이다 — 저장되는 여덟 글자(`chartSnapshotOf`, `pillars/index.ts`)와 판본(`version.ts`).
그 둘은 엔진 단계에서 제외했다(`ENGINE_DB_FACING`).

원칙 셋은 `ci-plan.test.ts` 가 값으로 든다: 모르는 파일 하나면 전부, 라벨(`full-ci`)은 더할 수만
있고 뺄 수 없다, diff 를 못 받았으면 전부. `main` 푸시·하루 한 번 일정(05:00 KST)·손으로 켠
실행은 계획을 안 본다.

### 필수 검사는 `gate` 하나

GitHub 의 필수 검사는 안 돈 job 을 「기다리는 중」으로 영원히 둔다. 선택으로 건너뛴 job 을
필수로 걸면 문서 PR 이 영영 안 머지된다. 그래서 `gate` 는 `if: always()` 로 항상 돌고 위 job
전부를 `needs` 로 물린다 — `needs.*.result` 에 `failure`·`cancelled` 가 하나라도 있으면 빨갛고
`skipped` 는 통과다. main 보호 규칙의 필수 검사는 이것 하나이고, 저장소의 auto-merge 를 켰다. 이제
`gh pr merge --auto` 가 비로소 기다린다. 관리자는 규칙 밖에 둔다(`enforce_admins: false`) —
main 에 직접 미는 일이 있다.

2026-09-22 에 걸었다 — 보호 규칙의 필수 검사 `gate`(`strict: false`), `enforce_admins: false`,
저장소 `allow_auto_merge: true`. 이 문서를 고친 PR 이 그 첫 시험이다: `plan` 이 `docs` 를 내고
차선 전부가 건너뛰어 `gate` 만으로 초록이 되는지, 그리고 `gh pr merge --auto` 가 그것을
기다리는지.

### `concurrency`

같은 가지에 새 커밋이 오면 대체된 실행을 끊는다. 벽시계는 안 줄고, force-push 뒤 옛 실행이
끝까지 도는 낭비가 사라진다.

## 안 한 것

- **궁합 시험의 격리.** `onlyTheseParticipate` 를 「시험이 만든 계정끼리만 서로 본다」로 바꾸면
  궁합도 여러 워커로 돌 수 있다. 하지만 공유 러너에서 워커는 거의 안 먹히므로(위 표) 얻는 것이
  없다. 스택을 가르는 쪽이 더 싸고, 이미 그렇게 했다.
- **Docker 이미지·브라우저 캐시.** 차선마다 2분 가까이 되는 준비 시간이 남는다. 캐시를 세우면
  절반쯤 줄 텐데, 5분 아래를 이미 맞춰 안 건드렸다. 벽시계를 더 줄일 일이 생기면 여기가 첫
  자리다.
- **`docs/test-strategy.md`.** 이슈가 가리켰지만 없던 파일이다. 원칙은 이 ADR 과
  `ci-plan.mjs` 머리말에 있고, 매트릭스 본체는 코드다 — 셋째 자리를 만들지 않았다.

## 머지는 한 줄로 선다 (2026-09-23, #143)

여러 세션이 나란히 머지하자 두 구멍이 드러났다. 보호 규칙의 `strict` 가 `false` 라 PR 은 **제 기준 main**
위에서만 gate 를 지났다 — 둘이 연달아 들면 합쳐진 상태는 머지 전에 아무도 안 쟀다. 그리고 그 뒤의 검증인
main 푸시 실행은 `cancel-in-progress` 로 다음 푸시에 끊겼다. 그날 main 실행 넷이 `cancelled` 였다.

- **strict 를 켰다.** PR 은 최신 main 을 품어야 든다. auto-merge 는 가지를 스스로 올리지 않으므로 `BEHIND`
  인 PR 은 `gh pr update-branch` 로 main 을 merge 하고(force push 없음) gate 를 다시 지난다. 나란히 선
  PR 마다 차선 한 벌(약 5분)이 더 도는 값이다.
- **머지 큐는 못 쓴다.** 개인 계정의 저장소라 GitHub 이 주지 않는다(조직 소유여야 한다). strict 가 그 자리다.
- **main 푸시의 실행은 커밋마다 제 그룹이다.** `cancel-in-progress: false` 만으로는 모자란다 — 같은 그룹에서
  기다리던 실행은 새 실행이 오면 취소된다. PR 은 전처럼 끊는다.

## 문서도 시험이 읽는다 — 정책 단계 (2026-09-23, #145)

세 단계의 맨 아래가 「문서 → `gate` 만」이었다. 그 사이 `scripts/code-rules.test.ts` 가 간극 대장 · PRD · 위임
규약 · ADR · `.claude/settings.json` 을 읽는 시험이 됐고(ADR 0086 · 0089 · 0090 · 0093), 문서 PR 이 그 시험을
깨도 그 PR 에서는 아무것도 안 돌았다. 반대로 `.claude/settings.json` 과 문서만 바꾼 #141 은 모르는 파일이라
약 5분을 전부 돌았다.

- **맨 아래 단계는 `policy` 다.** 문서 · `*.md` · `.claude/**` · `scripts/` 바로 아래의 `*.test.ts` 만 바뀌면
  `policy` 차선 하나가 scripts 시험 · 타입 · 린트를 돈다(로컬 12초). 아무것도 안 도는 단계는 없어졌다.
- **`scripts/*.test.ts` 가 정책인 까닭**은 시험 파일이 저 자신의 결과만 바꾸기 때문이다. 시험이 아닌
  `scripts/*.mjs` 는 CI 계획과 흐름 검사를 바꾸므로 전부로 간다.
- **`db:start` 가 새 러너에서 54322 를 못 잡았다**(main 실행 35821662685). 이미지는 rate limit 을 재시도로
  넘겨 다 받았고 `supabase start` 는 한 번만 불렸다 — 같은 job 의 재시도도, 차선끼리의 다툼(차선은 VM 이
  따로다)도 아니다. Ubuntu 의 임시 포트 범위가 543xx 를 품는 것이 가장 그럴듯해 범위를 60000 위로 올리고,
  그래도 안 서면 걷고 한 번 더 띄운다. 이미지 캐시와 동시 실행 제한은 rate limit 이 실패로 번진 것을 본
  뒤에 다시 잰다 — 이날의 rate limit 은 CLI 의 재시도가 넘겼다.
