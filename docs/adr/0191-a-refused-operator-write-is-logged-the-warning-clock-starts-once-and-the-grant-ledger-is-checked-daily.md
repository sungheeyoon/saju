# 운영자의 거절된 쓰기도 접속기록에 남고, 경고의 12개월은 처음 경고한 날부터 세며, 지급 장부는 매일 대조한다

> **근거** — 간극 대장 G-111(`docs/product/gaps/records/g-111.md` 「검수에서 남긴 결정 거리」 R-3 ~ R-9). #738 검수가 남긴 일곱을
> 운영자가 2026-10-17 에 「권한 대로, 다른 서비스의 근거를 따라」 정했다(조율자 전달). 근거 사본은 같은 날 내려받았고, 아래 「근거」의
> 인용은 그 사본에서 옮겼다. ADR 0187(지급 장부) · 0188(처분 · 상태 이력) · 0105(접속기록) 위에 선다. 마이그레이션 `20261219090000`.

## 잰 것 — 만들기 전에

- **R-3** — `app_user.status` 의 트리거 `account_status_is_recorded` 는 `after update of status … when (old.status is distinct
  from new.status)` 다. 공통 함수 · 탈퇴 신청 · 직접 UPDATE 모두가 이력 한 줄을 남기고, 공통 함수 밖의 것은 실행자 · 사유가 빈 줄과
  `notify_ops` 한 줄이다(`99_operator_report_review` 의 「직접 UPDATE」 둘이 잠근다). 빠지는 길은 소유자가 트리거를 끄는 것뿐이다 —
  `docs/ops/runbook/security.md` 「기록이 추가만 되는 것」이 이미 말하는 한계와 같다.
- **R-4** — 운영자 쓰기 문(처분 · 정지 · 해제 · 지급 · 회수 · 환불 세 걸음)은 성공이면 같은 트랜잭션에서 `allowed` 한 줄을 적고,
  거절하면 그 줄이 되감긴다. 앱은 `42501` 일 때만 `note_operator_denial` 을 불렀고, 그 문은 운영자가 부르면 아무것도 안 적는다. 그래서
  버전 충돌(`55000`) · 상태 거절(`23514` · `55000`) · 모양(`22023`)은 어디에도 안 남았다.
- **R-6** — `write_report_review` 는 적을 때마다 `reviewed_at = now()` 이고, 12개월 셈(`operator_member_warnings` ·
  `operator_member_sanctions` · `operator_report_target` 의 `warnings_12m` · `warned_here`, 화면의 `warningOrdinal`)과 이용자 안내의
  「경고한 날」(`my_warning_notice`) · 런북의 셈 질의가 그것을 읽었다.
- **R-7** — `book_reading_credit_grant` 는 계정이 있는지만 봤다. 탈퇴 대기 계정에 지급해도 하루 뒤 처분으로 함께 지워졌다.
- **R-8** — `Σ 장부 = extra` 는 `docs/ops/runbook/credits.md` 의 손 질의 하나뿐이었다.
- **R-9** — 쓰는 순서(`pick_reading_credit_share`)는 무료 → 운영 지급 → 산 때가 이른 묶음이다. 유효기간(ADR 0173)은 무료 · 운영
  지급이 받은 날부터 1년, 산 몫이 산 날부터 5년이고 아직 DB 가 걷지 않는다(G-25).

## 정한 것

1. **R-3 — 기록 + 알림을 그대로 두고 DB 로 막지 않는다.** break-glass(화면을 못 쓸 때 운영 SQL)가 열려 있어야 하고, 기준이 요구하는
   것은 막기가 아니라 기록과 그 보호다(아래 근거). 문서만 고친다.
2. **R-4 — 거절된 운영자 쓰기도 한 줄.** 접속기록의 결과 칸이 셋째 값 `refused` 를 받는다. 앱의 쓰기 액션이 거절을 받으면 제
   트랜잭션에서 `note_operator_refusal(동작, 코드, 신고 id, 계정 id, 주문 id)` 을 부르고, 그 문은 거른 조건 칸에 `user=<id>` ·
   `order=<id>` 와 `refused=<SQLSTATE>`(SQLSTATE 가 아니면 `other`)만 적는다 — 신고 id 는 대상 신고 칸. 메모 · 판단 근거 · 오류
   문장은 받지 않는다. 문을 부르기 전에 액션이 모양으로 거른 것은 `22023`, 준비 취소를 PortOne 확인이 막은 것은 `55000`(취소 있음) ·
   `other`(알 수 없음)로 적는다. `42501` 은 지금처럼 `denied` 다. 표의 검사식이 `refused` 를 앱의 쓰기 여덟에만, 거른 조건 칸이 코드로
   끝날 때만 받는다. 한 사람이 한 시간에 서른 줄까지(거절 문과 같은 까닭).
   **반출 묶음은 칸이 그대로라 `version` 3 을 올리지 않는다** — `outcome` 칸의 값이 하나 늘 뿐이고 검증(`scripts/audit-verify.mjs`)은
   값을 재지 않는다. 받는 쪽이 셋째 값을 알도록 `docs/ops/runbook/security.md` 「반출」의 「담기는 것」에 적었다.
3. **R-5 — 접속기록 1년은 법의 하한이다.** 그대로 둔다(코드 없음). 떠난 사람의 신고 기록(6개월, ADR 0098)보다 대상 요약 줄의
   `reported=<id> reporter=<id>` 가 오래 남는 것은 이 하한을 따른 결과다. 그 둘과 법 제21조(불필요해지면 지체 없이 파기)의 관계는
   **확인 못 함**이다 — 변호사 확인 거리로 남긴다. **정보주체 5만 명이 되면 2년으로 옮긴다**(런북 `security.md` 「어디에 며칠 남나」).
4. **R-6 — 12개월은 처음 경고한 날부터.** 신고 행에 `warned_at` 을 둔다 — 결과가 경고로 들어올 때 지금, 같은 대상의 경고를 다시
   적거나 갈래만 고치면 그대로, 경고에서 나가면 비움. **대상을 다른 사람으로 옮기면 옮긴 때가 그 사람의 경고한 때다** — 그 사람이
   경고받은 날이 그날이라서다. 나가 있다가 다시 경고로 들어오면 그날이 새 경고다. 셈 셋과 이용자 안내의 「경고한 날」, 처분 이력 ·
   대상 요약의 경고 줄 시각이 이것을 읽는다. `reviewed_at` 은 「마지막으로 본 시각」 그대로다(처리 필요 · 목록). 지금 있는 경고는
   처분 이력에서 지금 결과로 이어진 같은 대상의 경고 줄들 가운데 첫 줄의 시각으로 채웠다. 보관 표(`retention.report`)도 같은 칸을
   들고 옮길 때 그대로 간다. 검사식이 「경고면 경고한 때가 있고, 아니면 없다」를 잠근다.
5. **R-7 — 탈퇴 대기 계정에는 새 무상 지급을 받지 않는다.** 공통 함수가 `23514` 「탈퇴 대기 계정이라 지급할 수 없습니다.」(정지에서
   탈퇴 대기로 못 가는 거절과 같은 코드)로 거절한다 — 화면의 문 · 런북 모두. 회수는 받고, 정지된 계정의 지급(장애 보상)도 받는다.
   같은 요청의 재시도는 첫 결과를 돌려준다. 회원 화면은 탈퇴 대기면 지급 단추를 잠그고 같은 문장을 곁에 둔다.
6. **R-8 — 지급 장부를 매일 잰다.** 크론 `credit-grant-watch`(매일 05:41 UTC)가 `watch_reading_credit_grants()` 로 계정마다
   `Σ(지급 − 회수) = extra`(행이 없으면 0)를 재서, 다른 계정마다 `notify_ops` 한 줄(종류 `credit-grant-mismatch:<계정 id>`, 하루 한
   번 — `ops_alert` 의 `(kind, day)`). 계정 id 와 두 수만 가고, **아무것도 고치지 않는다.** 잡이 실패하면 `cron-watch` 가 본다.
7. **R-9 — 쓰는 순서는 「먼저 소멸하는 것부터」이고, 지금의 무료 → 운영 지급 → 이른 묶음이 그것과 같다 — 코드는 안 바꾼다.**
   잰 것: 무료는 가입 때 받으므로 그 뒤의 어느 운영 지급보다 먼저(또는 같은 날) 소멸하고, 묶음(+5년)보다 늘 먼저다. 묶음끼리는 산
   순서가 곧 소멸 순서다. **한 갈래만 어긋난다** — 산 지 4년이 넘은 묶음이 남은 계정에 운영 지급을 하면 그 지급(+1년)이 묶음(+5년)
   보다 늦게 소멸한다. 판매가 닫혀 있어(`reading_sale_is_open()`) 첫 판매 뒤 4년까지는 생기지 않는다. **유효기간을 DB 가 걷을 때
   (G-25, 약관 시행과 함께)** 순서를 몫의 이름이 아니라 소멸일로 고르고, 화면에 몫마다 소멸일을 보이며, 「유효기간 임박」 안내를 보낸다
   (며칠 전 · 어느 길인지는 그때 정한다).

## 버린 것

- **R-3 — DB 가 직접 UPDATE 를 막는다** — break-glass 를 닫는다. 막아도 소유자는 트리거를 끌 수 있어 막기가 완전하지도 않다. 기록과
  알림, 밖의 사본(Object Lock)이 지키는 쪽이 맞다.
- **R-4 — 거절을 `denied` 로 같이 적는다** — 월 점검의 「연속 거절」(운영자가 아닌 사람이 문을 두드림)과 섞인다. 값을 갈랐다.
- **R-4 — 결과 칸 대신 오류 분류 칸(`error_class`)을 쓴다** — CLI 결과 줄의 칸이고, 앱 줄의 검사식을 다시 지어야 한다. 대상 id 가
  이미 거른 조건 칸에 있어 같은 칸에 코드를 잇는 쪽이 작다.
- **R-4 — 묶음 `version` 을 4 로 올린다** — 칸이 그대로다. 값이 늘 때마다 올리면 동작 이름이 늘 때도 올려야 한다(지금까지 안 올렸다).
- **R-6 — 옮긴 경고도 처음 경고한 날을 물려받는다** — 옮겨 간 사람이 경고받지 않은 날을 그 사람의 경고로 센다.

## 치르는 값

- 운영자의 거절마다 앱이 DB 를 한 번 더 부른다. 적지 못해도 화면의 답은 그대로다(서버 기록에만 남는다).
- 반출본을 받는 쪽은 `outcome` 이 셋일 수 있다는 것을 알아야 한다 — 런북이 적었다.
- 확정 전의 환불(`credits.refund_book`)이 거절되면 그 줄에는 주문 id 가 없다 — 앱이 확보 id 만 들고 있어서다. 같은 운영자의 바로 앞
  `credits.refund_status` · `credits.refund_hold` 줄이 주문을 가리킨다.
