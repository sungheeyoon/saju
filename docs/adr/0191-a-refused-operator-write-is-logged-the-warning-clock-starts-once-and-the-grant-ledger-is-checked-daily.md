# 운영자의 거절된 쓰기도 접속기록에 남고, 경고의 12개월은 처음 경고한 날부터 세며, 지급 장부는 매일 대조한다

> **근거** — 간극 대장 G-111(`docs/product/gaps/records/g-111.md` 「검수에서 남긴 결정 거리」 R-3 ~ R-9). #738 검수가 남긴 일곱을
> 운영자가 2026-10-17 에 「권한 대로, 다른 서비스의 근거를 따라」 정했다(조율자 전달). 근거 사본은 같은 날 내려받았고, 아래 「근거」의
> 인용은 그 사본에서 옮겼다. ADR 0187(지급 장부) · 0188(처분 · 상태 이력) · 0105(접속기록) 위에 선다. 마이그레이션 `20261219090000`.
>
> **덧(2026-10-17, 운영 `212c725` 검토)** — 든 근거 몇이 결정을 받치지 않았고 R-4 의 범위가 부풀려 적혀 있었다. 동작은 그대로 두고
> 「정한 것」 · 「근거」를 고쳐 적었다 — 운영 판단과 참고를 가르고, 법이 요구하는 것과 우리가 고른 것을 섞지 않는다. R-4 의 빗장은
> 이제 조용히 버리지 않고 알린다(`20261220090000`), 확정의 거절 줄은 확인된 주문 id 를 싣는다. 법적 결론은 내리지 않는다.
>
> **덧(2026-10-18, 운영자 「고쳐라」)** — 운영자 화면에서 거절된 쓰기는 누가 불렀든 한 줄 선다. 액션이 문을 부르기 전에 거른 모양
> (`22023`)은 `note_operator_refusal` 로만 갔는데 그 문은 운영자가 아니면 안 적어, server action 을 바로 POST 한 사람의 거절이 어디에도
> 안 남았다. 이제 `noteWriteRefusal` 이 `42501` 밖의 코드에 두 문을 다 부른다 — 둘은 서로의 반대만 적으므로(운영자만 `refused`,
> 아니면 `denied`) 한 줄이다. 확정의 취소 번호가 빈 길에서 주문 읽기가 받은 `42501` 은 `credits.refund_status` 의 `denied` 로, 준비
> 취소의 확보 읽기가 `42501` 밖으로 실패한 것은 `credits.refund_release` 의 거절로 적는다. 마이그레이션 없음.

## 잰 것 — 만들기 전에

- **R-3** — `app_user.status` 의 트리거 `account_status_is_recorded` 는 `after update of status … when (old.status is distinct
  from new.status)` 다. 공통 함수 · 탈퇴 신청 · 직접 UPDATE 모두가 이력 한 줄을 남기고, 공통 함수 밖의 것은 실행자 · 사유가 빈 줄과
  `notify_ops` 한 줄이다(`99_operator_report_review` 의 「직접 UPDATE」 둘이 잠근다). 빠지는 길은 소유자가 트리거를 끄는 것뿐이다 —
  `docs/ops/runbook/security.md` 「기록이 추가만 되는 것」이 이미 말하는 한계와 같다.
- **R-4** — 운영자 쓰기 문(처분 · 정지 · 해제 · 지급 · 회수 · 환불 세 걸음)은 성공이면 같은 트랜잭션에서 `allowed` 한 줄을 적고,
  거절하면 그 줄이 되감긴다. 앱은 `42501` 일 때만 `note_operator_denial` 을 불렀고, 그 문은 운영자가 부르면 아무것도 안 적는다. 그래서
  버전 충돌(`55000`) · 상태 거절(`23514` · `55000`) · 모양(`22023`)은 어디에도 안 남았다.
- **R-6** — `write_report_review` 는 적을 때마다 `reviewed_at = now()` 이고, 12개월 셈(`operator_member_warnings` ·
  `operator_member_sanctions` · `operator_report_target` 의 `warnings_12m` · `warned_here`, 화면의 `warningOrdinal`)과 이용자 안내의
  「경고한 날」(`my_warning_notice`) · 런북의 셈 질의가 그것을 읽었다.
- **R-7** — `book_reading_credit_grant` 는 계정이 있는지만 봤다. 탈퇴 대기 계정에 지급해도 하루 뒤 처분으로 함께 지워졌다.
- **R-8** — `Σ 장부 = extra` 는 `docs/ops/runbook/credits.md` 의 손 질의 하나뿐이었다.
- **R-9** — 쓰는 순서(`pick_reading_credit_share`)는 무료 → 운영 지급 → 산 때가 이른 묶음이다. 유효기간(ADR 0173)은 무료 · 운영
  지급이 받은 날부터 1년, 산 몫이 산 날부터 5년이고 아직 DB 가 걷지 않는다(G-25).

## 정한 것

1. **R-3 — 기록 + 알림을 그대로 두고 DB 로 막지 않는다 — 운영 판단이다.** 기록 의무(고시 제5조③ · 제8조③)와 OWASP 의 break-glass
   기록 권고는 직접 UPDATE 를 열어 두라고 요구하지 않는다 — 평소의 바꿈을 막고 break-glass 만 따로 여는 길도 가능했다. 탈퇴 흐름과
   break-glass 가 모두 `status` 를 쓰므로 막는 길을 따로 짓는 대신 기록(이력 줄) + 장애 알림을 골랐다. 문서만 고친다.
2. **R-4 — 앱 액션이 받은 거절을 제한된 범위로 기록한다.** 접속기록의 결과 칸이 셋째 값 `refused` 를 받는다. 앱의 쓰기 액션이 거절을 받으면 제
   트랜잭션에서 `note_operator_refusal(동작, 코드, 신고 id, 계정 id, 주문 id)` 을 부르고, 그 문은 거른 조건 칸에 `user=<id>` ·
   `order=<id>` 와 `refused=<SQLSTATE>`(SQLSTATE 가 아니면 `other`)만 적는다 — 신고 id 는 대상 신고 칸. 메모 · 판단 근거 · 오류
   문장은 받지 않는다. 문을 부르기 전에 액션이 모양으로 거른 것은 `22023`, 준비 취소를 PortOne 확인이 막은 것은 `55000`(취소 있음) ·
   `other`(알 수 없음)로 적는다. `42501` 은 지금처럼 `denied` 다. 표의 검사식이 `refused` 를 앱의 쓰기 여덟에만, 거른 조건 칸이 코드로
   끝날 때만 받는다. **모든 거절을 적는 것이 아니다** — 한계는 셋이다:
   1. **한 운영자에 한 시간 서른 줄**(거절 문과 같은 까닭). 넘는 것은 버린다 — 버리기 시작하면 장애 알림
      `operator-refusal-cap:<운영자 id>` 한 줄(`ops_alert` 의 `(kind, day)` 라 한 운영자에 하루 한 번, 운영자 id 와 수만,
      `20261220090000`).
   2. **앱을 거치지 않고 RPC 를 바로 부른 거절은 적지 않는다** — 줄을 적는 것은 앱 액션이다. 운영자 화면이 쓰기의 유일한 의도된 길이다.
   3. **확정(`credits.refund_book`)의 거절 줄은 확인된 주문 id 만 싣는다** — 확정 문은 확보 id 만 받으므로, 액션이 화면의 주문 id 로
      이미 있는 운영자 읽기 `operator_reading_refund_hold` 를 불러 그 주문의 진행 중인 확보가 이 확보일 때만 싣는다
      (`app/ops/orders/book-refusal.ts`). 확보가 이미 닫혔거나(확정 · 준비 취소 뒤의 거절) 읽기가 실패하면 주문 칸이 빈다. 그 읽기는
      제 줄 `credits.refund_status` 를 하나 더 남긴다.
   OWASP 는 방향(입력 검증 · 권한 실패와 그 결과를 적는다)을 받칠 뿐, 이 셋을 빼고 적는 것이 완전하다고 받치지 않는다.
   **반출 묶음은 칸이 그대로라 `version` 3 을 올리지 않는다** — `outcome` 칸의 값이 하나 늘 뿐이고 검증(`scripts/audit-verify.mjs`)은
   값을 재지 않는다. 받는 쪽이 셋째 값을 알도록 `docs/ops/runbook/security.md` 「반출」의 「담기는 것」에 적었다.
3. **R-5 — 접속기록 1년 · 두 id 짝을 그대로 둔다(코드 없음).** 물음이 둘이다.
   1. **얼마나 두나** — 1년은 고시 제8조①의 하한이다. 2년은 「5만명 이상의 정보주체」(또는 고유식별 · 민감정보 등)일 때다 —
      **정보주체 5만 명 이상이 되면 2년으로 옮긴다**(런북 `security.md` 「어디에 며칠 남나」).
   2. **왜 두 id 를 다 적나** — 고시 제2조 제3호가 접속기록을 「… 처리한 정보주체 정보 …」를 담는 기록으로 정의하고, 운영자의 대상 요약
      읽기(`reports.target`)는 두 계정의 요약을 처리한다. 그래서 `reported=<id> reporter=<id>` 는 **처리한 정보주체**이지 신고의 증거가
      아니다. 떠난 사람의 신고 기록(6개월, ADR 0098)보다 이 줄이 오래 남는 것은 이 정의와 하한을 따른 결과다.
   2026 고시의 본문과 시행일(제8조 ①② 는 2026-10-31)은 **다시 확인할 거리**로 둔다 — 개인정보위 보도자료가 그 조의 1년 유예를
   말한다(아래 근거). 법 제21조와의 관계를 포함해 법적 결론은 내리지 않는다 — 변호사 확인 거리다.
4. **R-6 — 12개월은 처음 경고한 날부터.** 신고 행에 `warned_at` 을 둔다 — 결과가 경고로 들어올 때 지금, 같은 대상의 경고를 다시
   적거나 갈래만 고치면 그대로, 경고에서 나가면 비움. **대상을 다른 사람으로 옮기면 옮긴 때가 그 사람의 경고한 때다** — 그 사람이
   경고받은 날이 그날이라서다. 나가 있다가 다시 경고로 들어오면 그날이 새 경고다. 셈 셋과 이용자 안내의 「경고한 날」, 처분 이력 ·
   대상 요약의 경고 줄 시각이 이것을 읽는다. `reviewed_at` 은 「마지막으로 본 시각」 그대로다(처리 필요 · 목록). 지금 있는 경고는
   처분 이력에서 지금 결과로 이어진 같은 대상의 경고 줄들 가운데 첫 줄의 시각으로 채웠다. 보관 표(`retention.report`)도 같은 칸을
   들고 옮길 때 그대로 간다. 검사식이 「경고면 경고한 때가 있고, 아니면 없다」를 잠근다.
   **이것은 우리 운영 정책이다** — 처음 경고한 날부터 세고, 고쳐 적어도 시계를 다시 돌리지 않는다. YouTube 의 「각 경고는 적용
   시점부터 90일이 지나기 전에는 소멸되지 않습니다.」는 「경고가 적용된 때부터 센다」의 참고일 뿐이다 — 우리의 12개월도, 고쳐 적어도
   그대로 두는 규칙도 세우지 않는다.
5. **R-7 — 탈퇴 대기 계정에는 새 무상 지급을 받지 않는다 — 곧 지워질 계정에 주지 않으려는 운영 판단이다.** 리디의 「회원 탈퇴 시
   소멸」과 법 제21조는 탈퇴 대기 중의 지급을 막지 않는다 — 맥락이지 근거가 아니다. 공통 함수가 `23514` 「탈퇴 대기 계정이라 지급할 수 없습니다.」(정지에서
   탈퇴 대기로 못 가는 거절과 같은 코드)로 거절한다 — 화면의 문 · 런북 모두. 회수는 받고, 정지된 계정의 지급(장애 보상)도 받는다.
   같은 요청의 재시도는 첫 결과를 돌려준다. 회원 화면은 탈퇴 대기면 지급 단추를 잠그고 같은 문장을 곁에 둔다.
6. **R-8 — 지급 장부를 매일 잰다.** 크론 `credit-grant-watch`(매일 05:41 UTC)가 `watch_reading_credit_grants()` 로 계정마다
   `Σ(지급 − 회수) = extra`(행이 없으면 0)를 재서, 다른 계정마다 `notify_ops` 한 줄(종류 `credit-grant-mismatch:<계정 id>`, 하루 한
   번 — `ops_alert` 의 `(kind, day)`). 계정 id 와 두 수만 가고, **아무것도 고치지 않는다.** 잡이 실패하면 `cron-watch` 가 본다.
   Stripe Ledger 는 참고이고, 매일 돌리고 알리기만 하는 것은 우리 설계다.
7. **R-9 — 쓰는 순서는 지금과 앞으로를 가른다.**
   1. **지금(코드 그대로)** — 몫의 출처 순이다: 무료 → 운영 지급 → 산 때가 이른 묶음. 무상을 유상보다 먼저 쓰는 본보기로 카카오 광고
      캐시의 「무상캐시와 유상캐시가 모두 있는 경우, 무상캐시가 우선 소진됩니다.」가 있다 — 참고이고, 순서는 우리 운영 판단이다.
   2. **앞으로(정했고 아직 안 했다)** — 유효기간을 DB 가 걷을 때(G-25, 약관 시행과 함께) 순서를 출처가 아니라 **소멸일 순**으로 고르고,
      화면에 몫마다 소멸일을 보이며, 「유효기간 임박」 안내를 보낸다(며칠 전 · 어느 길인지는 그때 정한다). 리디 제5조의 「유효기간
      임박」은 이 안내의 참고일 뿐 순서의 근거가 아니다.
   잰 것: 지금의 출처 순이 소멸일 순과 어긋나는 갈래가 하나다 — 산 지 4년이 넘은 묶음이 남은 계정에 운영 지급을 하면 그 지급(+1년)이
   묶음(+5년)보다 늦게 소멸한다. 판매가 닫혀 있어(`reading_sale_is_open()`) 첫 판매 뒤 4년까지는 생기지 않는다.

## 근거 (확인 2026-10-17)

「갈래」 칸의 낱말 — **근거** 는 그 결정이 기대는 것, **맥락** 은 결정을 요구하지 않지만 둘레를 말하는 것, **참고** 는 다른 서비스의
본보기로 결정을 세우지 않는 것이다.

## 버린 것

- **R-3 — DB 가 직접 UPDATE 를 막고 break-glass 만 따로 연다** — 할 수 있었다. 탈퇴 흐름과 break-glass 가 모두 `status` 를 써
  막는 길과 여는 길을 따로 지어야 하고, 막아도 소유자는 트리거를 끌 수 있어 막기가 완전하지도 않다. 기록과 알림, 밖의 사본(Object
  Lock)이 지키는 쪽을 골랐다(운영 판단).
- **R-4 — 거절을 `denied` 로 같이 적는다** — 월 점검의 「연속 거절」(운영자가 아닌 사람이 문을 두드림)과 섞인다. 값을 갈랐다.
- **R-4 — 결과 칸 대신 오류 분류 칸(`error_class`)을 쓴다** — CLI 결과 줄의 칸이고, 앱 줄의 검사식을 다시 지어야 한다. 대상 id 가
  이미 거른 조건 칸에 있어 같은 칸에 코드를 잇는 쪽이 작다.
- **R-4 — 묶음 `version` 을 4 로 올린다** — 칸이 그대로다. 값이 늘 때마다 올리면 동작 이름이 늘 때도 올려야 한다(지금까지 안 올렸다).
- **R-6 — 옮긴 경고도 처음 경고한 날을 물려받는다** — 옮겨 간 사람이 경고받지 않은 날을 그 사람의 경고로 센다.

## 치르는 값

- 운영자의 거절마다 앱이 DB 를 한 번 더 부른다. 적지 못해도 화면의 답은 그대로다(서버 기록에만 남는다).
- 반출본을 받는 쪽은 `outcome` 이 셋일 수 있다는 것을 알아야 한다 — 런북이 적었다.
- 확정 전의 환불(`credits.refund_book`)이 거절되면 그 줄의 주문 id 는 확인된 때만 있다 — 확보가 이미 닫혔으면 비고, 같은 운영자의
  바로 앞 `credits.refund_status` · `credits.refund_hold` 줄이 주문을 가리킨다. 확인 읽기가 `credits.refund_status` 한 줄을 더 남긴다.
- 거절 빗장(시간당 30)에 닿은 뒤의 거절은 줄 없이 버려진다 — 알림은 「버리기 시작했다」만 말한다(하루 한 번).
