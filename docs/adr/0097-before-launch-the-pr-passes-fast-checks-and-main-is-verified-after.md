# 공개 출시 전에는 PR 이 빠른 검사만 지나고, 전체 검증은 머지 뒤 최신 main 에서 한다

운영 베타에는 실제 사용자가 없다(ADR 0093). 그런데 PR 마다 전체 CI(약 5분)가 돌고, strict(ADR 0082)가 뒤에 선
PR 을 최신 main 위에서 다시 돌렸다 — 2026-09-23 에 #151 은 두 번 다시 돌았다. 로컬에서도 화면을 건드리면 커밋 전에
e2e 를 돌렸다. 다치는 사람을 막는 값보다 기다리는 값이 컸다. 사람이 정했다: **빠르게 밀고 뒤에서 검증한다.**

## 정한 것

> 운영 베타에서는 PR 이 빠른 검사를 통과하면 머지하고, 전체 검증은 최신 main 하나에서 비차단으로 수행한다. 새 main
> 실행은 이전 main 검사를 대체한다. PRD §7.0 의 단계가 공개 출시로 옮겨지면 PR 전체 검증 정책으로 자동 복귀한다 —
> 실제 사용자 데이터가 들어오는 날에는 사람이 그날 단계를 옮긴다.

- **PR 의 필수는 `fast` 하나다** — 단위 · 타입 · 린트. 빌드는 뺐다: 빌드가 깨지면 Vercel 배포가 실패하고 이전 배포가
  선다. 정책 파일만 바뀌었으면 전처럼 `policy`. 필수 검사(`gate`)와 strict 는 그대로다 — 빠른 검사면 뒤 PR 을 다시
  돌리는 값이 작고, 「main 에 드는 상태는 최신 main 위에서 타입과 단위를 지났다」가 남는다.
- **`supabase/**` 는 단계와 상관없이 머지 전 전부다.** 이슈는 `supabase/migrations/**` 만 들었는데 넓혔다 — pgTAP ·
  `config.toml` · seed 도 DB 차선에서만 재어지고, `db:start` 가 깨지면 main 의 DB 차선이 다 선다. 라벨에 기대지 않는다.
- **단계를 모르면 전부다.** 「(지금)」이 없거나 둘이거나 표에 없는 이름이면 안전 쪽이다. 단계 표는
  `scripts/release-stage.mjs` 한 곳이고 등급 3 시험(ADR 0093)도 같은 것을 읽는다.
- **main 은 최신 하나만 끝까지 잰다.** 한 concurrency 그룹에서 새 푸시가 앞 실행을 끊는다. 최신 main 은 앞선 커밋을
  다 품는다. 잃는 것은 「어느 커밋이 깼나」를 바로 모르는 것이라 붉은 이슈가 마지막 초록부터의 범위를 적는다.
  하루 한 번의 일정은 제 그룹이다.
- **붉은 main 은 `ci-main-red` 이슈 하나가 든다**(`main-red.yml` · `scripts/main-red.mjs`). 실패면 열고, 이미 열려
  있으면 댓글, **지금 main 머리**가 초록이면 닫는다. 끊긴 실행은 무시한다. `issues: write` 는 `workflow_run` 으로 도는
  그 워크플로에만 있다 — PR 을 도는 verify 는 이슈를 못 건드린다. 위임 규약은 열린 이슈를 새 작업보다 먼저 두게 한다.
- **로컬 최소는 단위 · 타입 · 린트다.** 예외 넷 — e2e · 흐름 시험 자체를 고치면 그 시험 한 번, 새 잠금 · 계약 시험은
  일부러 깨뜨려 확인, 마이그레이션은 pgTAP · 생성 타입, 프롬프트 본문은 실호출 한 번. 「일부러 어긴 것」은 새 잠금에만.

## 그대로 지키는 것

등급 4(`deny`) · 원격 잠금(`db:push` · `db:remote`, ADR 0096) · 마이그레이션의 넓히기 → 앱 → 좁히기와 「마이그레이션이
먼저, 앱이 나중」(runbook 「배포」). 이것들은 CI 가 대신 못 하는 순서라 속도와 바꾸지 않는다.

## 언제 되돌리나

PRD §7.0 의 「(지금)」이 공개 출시로 옮겨지는 날 — `ci-plan.mjs` 가 그 PR 부터 머지 전 전체로 계획한다. 실제 사용자
데이터가 먼저 들어오면 그날 사람이 단계를 옮긴다(runbook 「초대」). main 의 concurrency 는 그때도 최신 하나로 둔다 —
머지 전 검증이 다시 전부가 되면 main 실행은 확인일 뿐이다.
