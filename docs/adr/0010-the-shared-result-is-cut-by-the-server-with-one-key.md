# 공유 결과는 매인 판본으로 나고, 자르는 일만 열쇠 하나를 쓴다

ADR 0008 은 「자르는 것은 서버가 한다」고 정했다. 이 ADR 은 **그 서버가 어디인지**를
정한다 — Match 결과 화면을 세우려니 그 자리가 비어 있었다.

## 셋이 한꺼번에 참이라 다른 길이 없다

1. **브라우저에 내려보낼 수 없다.** 상대의 정확한 생년월일시·출생지·전체 명식은
   Match 가 여는 범위 밖이다(ADR 0008). 그런데 Supabase RPC 는 로그인한 사람이 그대로
   부를 수 있으므로, **definer 함수가 내주는 것이 곧 브라우저가 볼 수 있는 것**이다
   (ADR 0003 「이행」).
2. **DB 는 명식을 계산할 수 없다.** 절기·자시·경도 판정이 TypeScript 엔진에 있다.
3. **형충회합을 SQL 에 다시 적을 수 없다.** 후보 노출 때는 다시 적었다 — 오행 두 축은
   마흔 줄이고, 두 언어의 시험이 같은 입력에 같은 기대값을 든다. 관계 판정은 다르다.
   `relations/` 는 구백 줄이고 회합의 성립 조건·반합·삼형의 고리·우선순위가 전부 그
   안의 판단이다. 그것을 SQL 에 옮기면 **판정하는 자리가 둘**이 되고, 갈렸을 때
   사용자가 보는 것은 「같은 두 사람인데 화면마다 다른 관계」다.

후보 노출에서는 1·2 만 참이라 세 번째 길이 있었다 — 참여자가 자기 오행 요약을 풀에
내놓는 것(ADR 0003 「이행」). 여기서는 그 길이 없다. 관계는 두 사람의 글자가 **한 자리에
모여야** 나오고, 모을 수 있는 자리는 두 판본을 다 읽을 수 있는 곳뿐이다.

## 그래서 — 판정은 DB 가, 읽기는 열쇠가, 자르기는 서버가

ADR 0003 은 「`service_role` 은 사용자 경로에 쓰지 않는다」고 적었다. 그 근거는 **「무엇을
볼 수 있는가」의 답이 정책에서 앱 코드로 옮겨 가기 때문**이었다. 그 근거가 살아 있도록
구멍의 모양을 못박는다.

- **누가 볼 수 있는가는 DB 가 답한다.** `my_match_scope(match_id)` 가 사용자 JWT 로 돌고
  `auth.uid()` 로 판정한다. 당사자가 아니거나, 어느 한쪽이 중지됐거나, 차단이 걸려
  있으면 **한 줄도 나오지 않는다**. 앱은 그 답이 없으면 아무것도 읽지 않는다.
- **앱은 사용자 id 를 넘기지 않는다.** 열쇠로 부르는 함수는 `match_id` 하나만 받는다.
  앱이 「이 사람입니다」라고 대는 모양은 ADR 0004 가 거부한 것이다.
- **열쇠가 부를 수 있는 것은 함수 하나뿐이다.** `match_calculation_inputs(match_id)` 는
  **그 Match 가 매어 둔 두 판본**만 내준다. 앱은 판본 id 를 손으로 댈 수 없고, 어떤
  Match 도 매지 않은 판본은 이 문으로 나오지 않는다. 표 권한은 그대로 하나도 없다
  (`20260824090200_access_policies.sql`).
- **열쇠로 읽은 것은 브라우저로 나가지 않는다.** 나가는 것은 `Compatibility` 와
  `MatchPreview` 와 문장이다. 두 `Saju` 는 서버의 그 함수 안에서 나고 그 안에서 죽는다.

## 결과는 **매인 판본**으로 난다 — 지금 판본이 아니다

Match 는 두 `chartRevisionId` 를 든다(ADR 0004). 동의는 사람이 아니라 그때 그 입력에
대한 것이므로, 결과도 그 입력으로 나야 한다. 어느 한쪽이 나중에 출생정보를 고쳐도
**이 Match 의 결과는 움직이지 않는다** — pending 요청은 무효가 되지만(ADR 0009) 이미
성립한 Match 는 지우지 않기로 했고(PRD), 지우지 않기로 한 것이 조용히 다른 값이 되면
무엇을 남긴 것인지 알 수 없다.

내 쪽 판본도 같은 문으로 읽는다. 「내 것은 RLS 로 읽고 상대 것만 열쇠로」 하면 내 결과가
지금 판본을 따라가고 상대 것은 매인 판본에 머물러, **한 화면에 두 시점이 섞인다.**

## 무엇이 보이는가 — 고지를 좁힌다

결과 화면에는 두 원국 **사이의** 관계가 표로 선다. 그 표에는 걸린 글자가 적히므로
**상대의 글자 중 관계에 든 것은 보인다.** 이것은 ADR 0008 이 이미 인정한 것과 같은
종류다(`elementSupport` 는 오행 구성을 사실상 드러낸다 — 궁합 그 자체라 뺄 수 없다).
뺄 수 없으므로 **동의 화면이 정확히 적는다**: 상대의 여덟 글자 전부와 그 위의 판정
(십성·신살·원국 안의 형충회합·운)은 열리지 않고, 두 사람 사이에 걸린 글자는 보인다.

보내기 전·수락 전·결과 화면이 **같은 한 벌**을 읽는다(`MATCH_DISCLOSURE`). 결과를
만들면서 실제로 무엇이 나가는지 알게 됐으므로 그 한 벌을 좁힌다 — 고지가 좁아지는
것은 자리가 채워졌다는 증거다.

## Consequences

- **이 경로는 앱 코드에 기대는 유일한 자리다.** 그래서 밖에서 잰다: 결과 화면 본문에
  상대의 생년월일·출생지가 없는가, 당사자가 아닌 사람이 열면 없는 것과 같은 답인가,
  상대가 판본을 고쳐도 결과가 그대로인가. 셋 다 흐름 검사가 실제 스택에 대고 잰다.
- 열쇠가 없는 배포에서는 결과 화면이 **선다가 만다**. 조용히 빈 화면을 내지 않고 「지금
  결과를 열 수 없습니다」라고 말한다 — 없는 것을 없다고 말하는 것과 같은 규율이다.
- AI 는 아직 없다. 중립적인 해석은 L3 문장 조립기가 낸다(`assembleCompatText`). 8단계가
  이 자리 위에 Reading 을 얹을 때, **모델에 넘길 근거는 이 함수가 이미 잘라 둔 것**에서
  나온다 — 출생 원문은 그때도 이 경계를 넘지 않는다(ADR 0008).
