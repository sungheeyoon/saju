# 주문 화면은 환불 금액을 셈해 보이고, 운영자가 PG 콘솔에서 취소한 뒤 장부에만 적는다

> **조율자가 정한 기본값 2026-10-16**(G-110 ② 을 맡기며 — 운영자에게 보고한다). 이번 판의 환불 화면은 PG 취소를 부르지
> 않는다. 금액을 셈해 보이고, 운영자가 「PortOne 콘솔에서 취소한 뒤 장부에 적기」 한 걸음으로 장부만 적는다. PG 취소 API 를
> 같은 걸음으로 묶는 것은 판매를 열기 전에 운영자가 정한다(G-110 에 남는다).

ADR 0106 은 환불을 서버 열쇠만 부르는 문(`refund_reading_order`)으로 적게 했고, ADR 0148 은 그 금액의 산식을 정하며 「환불 셈
화면 · 자동 환불은 판매를 여는 PR 의 몫」으로 남겼다. 그 사이 운영자의 환불은 break-glass 로 운영 SQL 을 열어 금액을 손으로
셈해 넣는 일이었다(`docs/ops/runbook/credits.md` 「수동 환불」). 판매를 열기 전에 그 자리를 화면으로 옮긴다(G-110 ②).

## 정한 것

1. **주문 화면 `/ops/orders`** — 운영자가 주문 번호(`rdo_…`)를 넣으면 그 주문의 결제 · 묶음 · 쓴 수 · 예약 중 수 · 안 쓴 수 ·
   돌려준 금액 · 유효기간과 같은 계정의 다른 주문이 선다. 읽는 문은 이미 있던 `operator_reading_refund_basis` 이고, 읽을 때마다
   접속기록에 `credits.refund_basis` 한 줄(주문 id 만)이 남는다(ADR 0106 · 0105). 이메일 · 닉네임으로 찾지 않고, 계정이 누구인지
   보이지 않는다. 운영자가 아니면 화면이 없다(404) — 주문 번호 없이 열어도 문을 한 번 두드린다(빈 id, 기록 한 줄).
2. **금액은 화면이 셈해 보이고 DB 가 다시 셈한다** — 산식은 ADR 0148 의 누적 셈 하나다: `결제액 × (이미 걷은 회차 + 이번 회차)
   ÷ 산 회차`(원 미만 버림) − 이미 돌려준 금액. 화면은 `src/lib/reading/bundle.ts` 의 `refundOwed` 로 셈하고, 누르면 운영자가 본
   금액을 함께 보낸다. 새 쓰기 문 `operator_refund_reading_order` 가 같은 산식으로 다시 셈해 **같을 때만** `refund_reading_order` 에
   맡긴다 — 화면을 연 사이에 다른 환불이 끼었거나 두 산식이 갈리면 적지 않는다.
3. **PG 취소는 부르지 않는다** — 운영자가 PortOne 콘솔에서 그 금액을 먼저 취소하고, 받은 취소 번호를 적어 「장부에 적기」를
   누른다. 취소 번호는 빠질 수 없고, 같은 번호로 다시 누르면 한 번만 적힌다(회차 · 사유가 다르면 거절). 런북의 「PG 에서 먼저,
   장부는 뒤에」 차례 그대로다.
4. **운영자가 로그인한 채 환불을 적는다** — 새 문은 `authenticated` 에 열리고 안에서 `is_operator()` 로 닫힌다. 적을 때마다
   접속기록에 새 동작 `credits.refund` 한 줄(거른 조건 칸에 주문 id 만)이 같은 트랜잭션에 남고, 거절된 시도는 줄과 함께 되감긴다.
   운영자가 아니면 `42501` 이고 앱이 `note_operator_denial('credits.refund')` 로 따로 적는다. 서버 열쇠로 부르는
   `refund_reading_order` 는 그대로다 — 쓴 회차까지 돌려주는 미제공(`failure`)과 금액이 산식과 다른 환불은 여전히 런북의 SQL 이다.
5. **걷는 것은 안 쓴 회차뿐이다** — 화면은 1장부터 안 쓴 수까지 고르게 한다. 예약 중인 회차는 풀린 뒤에 걷는다(G-21 ③).
   사유는 DB 가 받는 다섯 가운데 하나이고 자유 글을 받지 않는다(ADR 0106).

## 까닭

- **사람이 셈하던 자리가 가장 틀리기 쉬웠다** — 누적 셈은 나눠 돌려줄 때 원 단위가 갈리고, 이미 돌려준 금액을 빼는 것을 잊으면
  결제액을 넘긴다. 산식을 코드 한 곳(화면)과 DB 한 곳에 두고 둘을 대조하면 어느 쪽이 갈려도 적히지 않는다.
- **PG 취소를 묶지 않은 것은 판매가 아직 닫혀 있어서다** — PortOne 취소 API 를 부르려면 비밀 열쇠의 권한 · 실패했을 때 장부를
  어떻게 둘지(PG 는 취소됐는데 장부 쓰기가 실패한 갈래)를 정해야 하고, 그 판단은 샌드박스에서 실제 응답을 본 뒤가 낫다. 지금의
  두 걸음은 런북이 이미 정한 차례(돈이 나간 뒤에 적는다)와 같아 새 위험이 없다.
- **break-glass 를 줄인다** — 주문 하나를 가리키는 쓰기를 운영 SQL 로 하던 것을 운영자 화면으로 옮기면 누가 · 언제 적었는지가
  접속기록에 남는다(ADR 0105). SQL Editor 의 쓰기는 기록이 하루뿐이다(`docs/ops/runbook/security.md`).

## 대가

- 운영자가 콘솔에서 취소하고 화면에서 적는 사이에 잊으면 PG 와 장부가 갈린다 — 「돈은 나갔는데 장부에 없다」. 웹훅은
  `Transaction.Paid` 만 받으므로(G-23 ⑥) 자동으로 메워지지 않는다. 결제 이상 알림(G-110 ④)과 PG 취소를 묶는 다음 판이 이 틈을 닫는다.
- 로그인한 운영자가 쓰기 문 하나를 더 갖는다 — 운영자 계정이 털리면 그 계정으로 장부에 환불을 적을 수 있다. 돈은 PG 콘솔을 거치지
  않으면 안 나가고, 적힌 것은 접속기록에 남는다.
- 접속기록의 동작 목록(`operator_access_action_check`)과 거절 문의 목록이 하나씩 는다 — 같은 목록을 고치는 마이그레이션이
  나란히 오면 머지 차례에서 합쳐야 한다.

## 바뀌지 않는 것 · 남은 것

- 환불의 산식(ADR 0148), 장부의 표 · 쓴 순서(ADR 0106), `refund_reading_order` 의 판정과 권한은 그대로다.
- PG 취소 API 를 「장부에 적기」와 한 걸음으로 묶을지는 G-110 에 남는다 — 판매를 열기 전에 운영자가 정한다.
