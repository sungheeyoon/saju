# 주문 화면의 환불은 확보 → PG 콘솔 취소 → 확정 세 걸음이고, 확보한 회차는 이용자가 못 쓴다

> **조율자가 정한 기본값 2026-10-16**(G-110 ② 을 맡기며 — 운영자에게 보고한다). 이번 판의 환불 화면은 PG 취소를 부르지
> 않는다 — 운영자가 PortOne 콘솔에서 취소하고 화면은 장부만 적는다. PG 취소 API 를 같은 걸음으로 묶는 것은 판매를 열기 전에
> 운영자가 정한다(G-110 에 남는다).
>
> **같은 날 리뷰(#727, P1)로 다시 짰다** — 첫 판은 「콘솔에서 취소 → 장부에 적기」를 누를 때에야 회차를 잠그고 셌다. 마지막
> 1장을 돌려주는 사이 이용자가 풀이를 시작하면 돈은 나갔는데 장부가 거절되고, 새로고침으로도 안 풀렸다. 조율자가 세 걸음
> (확보 → 취소 → 확정)으로 고쳐 쓰게 했다.
>
> **같은 날 두 번째 리뷰(P1 셋)로 더했다** — 탈퇴하면 진행 중인 확보가 주문과 함께 지워졌고(확정 불가), SQL 환불이 확보가 잡은
> 금액을 먼저 쓸 수 있었으며, 준비 취소가 콘솔 취소 여부를 안 봤다. 결정 3 · 6 · 8 이 그 답이다.
>
> **같은 날 세 번째 리뷰(P1 둘)와 운영자의 「실행 전 확인」 규칙(2026-10-16)으로 고쳤다** — 준비 취소의 판정이 시각 하나만 봐서
> 「확보 전 요청 → 확보 뒤 성공」 · 「확보 전 요청 → 아직 요청 중」 · 「확보 전 콘솔 취소 4,300원, 장부 0원」이 모두 지나갔다. 판정을
> 상태 · 금액으로 바꿨다(결정 6). 세 동작에 확인창 · 고정한 값 · 요청 번호를 둔다(결정 10).
>
> **덧(2026-10-18, G-110 닫음)** — 「PG 취소 API 를 확정과 한 걸음으로 묶을지」는 운영자가 2026-10-16 에 정했다 — PG 확정 뒤,
> 조건부로(확보 → 취소 요청 → PortOne 에서 성공 확인 → 장부 확정). 그 결정은 G-112 기록의 G-112-4
> (`docs/product/gaps/records/g-112.md` 「정한 것」 · 「PG 확정 뒤」)에 산다 — 이 ADR 의 「G-110 에 남는다」는 그리로 옮겨 읽는다.
>
> 후속 결정(일부): ADR 0193(운영자 결정 2026-10-20) — 「PortOne 콘솔에서 취소」와 준비 취소의 PortOne 결제 조회(결정 4 · 6). PG 는 포트원을 거치지 않고 PG사와 직접 계약하므로, 취소는 그 PG사의 관리자 화면에서 하고 조회는 그 PG사의 규격으로 다시 짓는다. 확보 → 취소 → 확정 세 걸음과 확보한 회차를 잠그는 결정은 그대로 선다

ADR 0106 은 환불을 서버 열쇠만 부르는 문(`refund_reading_order`)으로 적게 했고, ADR 0148 은 그 금액의 산식을 정하며 「환불 셈
화면 · 자동 환불은 판매를 여는 PR 의 몫」으로 남겼다. 그 사이 운영자의 환불은 break-glass 로 운영 SQL 을 열어 금액을 손으로
셈해 넣는 일이었다(`docs/ops/runbook/credits.md` 「수동 환불」). 판매를 열기 전에 그 자리를 화면으로 옮긴다(G-110 ②).

## 정한 것

1. **주문 화면 `/ops/orders`** — 운영자가 주문 번호(`rdo_…`)를 넣으면 그 주문의 결제 · 묶음 · 쓴 수 · 예약 중 수 · 안 쓴 수 ·
   돌려준 금액 · 유효기간과 같은 계정의 다른 주문, 그리고 **진행 중인 환불**이 선다. 이메일 · 닉네임으로 찾지 않고 계정이 누구인지
   보이지 않았는데, 확인창이 대상을 가르도록 그 계정의 **닉네임과 계정 내부 번호의 앞 8자**를 함께 보인다(결정 10 — 동명이인을 가른다,
   이메일은 여전히 안 보인다). 운영자가 아니면 화면이 없다(404) — 주문 번호 없이 열어도 문을 한 번 두드린다(빈 id, 기록 한 줄).
2. **확보** — 걷을 회차 · 사유를 고르고 「환불 준비」를 누르면 `operator_hold_reading_refund` 가 그 회차를 잠그고 금액을 확정해
   `reading_refund_hold` 에 「진행 중」으로 둔다. 금액은 ADR 0148 의 누적 산식이다 — `결제액 × (이미 걷은 회차 + 이번 회차) ÷ 산
   회차`(원 미만 버림) − 이미 돌려준 금액. 같은 주문에 진행 중인 확보는 하나뿐이다(유일 인덱스).
3. **확보한 회차는 이용자가 못 쓴다** — 한도(`reading_credit_shares` → `reading_credit_limit_for`, 풀이 시작 · 인연 요청 · 화면이
   모두 지난다)와 다음 쓰임의 몫 고르기(`pick_reading_credit_share`)가 진행 중인 확보를 뺀다. 확보는 풀이 시작과 같은 사람
   자물쇠(`reading:user:<id>`) 안에서 하므로 나란히 와도 한쪽만 그 회차를 갖는다. 서버 열쇠의 `refund_reading_order` 와 산 사람의
   결제 내역(`my_reading_orders`)의 남은 회차도 확보를 뺀다. **회차만이 아니라 금액도 확보가 먼저 잡는다** — 진행 중인 확보가 있는
   동안 그 주문의 다른 환불(`refund_reading_order`, 회차 없이 금액만이라도)과 두 번째 확보는 거절된다(`55000`). 확정은 확보를 닫은
   뒤 그 문을 부르므로 걸리지 않는다.
4. **취소** — 운영자가 PortOne 콘솔에서 확보된 금액을 취소한다. 화면은 그 일에 필요한 칸(취소할 금액 · 결제 금액 · 취소 후 잔액 ·
   걷는 회차 · 사유 · 결제 번호 · 거래 번호)을 한 판에 보인다 — 네이버페이 부분취소 화면의 꼴이다.
5. **확정** — 콘솔이 준 취소 번호를 넣고 「장부에 확정」을 누르면 `operator_book_reading_refund` 가 확보를 닫고 그 금액 · 회차 ·
   사유로 `refund_reading_order` 를 부른다. 같은 취소 번호로 다시 눌러도 한 번만 적힌다. 확정된 확보에 다른 번호, 이 주문의 앞
   환불이 쓴 번호, 빈 번호는 거절한다.
6. **준비 취소는 PG 의 취소 내역을 본 뒤에** — 확정 전에는 「준비 취소」(`operator_release_reading_refund`)로 확보를 풀어 회차를
   돌려놓는다. 확정된 것은 풀지 못한다. 서버 액션이 풀기 전에 PortOne 결제 단건 조회(웹훅과 같은 조회)로 그 결제의 취소 내역을 보고
   **시각이 아니라 상태와 금액으로** 가른다: ① `SUCCEEDED` · `FAILED` 밖의 상태(`REQUESTED` 등)인 취소가 하나라도 있으면 언제
   요청했든 막는다. ② `SUCCEEDED` 취소액의 합(PortOne 의 `amount.cancelled` 도 읽히면 그 합과 같아야 한다)이 **장부에 적힌 그 주문의
   환불액**(지금 주문이면 `reading_order.refunded_amount`, 떠난 뒤면 보관된 결제의 환불액 + 떠난 뒤의 환불 합 —
   `operator_reading_refund_hold` 의 `booked_refund`, 화면이 대지 않는다)과 **정확히 같을 때만** 푼다. ③ 크면 장부에 안 적힌 취소가
   있다 — 막고 확정을 권한다. 작거나 읽을 수 없으면 — 열쇠가 없음 · 실패 · 결제 없음 · 모양이 다름 · 금액 칸이 서로 다름 — 막는다
   (fail closed). 확보 시각은 판정에 안 쓴다. 그때는 운영자가 콘솔을 같은 규칙으로 보고 사유를 남겨 서버 열쇠의
   `release_reading_refund_by_hand` 로 푼다(런북 「준비 취소를 손으로」). 푼 근거는 확보 줄의 `release_note` 에 남는다. 확인 창은
   「콘솔에서 아직 취소하지 않았을 때만」을 말한다. 화면을 닫았다 다시 와도 `operator_reading_refund_hold` 가 진행 중인 것을 다시
   내주어 이어서 확정한다.
7. **접속기록** — 문마다 동작 하나: 진행 상태 읽기 `credits.refund_status`, 확보 `credits.refund_hold`, 확정 `credits.refund_book`,
   준비 취소 `credits.refund_release`(거른 조건 칸에 주문 id 만). 주문 셈 읽기는 그대로 `credits.refund_basis` 다. 같은
   트랜잭션이라 거절된 시도는 줄도 되감기고, 운영자가 아니면 앱이 `note_operator_denial` 로 같은 이름을 따로 적는다.
8. **산 사람이 탈퇴해도 진행 중인 확보는 남는다** — 탈퇴를 막지 않는다. 확보는 주문 · 묶음에 FK 로 매지 않고 확정에 드는 값(계정
   내부 번호 · 가맹점 주문 번호 · 거래 번호 · 결제액 · 취소 후 잔액)을 제 줄에 둔다. 탈퇴 처리(`retention.keep_payments_of_leaver`)는
   결제를 전처럼 `retention.reading_payment` 로 옮기고 그 사람의 **닫힌** 확보만 걷는다. 남은 확보는 주문 번호로 찾으면 「탈퇴한 계정의
   주문」 판으로 서고, 확정하면 보관된 결제의 환불 합이 결제액을 넘지 않는지 보고 **떠난 뒤의 환불 표** `retention.reading_refund_after_leave`
   에 적는다 — `reading_payment` 는 고칠 수 없어서다. 그 표는 보관 규율 그대로다(API 역할 셋에 닫힘 · 고치지 못함 · 보류 두 칸 · 환불 +
   5년 뒤 크론 `retention.purge_expired_payments` 가 지움). 같은 크론이 주문이 없는 닫힌 확보 줄도 걷고, 그 뒤의 확정 재시도는 떠난 뒤의
   환불 표의 확보 번호로 알아본다. 계정 내부 번호는 `reading_payment` 도 드는 값이고 새 개인정보는 없다.
9. **화면이 못 하는 것은 런북의 SQL 이다** — 쓴 회차까지 돌려주는 미제공(`failure`)과 금액이 산식과 다른 환불. 그 길도 진행 중인
   확보가 잡은 회차는 걷지 못한다. 런북의 서버 열쇠 SQL(`refund_reading_order` · `release_reading_refund_by_hand`)은 「실행 전 확인」을
   따른다 — 대상 주문 · 계정 앞자리 · 금액을 select 로 먼저 보고, `begin` → 실행 → 결과 select → 맞으면 `commit`.
10. **세 동작의 「실행 전 확인」(운영자 규칙 2026-10-16)** — 준비 · 확정 · 준비 취소는 모두 `app/ui/confirm-dialog.tsx` 의 확인창을
   지난다. 창은 대상(주문 번호 · 닉네임 · 계정 앞자리) · 회차 · 금액 · 사유 · 실행하면 무엇이 되는지를 보이고, 단추는 실행명이다
   (「2장 · 8,600원 환불 준비」 · 「장부에 확정」 · 「준비 취소 — 2장 돌려놓기」). **창을 여는 순간의 값을 고정해 그것을 낸다**
   (`app/ops/orders/refund-confirm.ts` 의 `preparePlan`) — 준비는 그 금액(`p_expected_amount`)을 함께 내고 DB 가 다시 셈해 다르면
   거절한다. 확정 · 준비 취소는 확보 번호가 금액 · 회차를 고정하고, 확정은 창에 보인 취소 번호를 낸다. **준비에는 요청 번호**
   (`p_request_id`, 창을 열 때 지음)가 있어 응답이 끊겨 같은 번호로 다시 오면 같은 확보가 돌아온다(다른 회차 · 사유면 거절).
   확정은 취소 번호로, 준비 취소는 확보 상태로 이미 한 번만 적힌다. 처리 중의 두 번째 누름은 버리고(`oneAtATime`), 실패하면 고른
   값 · 요청 번호 · 취소 번호가 남는다. 성공하면 액션의 응답이 DB 에서 다시 읽은 화면을 싣고, 응답을 못 받으면 화면이 서버를 다시
   읽어 실제 결과를 세운다. 조회 · 검색 · 화면 이동에는 확인창이 없다.

## 까닭

- **돈이 먼저 나가므로 회차를 먼저 잠근다** — 콘솔 취소는 되돌리기 어렵고 장부 쓰기는 거절될 수 있다. 거절될 까닭(남은 회차가 없음)을
  돈이 나가기 전에 없애 두면 확정은 취소 번호 하나만 남는다.
- **사람이 셈하던 자리가 가장 틀리기 쉬웠다** — 누적 셈은 나눠 돌려줄 때 원 단위가 갈리고, 이미 돌려준 금액을 빼는 것을 잊으면
  결제액을 넘긴다. 금액을 확보할 때 DB 가 정해 두면 콘솔에 넣을 금액과 장부에 적힐 금액이 같은 값이다.
- **PG 취소를 묶지 않은 것은 판매가 아직 닫혀 있어서다** — PortOne 취소 API 를 부르려면 비밀 열쇠의 권한 · 취소는 됐는데 장부 쓰기가
  실패한 갈래의 처리를 정해야 하고, 그 판단은 샌드박스에서 실제 응답을 본 뒤가 낫다.
- **break-glass 를 줄인다** — 주문 하나를 가리키는 쓰기를 운영 SQL 로 하던 것을 운영자 화면으로 옮기면 누가 · 언제 적었는지가
  접속기록에 남는다(ADR 0105). SQL Editor 의 쓰기는 기록이 하루뿐이다(`docs/ops/runbook/security.md`).

## 대가

- 운영자가 콘솔에서 취소하고 확정을 잊으면 확보가 진행 중으로 남는다 — 이용자는 그 회차를 못 쓰고 장부에는 환불이 없다. 화면이
  다시 열 때마다 진행 중인 것을 보이지만, 스스로 닫히지는 않는다.
- 진행 중인 확보가 있는 동안 그 주문에는 SQL 환불도 막힌다 — 급한 미제공 환불은 확보를 먼저 확정하거나 준비 취소한 뒤에 한다.
- 준비 취소는 PG 의 성공한 취소액이 장부와 **정확히** 같아야 풀린다 — 장부에 안 적은 다른 경로의 취소(SQL 환불 전의 콘솔 취소 등)가
  하나라도 있으면 그것을 먼저 확정하거나 손으로 맞춰야 한다.
- 준비 취소는 PortOne 조회에 기댄다 — 열쇠가 없는 환경(지금의 운영 · 로컬)에서는 화면의 준비 취소가 늘 막히고 런북의 손 걸음을
  밟는다. 콘솔 확인은 사람의 눈이다.
- 앱의 준비 취소는 PortOne 확인을 서버 액션이 한다 — 운영자가 DB 문을 PostgREST 로 직접 부르면 그 확인을 건너뛴다. 운영자는 믿는
  사람이고 그 부름은 접속기록에 남는다.
- 탈퇴 뒤의 환불은 `reading_payment` 와 다른 표에 있다 — 보관된 결제의 환불 합을 보려면 두 표를 함께 본다. `reading_payment` 의 파기
  예정(`keep_until`)은 탈퇴 뒤의 환불로 늘지 않으므로, 결제 줄이 먼저 지워지고 떠난 뒤의 환불 줄이 더 오래 남을 수 있다.
- 로그인한 운영자가 쓰기 문 셋을 더 갖는다 — 운영자 계정이 털리면 장부에 환불을 적거나 회차를 잠글 수 있다. 돈은 PG 콘솔을
  거치지 않으면 안 나가고, 적힌 것은 접속기록에 남는다.
- 접속기록의 동작 목록(`operator_access_action_check`)과 거절 문의 목록이 넷 는다 — 같은 목록을 고치는 마이그레이션이 나란히
  오면 머지 차례에서 합쳐야 한다.

## 다음

- **PG 취소를 웹훅으로 받아 대사한다** — 지금 웹훅은 `Transaction.Paid` 만 받는다(G-23 ⑥). PortOne 의 취소 알림을 받아 진행 중인
  확보와 맞추면 「콘솔에서 취소했는데 확정을 잊음」과 「확정했는데 콘솔 취소가 없음」을 잡는다. 이번에는 하지 않는다.
- PG 취소 API 를 확정과 한 걸음으로 묶는 것은 PG 확정 뒤, 조건부로 간다 — 운영자 결정 2026-10-16, G-112-4(머리의 덧).
- 처리방침 · 보관 문서가 떠난 뒤의 환불 표를 들어야 하는지 — 결제 기록 5년의 같은 갈래라 새 항목은 아니지만, 표 이름을 적는 문서
  (`docs/legal/`)는 다음 처리방침 판에서 맞춘다.

## 바뀌지 않는 것

- 환불의 산식(ADR 0148), 장부의 표 · 쓴 순서(ADR 0106), `refund_reading_order` 의 권한(서버 열쇠만)과 재시도 규칙은 그대로다.
