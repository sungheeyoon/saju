# 풀이 회수가 집은 일감은 임대다 — 지금 쥔 작업자만 닫고, 일시 장애는 닫지 않고 놓는다

> **운영자가 설계와 범위를 승인했다(2026-10-23 낮 세션, 나이트 인계 「A. 풀이 회수 보완」).** 결정 점검표의 「실패했을 때
> 열리는가 닫히는가」에 걸린다 — 일시 장애가 실패로 닫히던 것을 놓기로 바꾼다. 8분 기한과 「기한 지난 `submitted` 는 마지막
> 조회 없이 닫는다」(ADR 0020, `app/api/cron/reading/route.ts`)는 그대로다.

## 무엇이 틀렸나 — origin/main 92e4a4b8 에서 잰 값(2026-10-23)

1. **집은 일감이 `retrieving` 에 갇힌다.** 집은 시각이 없어, 회수하던 함수가 죽으면(`maxDuration` · 배포 교체) 아무도 안 놓는다.
   `open_reading_jobs`(`20260925090000` 의 720줄)가 `retrieving` 을 8분 기한까지 건너뛰고, 기한 뒤 복구기
   (`app/api/cron/reading/route.ts` 88줄)가 결과가 provider 에 다 있어도 `model-timeout` 으로 닫는다.
2. **일시 장애가 최종 실패다.** 조회 예외는 모두 `model-retrieve-failed`(`app/me/reading/model.ts` 460줄), 저장의 DB 오류는 모두
   `save-rejected`(`app/me/reading/collect.ts` 238줄)로 곧바로 닫혔다 — 사용자는 실패 소식을 받고 풀이권은 풀린다.
3. **회수 조회에 앱이 정한 상한이 없다.** `new OpenAI()`(`model.ts` 263줄)의 SDK 기본은 10분 · 다시 2번이라 복구기
   (`maxDuration` 300초) · webhook(60초)보다 길다. 복구기는 일감을 차례로 돌아, 하나가 매달리면 뒤가 다 밀린다.

## 정한 것

| 물음 | 답 |

| 누가 놓고 · 저장하고 · 닫나 | 식별자를 든 부름은 **지금 쥔 작업자일 때만** — `release_reading_job` · `save_reading` · `fail_reading_job` 에 `p_lease_id`. 옛 작업자의 늦은 응답은 놓기 `false` · 저장 거절(23514) · 닫기 `false` |
| 임대는 얼마나 | **2분**(`reading_job_lease()`). 지나면 다른 작업자가 다시 집고, 복구기(`open_reading_jobs`)가 그 일감을 회수로 보낸다 |

## 임대시간의 셈

일감 하나를 쥐는 동안 기다림이 있는 것은 망을 지나는 셋이다. 집은 시각(`claimed_at`)부터 마지막으로 적을 때까지:

| 걸음 | 상한 | 근거 |
| --- | --- | --- |
| 집기의 답이 돌아옴 | 10초 | DB 부름 상한 |
| 회수 조회 | 10초 × 2번 | `timeout` 은 시도마다다(`openai` 7.8 `client.js` 의 `makeRequest`) |
| 다시 보내기 전 기다림 | 60초 | SDK 는 `retry-after` 가 60초 이하면 그대로 따르고, 넘거나 없으면 제 셈(0.5초부터 두 배, 8초까지)을 쓴다(`retryRequest`) |
| 저장 · 실패 · 놓기 | 10초 | DB 부름 상한 |
| 검사 | 셈 안 함 | 밀리초 |
| **합** | **100초** | `HOLD_BOUND_MS`, `app/me/reading/lease.test.ts` 가 잰다 |

100초 < **2분** < 8분 기한. 2분은 상한에 20초를 남기고, 죽은 작업자의 일감은 임대 2분 + 복구기 한 바퀴(1분) = 3분 안에 다시
집힌다 — 기한까지 5분이 남는다. webhook 의 작업자는 60초에 끊기므로 임대 안에서 죽고, 복구기의 작업자는 일감 하나에 100초를
안 넘긴다.

**임대가 짧아도 틀린 값은 안 남는다** — 저장 · 실패는 시도 행을 잠그고 일감 행을 잠근 뒤 식별자를 견주고(늘 이 차례 — 집기 ·
놓기는 일감 행만 잠근다), 시도는 `running` 에서 한 번만 떠난다. 상한을 넘기면 같은 결과를 둘이 회수하는 낭비가 생길 뿐이다.

## 중복 저장 · 중복 정산이 없는 까닭

저장은 됐는데 답만 끊기면 앱은 그것을 일시 장애로 보고 놓는다. 시도는 이미 `succeeded` 이고 일감은 지워졌다
(`reading_run_terminal_clears_job`) — 놓기는 `false`, 다음 바퀴는 집을 일감이 없다. 두 번째 저장은 「이미 끝난 시도입니다」에서
서고, 실패 닫기는 `false` 다. 풀이권 정산(`reading_run_settles_its_credit`)은 시도가 `running` 에서 떠날 때 한 번 돈다
(`supabase/tests/99_reading_job_lease.test.sql`).

## 버린 안

- **DB 가 임대 식별자를 지어 집기의 답에 싣는다** — 옛 앱의 집기도 식별자를 받게 되어, 식별자를 모르는 옛 앱의 놓기 · 저장이
  제 일감에서 거절된다. 앱이 지어 넘기면 「식별자 없이 집힌 일감」이 옛 앱의 것으로 갈린다.
- **놓기 실패를 다시 시도한다** — 임대가 지나면 풀린다. 한 자리를 두 번 지키지 않는다.
- **기한 지난 `retrieving` 도 마지막으로 한 번 조회한다** — 8분 기한의 결정(ADR 0020)을 바꾸는 일이라 이 범위 밖이다.
