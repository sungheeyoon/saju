# 익명 흐름의 입력은 쿼리스트링이 아니라 fragment 에 싣는다

익명 궁합 링크는 **두 사람의 이름·생년월일시·성별·출생지**를 통째로 들고 있다
(`?name=…&date=…&hour=…&gender=…&city=…&brule=…`). 쿼리스트링은 HTTP 요청 라인에
실리므로 이 값이 매 요청마다 서버 로그에 남고, 카카오톡·슬랙에 링크를 붙여 넣으면 그
서비스의 미리보기 크롤러가 URL 을 fetch 하면서 두 사람의 생년월일시를 가져가고,
결과 화면에서 외부 링크를 하나만 눌러도 `Referer` 로 새어 나간다.

**URL fragment 는 HTTP 요청에 아예 포함되지 않는다.** 링크 공유는 그대로 되고 — 받은
쪽 브라우저가 `#` 뒤를 읽어 똑같이 계산한다 — 서버도 크롤러도 못 본다. 익명 흐름은
브라우저가 계산하고 서버는 저장된 Person id 로만 계산하기로 이미 정했으므로, 서버가
이 값을 못 읽게 되는 것은 손해가 아니다.

코덱(`queryToSearchParams` / `queryFromSearchParams`)은 `URLSearchParams` 하나로
분리되어 있어 **한 줄도 바뀌지 않는다.** 바뀌는 것은 `useSearchParams()` 를
`new URLSearchParams(location.hash.slice(1))` 로 읽는 두 컴포넌트와, `?` 를 `#` 로
바꾸는 e2e URL 뿐이다.

## 함께 하는 것

- 옛 `?` 링크는 클라이언트가 읽은 뒤 `replaceState` 로 `#` 형식으로 바꾼다. **이것은
  링크를 안 깨뜨리기 위한 것이지 프라이버시를 위한 것이 아니다** — 그 링크가 열리는
  한 번의 요청에서 값은 이미 서버에 닿았고, 이미 뿌려진 링크는 되돌릴 수 없다.
- `Referrer-Policy: no-referrer`.
- 공유 화면이 **링크에 두 사람의 출생정보가 들어 있다고 직접 말하고**, `name` 에는
  별명을 권한다.

## 못 고치는 것

브라우저 히스토리에는 그대로 남는다. 링크를 받은 사람은 당연히 다 본다 — 그게 기능이다.

## 지금 옮기는 이유

나중에 옮기면 이미 공유된 `?` 링크를 서버가 `#` 로 리다이렉트해야 하는데, 그러려면
서버가 그 값을 봐야 한다 — 그게 바로 안 보려던 것이다.

## 분석 도구가 fragment 를 수집하면 이 결정은 무효다

대부분의 분석 SDK 는 `location.href` 를 통째로 기록한다. fragment 로 옮겨 놓고 분석
도구가 그것을 서버로 보내면 아무것도 안 한 것이 된다. **분석 도구를 붙일 때마다 hash
수집 여부를 확인하고 끄는 것이 이 ADR 의 일부다.** 이것은 「나중에 살펴볼 것」이 아니라
결정이 성립하기 위한 조건이다.

## 이행 — 저장된 Person 의 궁합은 `/me/compat` 에서 서버가 계산한다 (2026-08-24)

위 11행이 「서버는 저장된 Person id 로만 계산한다」고 이미 정했다. 여기서는 그것을
어떻게 이행하는지만 적는다. 새 결정이 아니다.

```
익명   /compat#<입력 두 벌>          → 브라우저가 계산 → 전체 궁합 화면
관리   /me/compat?a=<id>&b=<id>      → 서버가 판본 둘을 읽고 계산 → 전체 궁합 화면
향후   Match 화면                     → 서버가 Match 를 확인하고 **잘라서** 내려보냄
```

- 주소에는 **Person id 두 개만** 둔다. 저장된 출생 원문을 fragment 로 옮기지 않는다 —
  옮기면 남이 등록한 가족의 생년월일시가 주소창에 실리고, 그것은 이 ADR 이 익명
  링크에서 막으려던 것과 같은 일이다.
- id 가 요청 라인에 실리는 것은 피할 수 없고 괜찮다. 서버가 읽어야 하는 값이고, 불투명
  식별자이며, 접근은 RLS 가 잠근다. 이 ADR 이 막은 것은 **출생정보**이지 식별자가 아니다.
- 조회는 `supabaseOnServer()` 의 사용자 JWT 로 한다. **이 managed 경로에는 조회용
  `security definer` RPC 도 `service_role` 도 쓰지 않는다** — RLS 가 이미 답을 들고
  있는데 definer 를 세우면 판정하는 자리가 둘이 된다(ADR 0004).
  **Match 경로까지 금지하는 말이 아니다.** 상대의 판본은 사용자 JWT 로 읽혀서는 안
  되므로(ADR 0008), 그쪽은 자격을 명시적으로 검사하고 잘라서 내주는 서버 함수가
  필요할 수 있다. 그 결정은 6단계에서 한다.
- 계산은 기존 순수 코드 그대로다(`queryFromRevision` → `chartOf`). 저장하기 전에 본
  사주와 저장한 뒤에 보는 사주가 다를 자리를 만들지 않는다.

### 브라우저로 무엇이 내려가는지는 **접근 근거가 정한다**

근거는 「내가 등록하고 내가 입력한 사람이라서」가 **아니다.** 그 말은 항상 참이 아니다 —
claim 이 일어나면 기존 관리자는 `viewer` 로 내려가므로(`demote_others_on_claim`), 자기가
넣어 놓고 더는 못 고치는 Person 이 생긴다.

정확한 근거는 이것이다. **`user_person_access` 엣지가 있으면 RLS 가 이미 그 Person 의
판본 전체를 읽게 해 준다**(`"Person 이 보이면 그 판본도 보인다"` 정책은 역할을 묻지
않는다). 그러므로 managed 응답은 **사용자가 이미 조회할 수 있는 범위를 넓히지 않는다.**
`/me` 가 이미 그렇게 동작한다(`ReviseChart current={query}`, 「전체 명식 보기」가 자기
입력을 `#` 뒤에 싣는다). 4단계에서 자를 것은 없다.

자를 것이 생기는 것은 Match 상대이고, 그 범위는 ADR 0008 이 이미 정했다. 그때
`CompatView` 를 그대로 쓸 수는 **없다** — 지금 결과 화면은 양쪽 전체 명식과 Evidence 를
받는 구조라(`ChartPair` · `EvidencePanel`) 상대의 전체 명식이 빠지면 화면 일부가
달라져야 한다. **재사용되는 것은 서버의 자료 경계와 순수 계산 코드까지**이고 그 위는
갈라진다.

`/me/compat` 이 재사용하는 것도 `CompatCalculator` **전체가 아니다.** 그 컴포넌트는
fragment 입력 폼과 계산을 함께 든다(`app/compat-calculator.tsx:142`). 꺼내야 하는 것은
결과 영역인 `CompatView`(243행)이고, 익명 화면과 관리 화면이 그것을 공유한다. 입력을
어디서 받는지가 두 화면의 유일한 차이여야 한다.

payload 종류를 **인자로 받지 않는다.** 호출부가 `'managed'` 라고 댈 수 있으면 언젠가
Match 자리에서도 그렇게 댄다(PRD 183·235행).

그런데 **판별자를 내주는 것만으로는 반쪽이다.** `accessTo(personId)` 가
`{ via: 'managed' }` 같은 평범한 구조체를 내고 그 타입이 밖에 열려 있으면, 호출부가
똑같은 객체를 손으로 지어서 넘길 수 있다. 문자열 인자를 없앤 효과가 사라진다.

공개되는 것은 **묻지 않고 답만 내는 함수 하나**여야 한다.

```
payloadForViewer(personId)
  └─ 안에서 접근 근거를 조회하고
  └─ 안에서 무엇을 자를지 정하고
  └─ 허용된 payload 또는 null 을 낸다
```

`via` 판별자는 모듈 안에만 두거나, 밖에서 지을 수 없는 증표로 만든다. 보장하는 것은
암호가 아니라 **모양**이다 — 잘못 부를 인자가 존재하지 않는다.

4단계에는 `managed` 하나뿐이다. 그래도 이 경계를 지금 세우는 것은, 안 세우면 6단계에
「매치인가」를 묻는 분기가 호출부마다 흩어지기 때문이다.

### 없는 사람과 못 보는 사람은 같은 말로 거절한다

`?a=` 에 아무 UUID 나 넣었을 때 「그런 사람 없습니다」와 「볼 수 없습니다」가 갈리면,
그 응답 차이만으로 **그 Person 이 실재하는지**를 알아낼 수 있다. RLS 는 「안 보인다」
까지만 해 주고 그다음 문장은 화면이 쓰므로, 두 경우를 한 문장으로 묶는다.

**문장만 같아서는 부족하다.** 실재하지 않는 UUID 와 실재하지만 내 것이 아닌 UUID 에
대해 넷이 다 같아야 한다.

- HTTP 상태
- 사용자에게 보이는 문장
- 그려지는 화면의 종류
- 밖으로 나가는 응답의 구조

pgTAP 이 재는 것은 「둘 다 RLS 에서 안 보인다」까지다. **이 동등성은 서버 통합 시험이나
e2e 가 재야 한다** — 다른 층이므로 한쪽만 두면 못 잰다.

### id 링크는 언제나 지금 판본을 본다

`person.current_revision_id` 가 그 뜻이다. 특정 시점을 붙드는 것은 MatchRequest 가
revision 을 고정하는 일이고(PRD US 37·42) 층이 다르다.

화면은 그것을 **지문이 아니라 문장으로** 말한다 — 「현재 저장된 출생정보 기준입니다.
출생정보를 수정하면 이 결과도 달라질 수 있습니다.」 지문 앞자리는 판본 이력에만 둔다.
거기서는 구별이 전부이고(`app/me/page.tsx` 의 `RevisionHistory`), 결과 화면에서는
구별이 아무것도 아니다.
