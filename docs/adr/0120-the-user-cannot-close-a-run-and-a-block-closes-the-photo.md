# 사용자는 제 시도를 실패로 닫지 못하고, 차단은 요청을 주고받은 상대의 사진까지 닫는다

> **섰다**(2026-09-28). 밤샘 감사의 보안 발견 둘 — 운영자가 자는 동안 에이전트가 정했다. 되돌릴 수 있는 결정이고 대가는
> 아래 「값」에 적었다. 같은 마이그레이션(`20261030090000`)이 정합성 발견 둘(서울의 종료일 · 첫 덱 경합)도 고쳤는데,
> 둘은 결정이 아니라 적힌 뜻대로 고친 것이라 여기 안 적는다.

## 잰 것

**1. `fail_reading_run` 이 `authenticated` 에게 열려 있었다**(`20260909090000` 의 마지막 정의). 사용자가 PostgREST 로 제
`running` 시도를 곧바로 실패로 닫을 수 있었다. `start_reading_run` 은 두 수를 센다 — 사람마다 한 시간에 연 시도(`reading_rate_limit()` = 20), 서비스
전체가 오늘(서울) 연 시도(`reading_daily_budget()` = 500). **둘 다 실패한 시도를 센다**(상태를 안 가린다). 풀이권은 실패한
시도를 안 센다. 그래서 열고 닫기를 되풀이하면 풀이권 하나도 안 쓰고 한 시간 한도를 다 채울 수 있었고, 계정 몇이 모이면 그날
**모든 이용자**의 풀이가 「오늘 만들 수 있는 풀이를 모두 썼습니다」로 섰다 — 500 = 20 × 25 라 계정 둘이면 열세 시간,
스물다섯이면 한 시간이다. `p_usage` 에는 브라우저가 보낸 JSON 이 그대로
적혀 지출 집계(`reading_spend_daily`)를 흐렸다.

앱에서 이 문을 부르는 자리는 **하나**였다 — `app/me/reading/pipeline.ts` 의 `failAsUser`, `keyedClient` 가 던질 때(열쇠가 없는
배포)만 도는 길. 운영에는 열쇠가 있다. 그 밖에는 흐름 검사 `check-reading` 두 곳과 pgTAP 다섯 파일이 시도를 닫는 도구로 불렀다.

**2. 차단해도 요청을 주고받은 상대는 사진을 계속 봤다.** `may_see_photo`(`20261001100000` 의 마지막 정의)의 요청 갈래가
`status <> 'cancelled'` 만 봤다. `block_user` 는 받은 쪽이 차단하면 요청을 `rejected` 로, 보낸 쪽이 차단하면 `cancelled` 로
거둔다 — 앞의 경우 차단당한 요청자와 차단한 사람 **둘 다** 서로의 사진을 계속 봤다. 수락된 요청도 같았다(성립한 쌍의 갈래
`visible_matches` 는 차단을 보지만 요청 갈래가 다시 열었다). `my_match_requests` 는 끝난 요청에도 상대의 소개와 사진 표시를
실었다. pgTAP `64_audit_doors` 가 옛 정의에서 1 · 2 의 여덟 단언으로 붉었다(아래 「시험」).

## 정한 것

1. **사용자 권한으로 시도를 닫는 문을 걷는다**(`drop function public.fail_reading_run`). 닫는 문은 열쇠의 `fail_reading_job`
   (`service_role` 만) 하나다. 열쇠가 없는 배포에서는 시도가 열린 채 남고 10분 만료가 닫는다 — `failAsUser` 도 이제
   기록만 남긴다. 걷은 쪽을 고른 까닭: 사용자가 닫은 실패를 풀이권 소비로 세는 안은 풀이권이 없는 사람이 하루 상한을 태우는
   것은 못 막고(상한은 계정 수에 비례하지 않는다), 앱이 그 문을 쓸 까닭이 없다.
2. **요청 갈래의 사진은 기다리는 · 수락된 요청에만, 두 사람 사이에 차단이 없을 때만 연다.** 끝난 요청(거절 · 만료 · 무효)은
   사진을 안 연다. `my_match_requests` 는 줄을 그대로 세우되 **소개와 사진 표시는 기다리는 요청에만** 싣는다.

**차단만이 아니라 끝난 요청까지 닫는 까닭.** 차단만 닫으면 「그냥 거절된 요청」은 사진이 열리고 「차단이 끊은 요청」은 닫혀,
요청자가 사진이 열리는지로 차단을 알아낸다. PRD 는 「차단은 소식이 아니다 … 차단이 끊은 요청은 요청자에게 거절로 선다」다 —
둘이 같은 답이어야 그 문장이 선다. 끝난 요청의 줄은 화면(`/me/requests` 「끝난 요청」)에서 닉네임과 상태만 그리므로 화면이
바뀌는 자리는 없다.

## 안 고른 것

- **요청 갈래를 지우기.** 기다리는 요청의 카드는 상대의 사진을 세운다(받은 요청 · 보낸 요청). 기다리는 요청은 차단과 함께 설 수
  없다 — `block_user` 가 두 사람을 잠그고 기다리는 요청을 거둔다.
- **끝난 요청 줄에서 닉네임까지 비우기.** 「거절로 선다」에는 누구의 요청이었는지가 있어야 하고, 요청자는 그 이름을 이미 봤다.
- **넓히기 → 좁히기.** 인자 · 반환형이 안 바뀌어 옛 앱이 새 DB 위에서 그대로 돈다. 옛 앱이 `failAsUser` 를 밟는 것은 열쇠가 없을
  때뿐이고, 그때 받는 `PGRST202` 는 고치기 전과 같이 기록에만 남는다.

## 값

- 열쇠 없는 배포(로컬 dev 에서 비밀을 안 넣었을 때)에서 실패한 시도는 알림이 10분 늦게 선다 — 만료가 닫고, 만료는 알리지 않는다.
- 거절 · 만료 · 무효가 된 요청의 상대 사진은 더는 안 열린다. 그 사람이 다시 후보 덱에 서면 덱 갈래로 열린다.
