# 저장소의 사진은 앱이 판정 뒤 중계하고, 올리기는 DB 스위치 하나를 따라 옛 사진이 0 이 된 뒤에 저장소로 열린다

> **운영자 결정 2026-10-23**(조율자 세션에서 전함) — G-120 의 열람 방식과 전환 차례. 결정 점검표의 「누가 무엇을 볼 수 있는가 ·
> 할 수 있는가」(올리는 문) · 「데이터의 삭제」(옛 사진) · 「비용」(S3 GET · 함수 전송) 줄.
>
> 이 결정이 대체하는 것 — ADR 0202 의 「정한 것」 5 의 「올리는 문 넷은 로그인한 사람에게도 닫혀 있다」 · 6 「열람은 아직 404 다」 ·
> 둘째 덧붙임의 「차례는 켜기 → 안내 → 지우기다」, ADR 0200 「판본 대조」의 「판본이 다른데 바이트가 비면 그 장은 열람 방식이
> 정해질 때까지 404 다」.

## 운영자가 정한 것 (원문 요지)

- 열람은 **안 A** — 앱 경로가 판정한 뒤 S3 를 중계한다. ADR 0200 은 그대로다
- 기존 사진은 전부 지우고 다시 받는다. 차례는 **업로드 차단 → 기존 사진 전체 삭제 → 0건 확인 → S3 업로드 개방**
- 차단은 화면뿐 아니라 **서버의 모든 올리는 문**에 선다. 차단 중에는 까닭을 짧게 안내한다
- **DB 반영(`db push`)만으로 차단 · 삭제 · 저장소 개방이 시작되면 안 된다.** 운영 삭제 · 배포 · 켜기는 운영자가 따로 지시한다
- Vercel Pro 는 이 전환의 선행 조건이 아니다 — G-117 의 별도 결정으로 둔다

## 정한 것

1. **열람 — 안 A.** `photo_at` 이 판정(`may_see_photo`)을 지난 줄의 열쇠(`object_key`)를 함께 내고, 라우트(`app/me/photo/photo-response.ts`)가
   그 열쇠로 S3 에서 읽어 바이트 줄과 같은 머리(`private, no-cache` · 판본 `ETag`)로 낸다. 주소의 값으로 열쇠를 짓지 않는다. 작은 자리
   (아바타 · 편집 칸)는 `?s=card` 로 작은 벌을 받는다. 판본이 같으면 저장소에 안 닿고 304 다. 저장소가 꺼졌는데 열쇠 줄이 있으면 500,
   객체가 없으면 404 (`20261228150000`)
2. **올리기의 길은 DB 스위치 하나다** — `public.photo_upload_switch` 의 한 줄, 값 셋(`20261228140000`).
   - `db`(기본값) — 바이트 길의 문 둘(`add_my_photo` · `replace_my_photo`)만 받는다. 지금 운영 그대로다
   - `paused` — 올리는 문 다섯을 모두 거절한다(「사진 보관 방식을 바꾸는 중이라 지금은 사진을 올릴 수 없어요.」). 지우기 · 옮기기 ·
     위치 조정 · 보기 · 표 버리기는 그대로다
   - `s3` — 저장소 길의 문 셋(`begin_my_photo_upload` · `add_my_photo_object` · `replace_my_photo_object`)만 받는다
   - 다른 길의 문은 「사진을 올리지 못했어요. 다시 시도해 주세요.」로 거절한다 — 스위치 전에 그려진 화면이다. 실패를 받은 사진 판은
     목록을 다시 읽어 새 길로 선다
   - 거절은 계정 잠금(정지 · 로그인) 뒤, 하루 한도를 세기 전이다 — 정지 문장이 먼저이고 거절은 한도를 안 깎는다
3. **바꾸는 손은 운영 SQL 한 줄이고 배포 없이 듣는다** — 문마다 매번 표를 읽는다. 앱 역할은 표를 못 읽고 못 쓴다. 화면은
   `photo_upload_mode()` 로 값만 읽어 그 길로 보내거나 멈춘 동안 안내를 세운다. 스위치가 `s3` 인데 그 배포에 저장소 값이 없으면 화면은
   멈춘 것으로 보인다(보내도 실패뿐이다)
4. **`db push` 만으로는 아무것도 안 시작된다** — 스위치가 `db` 로 서므로 올리는 문 넷을 `authenticated` 에 다시 열어도 저장소 길은
   스스로 거절하고, 사진은 지워지지 않는다(지우기는 마이그레이션이 아니라 운영 SQL 이다). 운영 동작은 배포 뒤에도 그대로다 —
   화면의 길이 환경변수가 아니라 스위치를 따르는데 스위치가 `db` 다
5. **전환 차례** — `paused` → 옛 사진(바이트 줄) 전부 지우기 → 0건 재기 → 저장소 환경변수 · 재배포 → `s3`. 명령과 볼 값은
   `docs/ops/runbook/photo-store.md` 「사진 저장소로 바꾼다」. 차단을 먼저 하므로 지우는 동안 새 바이트 줄이 안 생기고, 지운 뒤 다시
   올리는 장은 모두 열쇠 줄이다 — 「먼저 바꿔 올리면 남는다」는 없다

## 막히는 흐름 — 코드로 잰 것 (2026-10-23, `origin/main` `8ad3f9b0`)

사진은 어떤 흐름의 조건도 아니다. 멈춘 동안 · 지운 뒤에 막히는 것은 **사진을 올리고 바꾸는 일**뿐이다.

- **가입** — `complete_signup` 은 사진을 묻지 않고 가입 폼에 사진 칸이 없다(PRD 「이름과 얼굴」 — 「프로필 사진과 소개는 가입 폼에 없다」)
- **프로필 완성** — 프로필 저장은 닉네임 · 소개만 본다(`missingInProfile`). 「프로필을 다 채웠는가」라는 문턱은 없다
- **매칭 노출** — 덱을 채우는 문(`fill_discovery_deck` · `discovery_pair_eligible`)은 사진을 안 본다. 사진은 카드에 「사진이 있나」로
  읽힐 뿐이다(`my_discovery_board` 의 `exists (… profile_photo …)`). 요청 · 수락 · 채팅 · 풀이도 사진을 안 묻는다
- 지운 사람은 사진 없는 사람의 기본 표시(이름 첫 글자)로 선다. 계정 관리의 「사진 추가」는 멈춘 동안에도 서고, 누르면 프로필의 안내로 간다

## 고르지 않은 것

- **환경변수로 차단** — 바꾸려면 재배포가 들고, 서버의 문(RPC)을 PostgREST 로 바로 부르는 길은 못 막는다
- **스위치 둘(차단 · 저장소)** — 「차단인데 저장소 켜짐」 같은 뜻 없는 조합이 생긴다. 값 셋 하나면 셋뿐이다
- **`signup_pause` 처럼 쌓는 표** — 바꾸는 일이 전환 때 두세 번이라 이력보다 한 줄이 읽기 쉽다. 언제 바꿨는지는 `changed_at` 이 든다
- **표 버리기(`drop_my_photo_upload`)도 막기** — 스위치가 바뀌는 사이에 표를 받은 올리기가 거절되면 앱이 이 문으로 표를 버린다.
  막으면 청소기가 한 시간 뒤 옮길 때까지 표가 남을 뿐이지만, 막을 까닭이 없다
