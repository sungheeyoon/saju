# 출생정보는 revision 으로 남고, claim 이 편집권을 옮긴다

`discovery-v0` 가 오행으로 후보 순서를 정하고 오행은 출생정보에서 나온다. 그래서
**출생정보를 고칠 수 있는 사람이 매칭 노출을 고칠 수 있다.** 두 방향을 다 막는다.

## 남이 고치는 것은 막는다

어떤 Person 이 어떤 User 의 **selfPerson 으로 승인(claim)된 순간부터**, 그 Person 의
출생정보를 고칠 수 있는 것은 그 User 뿐이다. 기존 manager/editor 는 자동으로 viewer 로
내려간다 — 병합 시나리오에서 희윤이 엄마 Person 의 manager 로 남으면 **희윤이 엄마의
매칭 노출을 조작할 수 있기** 때문이다.

다른 User 가 여전히 고칠 수 있는 것은 자기 쪽의 것뿐이다: `localLabel`, 관계 유형,
개인 메모. 생년월일시·출생지·달력 방식·계산 옵션은 못 고친다.

**서비스 코드의 관례로 두지 않고 DB 불변식으로 건다**(고유 제약·트리거·RLS). 잊으면
남의 매칭이 조작되는 종류의 규칙이라, 호출부가 기억해야 맞는 것은 틀린 것이다.
수정 경로도 하나로 모은다.

## 내가 고치는 것은 막지 않는다 — 대신 기록한다

「엄마한테 물어봐서 출생시간을 알아냈다」는 정직한 수정이고 권장할 일이다. 다만 시주가
붙으면 **여덟 글자 중 둘**이 바뀌어 오행 분포가 25% 움직이고 `elementSupport.missing`
이 통째로 달라질 수 있다.

그래서 Person 을 제자리에서 덮어쓰지 않고 **revision** 을 쌓는다
(`PersonChartRevision` / `chartFingerprint`). 노출 기록과 매칭 요청은 자기가 어느
revision 을 대상으로 만들어졌는지 값으로 든다 — ADR 0001 이 Reading 에서 푼 것과 같은
답이되, 91KB 가 아니라 지문 하나다.

```
MatchRequest
- requesterChartRevisionId
- receiverChartRevisionId
- discoveryPolicyVersion
- reasonSnapshot
```

## 대기 중 요청은 무효화한다

상대의 동의는 **특정 사주에 대한 동의**였다. 대상이 바뀌면 그건 다른 동의다. 어느
쪽이든 Evidence 를 바꾸는 수정이 일어나면 pending 요청(한쪽이 상세 궁합을 요청했고
상대가 아직 수락·거절하지 않은 상태)을 무효화하고 상대에게 알린다. **수락 시점에도
트랜잭션 안에서 현재 revision 과 요청 당시 revision 을 비교**한다 — 요청과 수락 사이의
창이 그대로 구멍이기 때문이다. 다르면 수락하지 않고 새 요청을 만들게 한다.

이름·사진·소개 변경은 해당하지 않는다. Evidence 를 바꾸는 것(생년월일시·출생지·달력
방식·계산 옵션)만이다.

이미 성립된 Match 와 과거 Reading 은 **삭제하지 않는다.** 과거 Reading 은 당시 Evidence
를 그대로 보존하고, 변경 이후의 분석은 새 Reading 이 된다(ADR 0001).

## Consequences

- 사주를 바꿔가며 후보를 찔러보는 것이 비용을 갖는다 — 떠 있는 요청이 전부 날아간다.
- 「출생시간 유무·변경 이력」이 그 자체로 신호가 된다. `discovery-v0` 의 노출 편향을
  나중에 재려면 이 기록이 있어야 한다.
