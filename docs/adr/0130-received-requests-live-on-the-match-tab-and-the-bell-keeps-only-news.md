# 받은 요청은 인연 탭 맨 위에 살고, 종은 소식만 든다 — 요청 하나는 딱지 하나만 켠다

> **운영자 위임 2026-09-29 밤, 아침 확인 대기** — 흐름 시안 g 의 「인연 탭 — 받은 요청(종에서 옮김) + 오늘의 인연」을 코드로
> 옮겼다(2라운드 E). 화면 흐름 · 메뉴 구조를 바꾸는 결정이라 결정 점검표에 걸리지만, 이번 밤은 운영자가 머지까지 위임했다.
> 주소는 그대로다 — `/me/requests` 도 `/me/matching` 도 산다(ADR 0126 과 같은 원칙).

## 잰 것 (2026-09-29, 코드)

- 종(`/me/requests`, 제목 「소식」)이 **받은 요청 → 보낸 요청 → 새 소식 → 끝난 요청 · 진행 안내 · 차단 수**를 한 화면에 세웠다.
  수락이 풀이를 떠나보내는 `after` 의 상한(`maxDuration = 300`)도 이 화면이 들었다(ADR 0038).
- 인연 탭(`/me/matching`)은 궤도 지도와 덱뿐이었다. 요청을 보내는 자리는 여기인데, 그 요청이 어떻게 됐는지 · 받은 요청에 답하는
  자리는 종 안이었다.
- 종의 딱지는 `unread_notifications()`(안 읽은 소식 전부)였다. 요청이 오면 소식 한 줄(`request_received`)이 생기고 종이 1 을 켰다.
  나 탭의 「아직 확인하지 않은 새 소식」 띠도 같은 수였다.
- 요청의 소식 줄(받음 · 수락 · 거절 · 무효 · 만료)은 링크가 없었다 — 「요청과 Match 를 이 화면이 이미 세우고 있어 갈 곳이 여기」였다.
- 소식은 앱 밖으로 안 나간다 — 푸시 · 메일 링크는 없다(§6.4).

## 정한 것

1. **받은 요청 · 보낸 요청 · 끝난 요청 · 진행 안내 · 차단 수는 인연 탭 맨 위에 선다**(`app/me/matching/requests-lead.tsx`).
   부품은 종의 화면에서 **옮겼다** — 요청 카드의 머리 · 동의 질문(`MatchConsentQuestion`) · 수락/거절 · 차단/신고 · 거두기 ·
   끝난 요청 · 진행 안내는 한 벌이다. 답하는 누름과 서버 액션은 그대로 `app/me/requests/{manage.tsx,actions.ts}` 에 산다.
   - **받은 요청은 있을 때만 크게 선다.** 카드마다 무엇이 열리는지(여덟 글자 공개)가 수락 단추 위에 처음부터 서 있다 —
     「무엇이 열리는지 읽은 뒤에만 수락」(ADR 0038)은 자리를 옮겨도 같다.
   - **보낸 요청 · 끝난 요청 · 차단 수는 한 줄 접이칸이다** — 제목 줄이 「보낸 요청 n개 · 끝난 요청 m개」를 말한다.
   - **요청이 하나도 없으면 아무것도 안 선다.** 이 탭의 본체는 덱이다 — 빈 칸이 덱을 밀어내지 않는다.
   - 덱이 서지 않는 자리(내 사주가 없다 · 쉬는 중)에도 받은 요청은 선다. 계정이 멈추면 요청 대신 계정 안내가 선다(전과 같다).
   - `maxDuration = 300` 은 인연 탭이 든다 — 수락을 부르는 라우트가 여기다.
2. **종(`/me/requests`)은 새 소식만 든다.** 제목 「소식」 그대로, 들어오면 전부 읽음이 된다(전과 같다). 요청의 소식 줄은 이제
   **인연 탭(`/me/matching`)으로 가는 링크**다 — 성립한 요청도 인연 탭으로 간다(결과 화면은 풀이 목록이 들고, 소식 화면에 Match 로 가는
   길을 따로 세우지 않는다는 흐름 검사가 있다). 풀이 실패는 전처럼 다시 누를 자리로 간다.
3. **요청 하나는 딱지 하나만 켠다**(`src/lib/consent/counts.ts`).
   - **인연 탭은 답할 일을 센다** — 받은 요청 중 아직 답하지 않은 것(`answerCount`). 읽어도 안 줄고 답하거나 차단해야 준다.
   - **종은 지나간 일을 센다** — 안 읽은 소식 중 **요청이 왔다는 소식(`request_received`)을 뺀** 것(`bellCount`). 그 도착은
     인연 탭이 이미 센다. 수락 · 거절 · 무효 · 만료 · 풀이 소식은 종이 센다.
   - **나 탭의 소식 띠는 종과 같은 수다**(`unreadCount` 가 머리글의 문 `readUnreadNotifications` 를 지난다).
   - 둘 다 부속 정보다 — 못 읽으면 딱지를 안 세운다(ADR 0078). 머리글은 화면을 옮길 때 다시 세고, 같은 화면에서 답하거나
     차단하면 창에 알린다(`REQUESTS_TO_ANSWER_MOVED`, 채팅 · 소식과 같은 모양).
   - 탭 딱지의 보이지 않는 말은 「n건 답할 요청」이다 — 「안 읽음」은 채팅과 종의 말이다.
4. **무를 화면 표를 새 자리에 맞췄다**(`app/refresh.ts`): 요청을 보냄 → `/me` · `/me/matching`, 답함 · 거둠 · 차단 · 소식 읽음 →
   `/me/matching` · `/me/requests` · `/me`, 신고 → `/me/matching`.

## 치르는 값

- **종의 수를 세는 문이 무거워졌다.** `unread_notifications()`(수 하나)에서 `my_notifications()`(최근 50줄)로 옮겼다 — 갈래를 알아야
  빼기 때문이다. 마이그레이션을 쓰지 않는 라운드라 DB 에 새 문을 안 열었다. 50줄 밖의 안 읽은 소식은 딱지에 안 선다(소식 화면도
  그 50줄만 그린다). 인연 탭의 수도 `my_match_requests()` 목록을 읽어 센다. 수만 내는 문이 필요해지면 넓히기 마이그레이션 하나로 연다.
- **요청이 왔다는 사실만으로는 나 탭의 띠가 안 선다.** 받은 요청은 인연 탭의 딱지가 알린다 — 나 탭에서 인연 탭까지 한 번 누른다.
- **받은 요청이 있으면 폰에서 덱이 아래로 밀린다.** 폰은 한 화면에 카드 한 장이던 모양(2026-09-25)이 요청이 있는 동안만 깨진다 —
  답할 일이 먼저라는 쪽을 골랐다(시안 g). 요청이 없으면 전과 같다.
- 흐름 검사(`scripts/check-match.mjs`)의 누설 검사는 응답 전체가 아니라 **요청 자리의 마크업**(`#requests-lead`)을 잰다 — 같은 응답에
  내 일간과 후보의 점수를 들어야 하는 덱이 함께 서기 때문이다. 요청 자리의 클라이언트 부품은 요청 · 사람 id 만 받는다.

## 2026-09-29 e+ — 받은 요청 → 오늘의 인연 → 최근 인연 궁합 → 지난 요청

> **운영자 답 2026-09-29 e+** — 「인연은 `받은 요청 → 오늘의 인연 → 최근 인연 궁합` 순서로 한다. 궁합과 인연에는 최근 결과 3개만
> 둔다. 각 `모두 보기`는 탭 불이 없는 `/me/readings` 의 해당 필터로 보낸다.」 주소 · DB · 탭 이름은 그대로다.

- **받은 요청과 지난 요청이 갈라 선다**(`requests-lead.tsx` 의 `ReceivedRequests` · `RequestHistory`). 받은 요청은 전처럼 덱 위에
  있을 때만 크게 서고, 보낸 요청 · 끝난 요청 · 진행 안내 · 차단 수의 한 줄 접이칸은 **탭 맨 아래**로 내려갔다 — 기다리거나 지나간
  일이라 덱과 최근 인연 궁합보다 뒤다. 요청 읽기가 실패하면 까닭 한 줄은 맨 위 한 자리에만 선다.
- **최근 인연 궁합**(`recent-matches.ts` · `recent-match-shelf.tsx`)이 덱 아래 선다. 풀이 보관함과 같은 문(`my_readings`)을
  **덱 · 받은 요청과 나란히** 읽어 인연 궁합만 최신 셋을 고른다 — 차례는 문이 준 그대로다. 표지는 책장의 궁합 표지(`PairCover`)이고
  누르면 `/me/match/[id]` 로 간다(인연 탭 불, ADR 0126). 셋 밖에 더 있으면 「모두 보기」가 `/me/readings?kind=match` 로 보낸다.
  한 권도 없으면 구역이 안 선다.
- **부속 정보다**(ADR 0078) — 풀이 목록 문이 던지면 그 구역만 안 서고 덱은 그대로 선다(`SkippableRead`).
- 덱이 서지 않는 자리(내 사주가 없다 · 쉬는 중 · 자격이 없다)도 같은 차례다 — 조용한 궤도 아래 최근 인연 궁합과 지난 요청이 선다.
- 흐름 검사(`scripts/check-match.mjs`)는 요청 자리를 두 요소로 잰다 — 받은 요청 `#requests-lead`, 지난 요청 `#requests-log`.

**치르는 값** — 탭 이동 한 번에 `my_readings` 부름이 하나 는다. 덱을 세우는 차례 호출과 나란히 돌아 기다림은 늘지 않는다.
보관함과 같은 문이라 인연 궁합 셋을 위해 내 글 전부를 받는다 — 수만 내는 문은 필요해지면 연다.
