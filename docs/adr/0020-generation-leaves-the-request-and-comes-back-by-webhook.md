# 만드는 일이 요청을 떠난다 — 결과는 webhook 으로 돌아온다

자기 풀이 호출 넷을 재 보니 **둘이 240초를 넘겼다.**

```
72s   OK
120s  OK
>240s 타임아웃
>240s 타임아웃
```

문턱을 올릴 여지가 거의 없다.

```
Vercel maxDuration        300초   ← 플랫폼 하드 상한
클라이언트 timeout         240초   ← 여기서 끊는다
DB reading_run_timeout    600초
```

240초는 일부러 그 아래로 잡은 값이다(`GENERATION.settings.timeout`). 플랫폼이 끊으면
실패를 적을 코드가 아예 안 돌고 시도가 `running` 인 채로 남기 때문이다. 그러니 올릴 수
있는 것은 60초뿐이고, 그마저 파이프라인의 나머지가 써야 한다. **300초로 올려도 넘는
판이 남는다.**

## 문제는 시간이 아니라 **어디에 매여 있는가**다

ADR 0016 이 만드는 일을 누름에서 떼어 `after` 로 보냈다. 그것으로 「새로고침하면 만들던
것이 끊긴다」는 고쳤지만, `after` 는 여전히 **라우트의 `maxDuration` 안에서** 돈다.
화면만 비동기이고 서버는 완성본을 기다린다.

그래서 다음 셋은 답이 아니다.

- **재시도** 평가는 끝낼 수 있어도 장애를 가린다. 사용자에게는 여전히 실패다.
- **타임아웃 연장** 60초를 더 얻는데 관측된 초과는 그보다 크다.
- **스트리밍** 첫 토큰은 빨리 와도 **검사와 저장까지 서버가 살아 있어야** 한다.
  300초 벽은 그대로다.

셋 다 요청 수명 안에서 해결하려 한다. 그 수명 밖으로 내보내야 한다.

## 제출하고 떠난다

```
사용자 요청
  → reading_run 생성 · reading_job 에 입력을 얼린다
  → OpenAI 에 background 작업 제출 (metadata.reading_run_id)
  → response_id 저장
  → 함수 즉시 종료

webhook 도착
  → raw body 서명 검증
  → event_id·response_id·type 을 멱등 기록
  → 즉시 2xx                      ← 여기까지가 webhook 이 하는 일 전부

그 뒤 (짧은 후속 작업 또는 복구기)
  → response 회수 → metadata.reading_run_id 확인
  → 검사 → 저장 → run 닫기

화면
  → 지금처럼 run 상태를 물어 본다
```

### webhook 은 작업자가 아니라 **도착 신호**다

두 가지가 이 순서를 강제한다.

**payload 에 `metadata` 가 없다.** 오는 것은 `response_id` 다. 우리가 붙인 이름표는
response 를 **회수한 뒤에야** 읽을 수 있다.

**몇 초 안에 2xx 가 없으면 재전송된다.** 회수·검사·저장을 응답 전에 하면 그 시간이
길어질수록 재전송이 늘고, 늘어난 재전송이 다시 같은 일을 시킨다. webhook 자체가
불안정해지는 고리다.

그래서 **받았다는 사실만 먼저 적고 끝낸다.** 그 뒤 일은 `after` 로 해도 된다 — 이제
모델을 기다리는 일이 아니라 이미 끝난 것을 가져오는 일이라 짧다. 거기서 실패해도 받은
사건이 DB 에 남아 있으므로 복구기가 다시 집는다.

**전면 재작성이 아니다.** `reading_run` 상태 기계도, 10분 만료도, 화면 polling 도 이미
있다(ADR 0016). 바뀌는 것은 「누가 완성본을 기다리는가」뿐이다.

## 왜 Vercel Workflow 가 아닌가

WDK 와 Queues 가 정확히 이 문제를 위해 있고 이 저장소는 Vercel 위에 있다. 그래도 안
쓰는 이유는 하나다 — **위에 적은 자산이 이미 우리 DB 에 있다.** background+webhook 은
그것을 그대로 쓰고, WDK 는 새 런타임 모델을 들이면서 절반쯤 대체한다.

바꿔 말하면 이것은 「WDK 가 나쁘다」가 아니라 「지금 우리에게 덜 필요하다」다. 상태를
우리 DB 밖에 두고 싶어지는 날이 오면 그때 다시 본다.

## 끝나는 길은 넷이고, 그 넷을 다 닫아야 한다

`completed` 만 처리하면 나머지 셋에서 시도가 열린 채 남는다 — `failed` · `cancelled` ·
`incomplete`. 그리고 회수해서 **검사에 떨어진 경우**도 닫아야 한다.

**그런데 지금 그 문이 없다.** `fail_reading_run` 은 `r.user_id = (select auth.uid())`
를 걸고 `authenticated` 에게만 열려 있다. webhook 에는 사용자 JWT 가 없으므로 **부를 수
없다.** 성공 쪽은 `save_reading` 이 이미 열쇠에 열려 있어 되는데, 실패 쪽만 막혀 있다.

성공 쪽은 새로 만들지 않는다. `save_reading` 이 **이미** 저장하면서
`status = 'succeeded'` 로 닫는다. 거기에 `reading_job` 삭제만 더한다.

```
성공   save_reading 을 넓힌다
       → Reading 저장 + run 성공 + reading_job 삭제

실패   fail_reading_job 을 새로 둔다 (열쇠 전용)
       → run 실패 + 알림 + reading_job 삭제
```

**둘 다 각자 한 트랜잭션이다.** 저장은 됐는데 job 이 남거나, run 은 닫혔는데 알림이 안
가는 중간 상태를 만들지 않는다.

이것은 계약을 바꾼다. 이 저장소는 「열쇠에 직접 연 것은 `match_calculation_inputs` 와
`save_reading` **둘뿐**」이라고 마이그레이션에 적어 두었고 시험이 그것을 잰다. 이제
**정확히 셋**이다.

```
match_calculation_inputs
save_reading
fail_reading_job
```

그 문장과 시험을 함께 고친다 — **고치지 않고 여는 것이 더 나쁘다.** 열린 문의 수를
아무도 안 세게 되기 때문이다.

## 얼린 입력은 따로 산다 — 그리고 끝나면 지운다

`reading_run` 은 일부러 본문도 판본 FK 도 안 든다. 그런데 완료 시점에 필요한 것은 그보다
많다 — `checkReading` 은 출생 원문(`BirthSecret[]`)이 있어야 유출을 잴 수 있고, 저장에는
판본 둘·`viewedAt`·prompt·evidence·generation 이 있어야 한다.

그래서 임시 `reading_job` 을 둔다.

| 든 것 | 왜 |
| --- | --- |
| `run_id` (1:1) | 어느 시도의 것인가 |
| `revision_a` · `revision_b` FK | **작업 중에는 원래 판본을 붙들어** 같은 입력으로 검사·재현한다 |
| 정확한 prompt · evidence | 사이에 배포가 나도 같은 입력을 쓴다 |
| `viewed_at` · prompt version · 요청 모델과 설정 | 되짚을 값 |
| provider response id · 처리 상태 | 회수와 멱등 |

**붙든다고 저장까지 되는 것은 아니다.** 그 사이 현재 판본이 바뀌면 기존 `save_reading`
이 저장을 거절한다(「만드는 동안 출생정보가 바뀌었습니다」). 붙드는 것은 **만든 것과 검사한
것을 같은 입력으로 맞추기 위한 것**이지, 낡은 입력으로 쓴 글을 밀어 넣기 위한 것이 아니다.

**사용자에게 열지 않는다.** 열쇠 전용 RPC 만 닿는다.

그리고 **성공이든 실패든 확정되면 지운다.** 안 지우면 실패한 시도 때문에 출생 판본이
영영 붙들린다 — ADR 0011 이 「terminal 요청은 판본을 놓고 지문만 남긴다」고 정한 그 자리다.
얼리는 것은 **일이 도는 동안만**이다.

## 모델 경계는 없애지 않고 역할을 바꾼다

`model.ts` 는 「모델을 부르는 유일한 자리」로 서 있다. 제출과 회수가 갈린다고 그 자리를
없애면 provider SDK 가 파이프라인 전체로 번진다.

그래서 같은 경계 안에 둘을 둔다 — `submitBackgroundReading()` 과
`retrieveBackgroundReading()`. **스키마는 한 벌이다.** 지금 `Output.object` 가 쓰는
JSON Schema 를 Responses API 의 strict structured output 에 그대로 물린다. 복사하면
두 벌이 되고, 어긋난 쪽을 알 수 없게 된다.

한 가지 값을 미리 적는다 — **`@ai-sdk/openai` 는 Responses API 의 `background` 를
내주지 않는다.** 그 이름으로 있는 것은 이미지 생성의 배경 투명도다.

그래서 **공식 `openai` SDK 를 의존으로 들인다.** 직접 HTTP 로 두드리는 것보다 낫다 —
raw body 서명 검증과 Responses 타입을 같이 얻고, 그 둘은 우리가 다시 쓰면 틀리기 쉬운
자리다. 구조화 출력의 강제와 파싱을 우리가 다시 써야 한다는 것이 이 결정의 실제 비용이고,
스키마는 지금 쓰는 JSON Schema **한 벌**을 그대로 문다.

회수한 결과의 **실제 `model` 과 `usage` 도 버리지 않는다.** 요청한 이름과 응답한 이름이
다를 수 있고, 비용을 세려면 결과와 함께 와야 한다.

## 두 시계를 같은 것으로 보지 않는다

`reading_run_timeout` 은 **10분**이고 provider 의 임시 보관도 **약 10분**이다. 거의 같아서
안전 여유가 없다 — 만료 직전에 회수를 시도하면 둘 다 사라진 뒤일 수 있다.

그래서 둘을 다른 정책으로 적는다.

| | 무엇 | 누가 정하나 |
| --- | --- | --- |
| 사용자 작업 만료 | 이 시도를 포기하고 대상을 푸는 시각 | 우리 |
| 결과 회수 가능 시간 | provider 가 결과를 들고 있는 동안 | provider |

**webhook 이 기본이고 복구 조회는 그 뒤를 받친다.** 「충분히 짧게」로 두면 아무도 안
정한 것이 되므로 값으로 박는다.

| | 값 | 누가 |
| --- | --- | --- |
| 복구 조회 | **1분** | **Supabase `pg_cron`** — 아래 |
| 우리 deadline | 제출 후 **8분** | 그 뒤에는 실패로 닫는다 |
| 사용자 작업 만료 | **10분** (`reading_run_timeout`) | deadline 뒤에도 안 닫힌 것을 DB 가 줍는다 |
| 화면 폴링 | 3초 | 표시용. 상태만 읽는다 |
| 최후 청소 | 하루 한 번 | Vercel cron |

```
Supabase 복구 1분  <  우리 deadline 8분  <  DB 실행 만료 10분
```

### 깨우는 것은 Vercel 이 아니다

처음에는 이 1분을 Vercel cron 에 걸었다. **Hobby 요금제의 cron 은 하루 한 번이고, 분
단위는 배포가 거절된다.** 요금제를 안 보고 적은 값이었다.

화면이 이미 3초마다 물어보고 있으니 거기 얹는 길도 있었다. 안 그러기로 한 이유가 셋이다.

- **탭을 닫으면 복구도 닫힌다.** 사람이 없을 때가 복구가 필요한 때다.
- **폴링은 읽기 전용으로 잠겨 있다**(`actions.ts` — 「모델을 부르지 않고 결과도 바꾸지
  않는다」). 그 잠금을 푸는 것이 이 일보다 크다.
- **3초마다 provider 를 조회하게 된다.** 막으려면 throttling 이 또 필요하다.

그래서 **깨우는 쪽만 바꾼다.** 복구 API 도 집는 문도 시계도 그대로다 —
`pg_cron` 이 1분마다 `wake_reading_recovery()` 를 돌리고, 그 함수가 `pg_net` 으로
`/api/cron/reading` 을 두드린다.

주소와 열쇠는 **Vault** 에서 읽는다. 마이그레이션에 적으면 그 값이 git 에 남고, 저장소를
읽을 수 있는 사람이 곧 복구기를 부를 수 있는 사람이 된다. 아직 안 넣었으면 **조용히
지나간다** — 1분마다 예외를 쌓으면 그 소음이 진짜 실패를 덮는다.

`pg_net` 의 기본 HTTP 문턱은 **2초**다. 복구기는 일감 여럿을 차례로 집으므로 그보다
오래 걸린다 — 45초로 명시한다. 2초에 끊기면 매 분 같은 일을 시작만 하고 버린다.
`pg_net` 이 beta 라는 것도 값으로 적어 둔다.

### 비밀값 둘은 다른 값이다

| | 무엇을 막나 | 어디에 |
| --- | --- | --- |
| `OPENAI_WEBHOOK_SECRET` | 들어온 것이 정말 provider 가 보낸 것인가 | Vercel 환경변수 |
| `CRON_SECRET` | 복구 API 를 아무나 못 두드리게 | Vercel 환경변수 **와** Supabase Vault |

**하나로 쓰지 않는다.** 하는 일이 다르고, 하나가 새는 순간 둘 다 샌다.

**provider 회수 가능 시간은 이 부등식에 넣지 않는다.** 문서가 「약 10분」이라고만 하므로
`10분 < provider` 는 보장되는 값이 아니다 — 우리 쪽 숫자와 나란히 세우면 보장 안 되는 것을
보장인 척 쓰게 된다. **우리는 8분 이후의 회수 가능성에 기대지 않는다.** 8분에 못 가져오면
그 시도는 실패다.

## 제출과 기록 사이의 틈

제출은 됐는데 `response_id` 저장이 실패하면 그 작업은 주인을 잃는다. 돈은 나가고 결과는
아무 데도 안 붙는다.

그래서 요청의 `metadata` 에 `reading_run_id` 를 싣는다. 저장이 실패해도 webhook 이 그
값으로 실행 건을 다시 찾는다. **이름표를 결과에 붙여 보내는 것이 우리 쪽 기록보다
먼저다.**

## webhook 은 여러 번 와도 한 번만 저장한다

재전송은 정상 동작이다. 같은 사건이 두 번 오면 두 번째는 아무것도 하지 않아야 한다 —
판정은 DB 가 한다. 서명 검증도 여기 붙는다. 이 경로는 인증된 사용자가 아니라 provider 가
두드리는 문이라, 우리 다른 문과 규칙이 다르다.

**그 기억을 `reading_job` 에 두면 안 된다.** job 은 terminal 에 지워지는데, 재전송은 그
뒤에 온다 — 지우고 나면 「이미 처리했다」를 기억할 곳이 없어져 같은 사건을 처음 본 것처럼
다시 집는다. 얼린 입력의 수명과 영수증의 수명은 다른 시계다.

그래서 작은 표를 따로 둔다.

```
reading_webhook_event
  event_id     PK
  response_id
  event_type
  received_at
  processed_at
```

**본문도 prompt 도 evidence 도 넣지 않는다.** 여기 있어야 하는 것은 「이 사건을 받았고
처리했다」뿐이다.

수명은 job 보다 훨씬 길다. provider 가 최대 **72시간** 재전송할 수 있으므로 영수증은 적어도
그보다 오래 남아야 뜻이 있다.

## 보관되는 것은 **둘**이다 — 「10분」으로 설명하면 안 된다

background mode 는 `store: false` 여도 비동기 처리를 위해 응답을 약 10분 보관한다. 그것만
적으면 절반이다. **prompt caching 이 따로 돈다.**

우리 실측이다.

```
15:07  A  cacheWrite 19,114
15:13  B  (타임아웃)
15:29  B  cacheRead  20,353   ← 16분 뒤에도 재사용됐다
```

문서상 이 계열의 캐시는 마지막 write/read 뒤 **최소 30분** 재사용 가능하고 더 오래 남을
수도 있다. 남는 것은 GPU 로컬의 암호화된 KV 상태이지 우리가 보낸 문서 자체는 아니지만,
**개인정보 설명에서 응답 보관과 캐시 보관은 다른 항목이다.**

둘 다 받아들인다. 근거는 하나이고 이미 값으로 있다 — **ADR 0008 이 「출생 원문은 모델에
도달하지 않는다」를 코드와 시험으로 잠그고 있고**, `redactEvidence` 의 `REDACTED_PATHS`
가 무엇을 왜 뺐는지 계약에 실어 보낸다(생년월일시 원문·보정 내역·경도·절입까지의 거리).
즉 「비식별화된 요청」이 주장이 아니라 **검사되는 사실**이고, 그 사실은 10분짜리 보관에도
30분짜리 캐시에도 똑같이 적용된다.

받아들이지 않는 길도 적어 둔다 — implicit caching 을 끄면 캐시 보관이 사라지는 대신 비용과
지연이 오른다(우리 실측으로 캐시가 먹은 호출이 $0.0083, 안 먹은 것이 $0.0133 이었다).
그리고 응답 10분 보관까지 허용할 수 없다면 남는 길은 Vercel 밖의 장시간 worker 이고,
그것은 이 결정보다 훨씬 크다.

**개인정보 설명에는 둘을 따로 적는다.**

## 무엇이 바뀌지 않는가

검사와 저장은 그대로다. 회수한 결과도 `checkReading` 을 지나고 같은 원자적 절차로
저장된다. **모델을 어떻게 부르느냐가 무엇을 저장해도 되느냐를 바꾸지 않는다.**

## 그래서 순서

1. 이 문서
2. `reading_job` (얼린 입력, terminal 에 삭제) 과 `reading_webhook_event` (영수증, 72시간 이상)
3. 종료 RPC — `save_reading` 을 넓히고 `fail_reading_job` 을 연다. 「둘뿐」 계약과 시험을 셋으로
4. 제출 — `openai` SDK, `background: true`, `metadata.reading_run_id`
5. webhook — raw body 검증 · 사건 멱등 기록 · **즉시 2xx**
6. 회수 — 짧은 후속 작업이 response 를 가져와 `checkReading` 과 원자 저장 재사용
7. 복구 — `pg_cron` 1분, 8분 deadline, terminal 넷을 다 닫는다
8. 그 뒤에야 15회 A/B. 결과가 좋은지 따지기 전에 **결과 자체가 도착해야 한다**
