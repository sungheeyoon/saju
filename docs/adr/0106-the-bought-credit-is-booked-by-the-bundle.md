# 산 풀이권은 결제 주문에 매인 묶음이 들고, 어느 쓰임이 어느 몫을 썼는지가 묶음마다 남는다

G-21 은 ⑤ 「산 몫은 `reading_credit_grant` 와 다른 표가 들고 결제 주문과 이어진다」와 ④ 「결제와 쓰임은 묶음별로
따라갈 수 있어야 한다」를 정했고, G-25 ⑥ 은 「묶음별 결제 · 사용 이력은 어느 산식이든 필요하므로 먼저 만든다」고
적었다. 환불 산식은 변호사 검토 뒤다. 이 ADR 은 그 **장부**를 PG 와 무관하게 먼저 세운 기록이다
(`20261011090000_the_bought_credit_is_booked_by_the_bundle.sql`). 2026-09-24, 운영자가 자리를 비운 사이 에이전트가
정했고 결정은 아래에 모았다.

## 잰 것 — 만들기 전에

- **셈은 세 자리를 센다**(`reading_credits_used`): 성공한 시도 · 유효시간(10분) 안의 도는 시도 · 기한 안의 대기
  요청. 셈이 **행을 안 고치고** 자리를 풀어 주는 곳이 셋 있다 — 유효시간을 넘긴 시도(`running` 그대로), 기한이 지난
  요청(크론이 밀기 전), 수락은 됐는데 자동 시도가 못 선 요청.
- **셈은 지운 것을 되돌려 준다.** `reading_run` 은 사람 · 궁합 쌍을 `on delete cascade` 로 따른다 — 저장한 사람을
  지우면(`app/me/actions.ts` 의 `user_person_access` 삭제 → 고아 사람 정리) 그 사람의 성공한 시도가 사라지고
  잔액이 하나 는다. 상대가 떠난 궁합의 시도도 같다(`match_without_its_pair_is_cleared`).
- **두 문의 자물쇠가 달랐다.** `start_reading_run_for` 는 셈 전에 `reading:user:<id>` advisory 를 잡는데
  `request_match` 는 계정 행 둘(`lock_users`)만 잠갔다 — 풀이 시작과 인연 요청이 나란히 마지막 한 번을 읽으면 둘 다
  지나갔다. ADR 0021 의 「사람 자물쇠 안에서 센다」가 인연 요청(ADR 0038)이 들어온 뒤로 한쪽 문에만 참이었다.
- 1회권과 견준 할인율은 12.2 · 18.8 · 39.8% 다 — 그때 가격 표의 「19%」 · 「40%」는 반올림이라 실제보다 컸다.
  **운영자가 표시를 정수 내림(12 · 18 · 39%)으로 정했다(2026-09-24)** — 가격은 그대로다(아래 「운영자 승인」).

## 정한 것

**1. 잔액은 여전히 센다. 장부는 환불 셈의 입력이다.** 한도 한 줄만 바뀐다 —
`무료 + 예외 + Σ(묶음의 산 수 − 환불로 걷은 수)`. 쓰임 장부가 잔액을 정하면 ADR 0021 이 없앤 「빼기와 돌려주기」가
돌아온다. 산 몫이 0 인 지금 모든 계정의 한도 · 잔액 · 거절은 그대로다.

**2. 표 다섯.** 모두 RLS 를 켜고 정책이 없으며 어느 API 역할에도 권한이 없다.

| 표 | 무엇을 드나 |
| --- | --- |
| `reading_order` | 결제 주문 — 산 회차 수 · 금액 · 통화(KRW) · 제공자 · 제공자 주문 번호 · 거래 번호 · 멱등 열쇠 · 상태 · 환불한 금액 · 시각 |
| `reading_bundle` | 산 묶음 — 주문 1:1, 승인 때 선다. 산 수 · 가격 스냅샷 · 산 때 · 걷은 수 |
| `reading_order_refund` | 환불 한 번 — 금액 · 걷은 회차 · 사유 분류 · 제공자 환불 번호 |
| `payment_event` | 제공자의 알림 — `(provider, provider_event_id)` 가 하나라 같은 알림은 한 번만 |
| `reading_credit_use` | 쓰임 — 어느 시도 · 요청이 어느 몫(무료 · 예외 · 묶음 id · 몫 밖)을 썼나, 예약 · 확정 · 풀림과 그 시각 |

**3. 상태 기계는 표가 지킨다.** 주문은 대기 → 승인 | 취소, 승인 → 부분 환불 | 전액 환불, 부분 환불 → 전액 환불뿐이고,
무엇을 샀는지 · 얼마였는지 · 거래 번호는 한 번 서면 안 바뀐다(`reading_order_moves`, `55000`). 묶음은 걷은 수만
는다. 쓰임은 예약에서만 움직인다.

**4. 쓴 순서는 자리를 잡는 순간 정한다.** 시도나 요청의 행이 생기면 트리거가 몫 하나를 붙인다 — 무료에 빈자리가
있으면 무료, 없으면 예외, 없으면 산 때가 이른 묶음. 인연 요청이 수락되면 그 자리에서 선 시도(`match-accept:<요청
id>`)가 **요청의 쓰임을 그대로 이어 받는다** — 새 몫을 고르지 않는다. 셈이 행을 안 고치고 풀어 준 셋은 다음에 그
사람의 몫을 고를 때와 운영자가 환불 셈을 읽을 때 먼저 정리한다(`settle_reading_credit_uses` — 셈과 같은 물음이다).

**5. 확정된 쓰임은 대상이 지워져도 확정이다 — 몫 밖(`outside`).** 셈이 지운 시도의 자리를 되돌려 주는 지금 동작은
바꾸지 않는다. 대신 장부는 그 쓰임을 지우지 않으므로, 되돌아온 자리로 만든 풀이는 어느 몫에도 안 든 것으로
적힌다. 장부의 자리로 셈하면 산 몫을 쓰고 대상을 지워 그것을 환불로 바꾸는 길이 생기기 때문이다. 몫 밖은 환불 대상이
아니다. 한도가 8 → 5 로 내려가 이미 넘게 쓴 계정의 옛 쓰임도 채워 넣을 때 같은 자리에 선다.

**6. 인연 요청도 셈 전에 사람 자물쇠를 잡는다.** `request_match` 의 본문을 로컬의 살아 있는 정의에서 받아 적고 한 줄만
더했다(ADR 0043 의 규율). 쓰임 트리거도 같은 자물쇠 안에서 몫을 고른다.

**7. 주문을 여는 문은 로그인한 사람, 승인 · 취소 · 환불은 서버만.** `open_reading_order` 는 판매가 열렸을 때만 돌고
(`reading_sale_is_open()` = **false**), 금액은 가격표(`reading_bundle_price`)에서 온다 — 부르는 쪽이 금액을 대지
않는다. 대기 주문은 아무것도 얹지 않는다. `approve_reading_order` · `cancel_reading_order` · `refund_reading_order` 는
`service_role` 에만 열었다. 승인은 낸 금액이 주문과 다르면 거절하고(→ 「정정」: 던지지 않고 돌려준다), 같은 알림 · 같은 거래 번호로 두 번 와도 묶음은
하나다. 환불은 **안 쓴 회차만** 걷는다 — 예약 중인 것은 풀릴 때까지 안 쓴 것이 아니다. 환불 **금액**은 사람이 정해
넣는다(산식 없음, G-25 ⑥).

**8. 개발 · 시험용 승인 헬퍼는 마이그레이션에 두지 않는다.** pgTAP 이 이 트랜잭션 안에서만 판매 스위치를 바꾸고
`service_role` 로 승인 문을 부른다. 운영에 있는 헬퍼는 없다 — 운영에서 몫을 만드는 길은 승인 문 하나다.

**9. 운영자는 환불 셈의 입력을 한 번에 읽는다 — 읽을 때마다 적힌다.** `operator_reading_refund_basis(주문 id)` 가
그 주문의 계정이 가진 주문 전부를 묶음별로 낸다: 산 수 · 걷은 수 · 쓴 수 · 예약 중 수 · 안 쓴 수 · 결제 금액 · 환불한
금액 · 주문 시각 · 결제 시각 · 첫/마지막 쓴 때 · 거래 번호. ADR 0105 의 운영자 문 규칙 그대로 — 운영자만, 같은
트랜잭션에서 접속기록 한 줄(`credits.refund_basis`, 거른 조건 칸에 주문 id 만), 거절은 `note_operator_denial` 이 적는다.
**화면은 아직 없다** — 판매가 닫혀 있어 주문이 0건이다. 판매를 여는 PR 이 `/ops/**` 에 세운다.

**10. 떠나면 결제 기록은 따로 5년, 앱은 못 읽는다(G-25 ②).** ADR 0098 과 같은 자리 — `auth.users` 의 `before delete`
트리거가 **승인된 적 있는** 주문을 `retention.reading_payment` 로 옮기고(묶음 · 쓰임 · 환불 · 알림은 jsonb), 일반 표의
행은 cascade 로 지워진다. 결제 전에 닫힌 주문은 거래가 아니라 안 옮긴다. 보존은 마지막 결제 사건(승인 · 환불)부터
5년이고 크론 `payment-retention-purge`(매일 04:53 UTC)가 지난 줄을 지운다. 분쟁 · 수사기관의 요청이 걸린 줄은
`hold_reason` 으로 미룬다. `retention` 스키마는 API 역할 셋 모두에 닫혀 있다.

**11. 로그인 이메일은 결제 기록에 옮기지 않는다.** 처리방침 v7 후보가 「구현 때 정한다」로 남긴 자리다. 거래는 PG 의
거래 번호로 되짚고, 거래 주체의 식별 정보는 PG 가 든다 — 우리가 새로 모을 까닭이 없다. 변호사 검토가 「거래 주체를
식별하는 정보를 우리가 들어야 한다」고 답하면 다시 연다(G-25).

## 정정 (2026-09-24) — 거절은 돌려주고, 같은 열쇠는 나란히 와도 하나다

외부 리뷰가 찾았다. 고친 것은 `20261013090000`.

- **금액이 다른 승인은 던지지 않고 `refused` 를 돌려준다.** 던지면 방금 넣은 `payment_event(outcome = 'refused')` 도 되감겨 거절한
  알림이 남지 않았다. 이제 문은 한 줄 `(outcome, bundle_id)` 을 내고, 같은 알림이 다시 오면 처음의 결과를 그대로 낸다. 떠날 때
  `retention.reading_payment` 는 승인된 적 있는 주문의 알림을 거절까지 결과째 옮긴다 — **승인된 적 없는 주문의 거절 알림은 안
  옮긴다**(그 주문은 거래가 아니라는 이 ADR 의 선). 그 선이 맞는지는 PG 웹훅과 함께 본다(G-23 ⑥).
- **`open_reading_order` 는 `insert … on conflict do nothing` 뒤 다시 읽는다.** SELECT → INSERT 라 같은 열쇠로 나란히 오면 늦은 쪽이
  `unique_violation` 을 받았다. 그리고 **같은 열쇠를 다른 묶음 · 다른 제공자에 쓰면 거절한다**(`22023`) — 옛 주문을 돌려주면 5회를
  누르고 3회 주문을 받는다.

**메모 (2026-09-24, `20261015090000`)** — 같은 알림 번호는 **같은 요청일 때만** 재시도다. 부딪힌 `payment_event` 의 주문 · 종류 · 금액(승인된 알림이면 주문의 거래 번호까지)이 모두 같아야 처음의 결과를 돌려주고, 하나라도 다르면 `22023` 으로 던진다 — 전에는 다른 주문이 `applied` 를 받았다. 위 정정이 「거절은 돌려준다」로 바꾼 것은 새 알림의 거절 줄을 남기기 위해서였고, 여기서는 처음의 줄이 이미 있어 던져도 잃는 기록이 없다. 같은 환불 번호도 금액 · 회차 · 사유가 같을 때만 한 번으로 친다.

## 버린 것

- **쓰임을 그때그때 셈으로 되짚는다(뷰)** — 쓰는 길이 없어 늘 셈과 맞지만, 무료 몫이 1 로 내려가거나 예외가
  늦게 얹히면 **지난 쓰임의 몫이 바뀐다.** 5년 두는 결제 기록이 오늘의 설정에 따라 다시 쓰이면 안 된다.
- **장부가 문을 지킨다(트리거가 넘치면 거절)** — 셈이 지운 자리를 되돌려 주는 한 장부와 셈이 갈리고, 그러면
  「잔액은 남았는데 누르면 거절」이 난다(ADR 0043 이 막은 자리). 시험 도구가 시도 행을 직접 넣는 자리도 깨진다.
- **삭제된 시도의 쓰임을 풀어 셈과 맞춘다** — 산 몫을 쓰고 대상을 지우면 환불할 회차가 생긴다.
- **개발용 승인 헬퍼를 마이그레이션에 둔다** — 운영에 있는 한 「못 부른다」는 권한 설정 하나에 걸린다.

## 잠그지 않은 것

- **풀림과 새 쓰임이 한 사람에게 동시에 오면** 새 쓰임이 방금 풀린 무료 자리를 못 보고 다음 몫(묶음)을 고를 수 있다.
  풀림(거절 · 거둠 · 만료)은 자물쇠를 안 잡는다 — 잡으면 만료 크론이 여러 사람의 자물쇠를 차례로 쥐며 교착의 자리가
  생긴다. 셈과 잔액에는 영향이 없고 환불 셈에서 그 사람에게 불리한 쪽으로 한 칸 어긋날 수 있다.
- **두 세션의 진짜 경합은 pgTAP 이 못 만든다.** 대신 두 문이 **셈하는 순간 같은 자물쇠를 쥐고 있는가**를 잰다 —
  `request_match` 에서 그 한 줄을 빼면 붉어진다(`48_reading_bundle_ledger`).
- **탈퇴 때 남은 유료 풀이권**(G-25 ⑦)은 아직 소멸도 환불도 아니다 — 기록만 옮기고 몫은 계정과 함께 사라진다.
  탈퇴 판에 남은 수량과 환불 신청 길을 보이는 일은 판매를 여는 PR 의 몫이다.
- **서비스 열쇠가 새면** 승인 문으로 몫을 만들 수 있다. DB 는 PG 의 서명을 못 본다 — 서명 검증과 금액 대조는 웹훅
  라우트가 든다(G-23 ⑥). 그 열쇠는 이미 모든 것의 열쇠라 이 표만의 문제가 아니다(ADR 0100 이 예외 표를 서비스 열쇠에
  안 연 까닭과 다르다 — 결제 확인은 서버가 적어야 한다).
- **가격표가 두 자리다** — 주문 금액은 DB(`reading_bundle_price`)가, 화면의 할인율은 `src/lib/reading/bundle.ts` 가 든다.
  각자의 시험이 같은 넷을 든다. 갈리면 DB 가 맞다. 할인율 표시는 정수 내림 하나다(`discountAgainstSingles`) — 상품 화면 ·
  결제 전 고지가 서는 PR 이 이 값을 쓰는지는 그 PR 의 체크리스트가 든다(G-21 「판매를 열 때 남은 것」).

## 운영자 승인 (2026-09-24)

운영자가 에이전트가 정한 것 중 둘과 표시 하나를 승인했다. 구현은 바뀌지 않는다.

- **쓴 순서는 무료 → 예외 → 오래된 유료 묶음이다**(결정 4) — 잔액 셈에는 안 들고 환불 셈에만 든다.
- **떠난 뒤 남는 결제 기록에 로그인 이메일을 옮기지 않는다**(결정 11). 거래는 PG 거래 번호(`provider_payment_id`)와 내부
  주문 번호(`reading_order.id` · 가맹점 주문 번호 `provider_order_id`)로 되짚는다. 본인확인 분쟁에 필요한 최소 거래
  식별자가 무엇인지는 변호사 검토 목록에 있다(`docs/legal/README.md`).
- **할인율 표시는 1회권 대비 정수 내림이다** — 3회 12% · 5회 18% · 20회 39%. 가격은 바꾸지 않는다.
