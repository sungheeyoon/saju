# Auth 서버에는 관문이 한 번 묻고, 화면은 쿠키의 서명을 스스로 확인한다

> **섰다**(2026-09-27). 운영자 결정 — 「로그인 확인이 두 번 도는 것을 한 번으로 줄여라」. ADR 0116 의 「잠그지 않은 것」 마지막 줄을
> 닫는다. ADR 0041(관문은 길만 가리키고 로그인 판정은 화면이 한다)은 그대로다.

## 잰 것 (2026-09-27, `origin/main` `e370931`)

- `auth.getUser()` 가 스물세 자리에 있었다 — 관문(`proxy.ts`) 하나와 서버 화면 · 레이아웃 스물하나, 서버 액션 하나
  (`app/me/discovery/actions.ts`). 브라우저의 둘(`save-for-reading.tsx` · `browser-session.ts`)은 `getSession` 이라 안 든다.
- `getUser` 는 부를 때마다 Auth 서버의 `/auth/v1/user` 로 가는 왕복이다. 탭 넷의 실제 이동(RSC)마다 **둘**(관문 · 화면),
  미리 받기마다 하나(관문)였다 — 아래 표의 방법으로 센 값이고, 로컬에서도 한 번에 25~40ms 다.
- **서명 키는 둘 다 비대칭이다.** 운영(`xgdeguyxgkillndraonc`)의 서명 키 목록은 ES256 이 `in_use`, 옛 HS256 이 `previously_used`
  (Management API 를 읽기만 했다), 공개 JWKS 에 ES256 하나. 로컬 스택(CLI 2.115)도 JWKS 에 ES256 이 서고 발급된 토큰 머리가
  `alg: ES256` 이다.
- `@supabase/auth-js` 2.112.3(`@supabase/ssr` 0.12.4 · `supabase-js` 2.112.3)의 `getClaims()` 는 토큰 머리가 비대칭이고 `kid` 가
  있으면 JWKS 로 서명을 이 서버에서 확인하고, `HS*` 거나 `kid` 가 없으면 `getUser` 로 물러난다. JWKS 는 모듈 전역에 저장 키별로
  10분 붙든다(`GLOBAL_JWKS`, `JWKS_TTL`) — 따뜻한 함수에서는 네트워크가 없다. 만료도 본다(`validateExp`).
- **DB 는 이미 서명만 본다.** 로컬에서 `logout` 으로 끊은 세션의 토큰으로 `/rest/v1/app_user` 를 부르면 200 이 온다. 같은 토큰에
  `/auth/v1/user` 는 403 `session_not_found`, 계정을 지운 뒤에는 403 `user_not_found` 를 답한다.

## 정한 것

**네트워크 확인은 관문이 든다.** 까닭 셋.

1. 쿠키를 갱신할 수 있는 자리는 관문뿐이다 — 서버 컴포넌트는 쿠키를 못 쓴다(`server-client.ts` 의 `catch`). 토큰이 만료돼
   갱신해야 하는 요청은 어차피 관문에서 Auth 서버로 간다.
2. 관문은 `/me` · `/compat` · `/auth` · `/signup` · `/ops` 의 **모든** 요청에서 화면보다 먼저 돈다(ADR 0041 이 거기로 옮긴 까닭).
3. 관문이 Auth 서버의 거절을 받으면 **그 세션의 쿠키를 걷고**, 걷힌 요청이 화면에 간다(`NextResponse.next({ request })`). 끊긴
   세션은 라이브러리가 이미 걷고(`_removeSession`), 지워진 계정의 403 은 안 걷으므로 관문이 `401` · `403` 에서 걷는다.
   닿지 못한 것(네트워크 · 5xx)은 거절이 아니라 안 걷는다.

**화면은 `signedInUser`(`app/auth/signed-in.ts`)로 쿠키의 서명을 확인한다** — `getClaims()`. 스물두 자리가 이것 하나를 부른다.
화면은 관문이 붙인 머리 · 값을 **하나도 안 받는다.** 받는 것은 브라우저가 보낸 쿠키(관문이 걷었으면 걷힌 쿠키)이고, 서명이
안 맞거나 만료됐으면 아무도 아니다. 그러니 「화면이 스스로 묻는다」는 ADR 0041 의 성질이 남는다 — 관문이 통째로 사라져도 화면이
위조된 토큰을 받아들이는 길은 없다.

관문의 계정 · 일정 읽기와 화면의 계정 읽기를 하나로 합치지 않았다. 둘은 칸이 다르고(관문은 가입 · 안내 판본, 화면은 상태 ·
이름 · 사진), 합치려면 관문이 읽은 값을 머리로 넘겨 화면이 믿어야 한다 — 그것이 이 결정이 피한 길이다.

## 잰 값 — 고친 뒤

ADR 0116 의 방법(PR #284 본문) 그대로다. `next build` + `next start`(로컬 스택), 계정 셋 × 두 바퀴, 중앙값. 늦춘 스택은 Supabase
부름마다 +25ms · 요청마다 +150ms · 브라우저 왕복 20ms. 서버 쪽은 `node --import` 로 `fetch` 를 감싸 요청마다 센다.

| 요청 | `/auth/v1/user` 전 → 뒤 | 차례로 부르는 물결 전 → 뒤 |
| --- | --- | --- |
| 탭의 실제 이동(RSC) · 첫 문서 | 2 → **1** | 홈 7 → 5.5 · 매칭 9 → 8 · 풀이 5 → 4 · 채팅 5 → 4 |
| 미리 받기 | 1 → 1 | 2 → 2 |
| JWKS | — | 서버 프로세스마다 첫 요청에 **1**(그 뒤 10분 0) |

누름 → 본문(늦춘 스택, 데스크톱): 홈 → 매칭 625 → 590ms · 매칭 → 풀이 397 → 346 · 풀이 → 채팅 370 → 322 · 채팅 → 홈 454 → 423.
로컬 그대로는 전후 모두 310~355ms — ADR 0116 의 300ms 묶음이 바닥이라 안 보인다.

## 잠그지 않은 것 · 대가

- **Auth 서버에 닿지 못하면 화면이 서명만으로 연다.** 전에는 화면의 `getUser` 도 실패해 로그인으로 보냈다. 지금은 관문의 확인이
  네트워크로 실패해도 쿠키를 안 걷으므로, 서명과 만료가 맞는 토큰이면 화면이 선다. DB 는 원래 서명만 봤으므로 볼 수 있는 것은
  같다.
- **matcher 밖에서 `signedInUser` 를 부르면 끊긴 세션을 못 알아챈다.** 지금 부르는 스물두 자리는 모두 matcher 안이다. 관문
  밖의 새 화면(`/` 같은)이 로그인을 물어야 하면 `getUser` 를 쓰거나 matcher 를 넓힌다.
- 비대칭 키를 되돌리면(대칭 키로 서명) `getClaims` 가 `getUser` 로 물러나 전의 왕복 둘로 돌아간다 — 틀리지는 않고 느려진다.
- e2e 두 줄이 이 결정을 든다: 「다른 곳에서 끊긴 세션의 쿠키로는 탭을 눌러도 주소로 열어도 로그인으로 간다」, 「지워진 계정의
  쿠키로는 화면이 안 열린다」. 뒤엣것은 관문의 쿠키 걷기를 끄면 붉다(확인했다).
