# `await` 에 붙은 판단은 시험이 못 부른다

## 후보 문장이 또 반쯤 틀렸다

이슈 #88 의 후보 5 는 이렇게 적혀 있었다.

> `panel.tsx` 858줄 중 690줄에 어떤 vitest 도 못 닿는다. include 가 `*.test.ts` 뿐이고
> environment 가 `node` 라 `.test.tsx` 는 안 돈다(저장소에 0개).

**막고 있던 것은 확장자도 environment 도 아니다.** 같은 파일의 `panelChrome` 은 `.tsx` 에
살면서 `.test.ts` 가 그냥 부르고 있었고(스무 항목), 그 사실이 반증이다. 설정을 한 줄도
안 고치고 이번 작업이 끝났다는 것이 두 번째 반증이다.

진짜로 막고 있던 것은 **판단이 `await` 와 한 문장에 붙어 있던 것**이다.

```ts
if (result.ok) {
  announceCreditsMoved();
  dispatch({ type: 'opened', started: result.started });
  return;
}
if (allowMockFallback) { showMock(); return; }
dispatch({ type: 'refused', message: result.message });
```

「무엇이 서는가」를 부르려면 `generateReading` 을 부르는 수밖에 없고, 그것은 서버 액션이다.
지켜보는 고리도 마찬가지로 `setInterval` 안에 판단이 들어 있었다. **브라우저를 세워야만
부를 수 있는 판단**이라 아무도 안 쟀다 — ADR 0072 뒤의 `panelChrome` 과 같은 진단이고,
고치는 법도 같다.

그리고 **690줄이라는 수도 재는 값이 아니었다.** 그 대부분은 JSX 이고, 거기서 렌더 시험이
잠글 수 있는 것은 얇다. 실제로 잴 것이 있던 자리는 **누름 55줄과 고리 36줄 안의 갈래
열**이었다.

## 무엇을 옮겼나

`afterPress` · `afterAsking` · `answerOf` · `previewReading` 을 `reading-state.ts` 로 내렸다.
넷 다 값을 받아 값을 낸다. 칸에 남은 것은 **집행**뿐이다.

```ts
function apply(decision, dispatch, reread) {
  if (decision.event !== null) dispatch(decision.event);
  if (decision.announcesCredits) announceCreditsMoved();
  if (decision.rereads) reread();
}
```

**부수효과를 하지는 않되 언제 할지는 값이 답한다**가 이 파일의 새 계약이다. 외치는
일(`announceCreditsMoved`)과 다시 읽는 일(`router.refresh`)이 갈래마다 손으로 적혀 있던
것을 `FlowDecision` 의 두 칸으로 모았다.

`allowMockFallback: boolean` 은 안 받는다. **예시 글을 세울 수 있는가**와 **세울 글이
있는가**를 따로 들면 한쪽만 지우는 갈래가 생기므로, `preview: CurrentReading | null`
하나로 받는다 — 같은 파일이 `isMock` 을 안 드는 것과 같은 까닭이다.

## 값으로 남은 것 넷

재고 나서야 적을 수 있게 된 것들이다.

1. **개발 기계에서는 거절까지 예시 글이 덮는다.** 「풀이권을 다 쓰셨어요」가 예시 글로
   가려진다. 일부러 그렇게 둔 맞바꿈이지만 **아무 데도 안 적혀 있었다** — 이제 시험이
   그 문장을 들고 있다. 프로덕션에는 `preview` 가 `null` 이라 이 갈래가 없다.
2. **한 번 못 물은 것으로 기다림을 끝내지 않는다.** 만드는 일은 4분까지 가고 그동안
   왕복이 80번이다.
3. **「가리킬 시도가 없다」도 끝이 아니다.** `lastReadingRun` 이 「아직 안 만들었다」와
   「못 보는 대상이다」를 한 값으로 내므로, 그것으로 끝내면 도는 시도를 두고 「없다」고
   말하는 화면이 된다.
4. **끝난 것을 보면 외치고 다시 읽는다 — 둘 다.** 하나만 하면 헤더의 숫자나 글 둘 중
   하나가 낡는다.

**이번에는 버그가 안 나왔다.** 지난 네 라운드가 연달아 하나씩 찾았지만 여기서는 옮긴
갈래 열이 다 이미 맞게 돌고 있었다. 값은 **아무도 안 재던 갈래 열이 이제 재어진다**는
것 하나다.

## 아직 못 닿는 것은 그대로다

`<dialog>` 의 열림·닫힘, `LoadingState` 의 초 세기, 고리의 3초 간격과 정리. 전부 렌더링과
훅이고 jsdom 없이는 안 닿는다 — 그리고 `showModal` 은 jsdom 에 없다. 확인 창은 이 저장소가
**일부러 상태를 안 들고 브라우저에 맡긴 자리**라, 메우고 나면 브라우저가 하던 일을 흉내
낸 것을 재게 된다. 열 값이 생기면 그때 연다.

## 안 한 것

- **`test:flow` 를 CI 에 붙이는 일**과 **「어떤 변경에 어떤 검사를 돌리는가」 매트릭스.**
  둘 다 이번 범위 밖이다. 지금 워크플로가 **바뀐 자리를 안 보고 전부 돌리는데**, 그 위에
  검사를 더 얹으면 한 번 도는 값이 더 커진다. 범위를 먼저 가른 뒤에 붙일 자리다.

- **단위 시험의 기본 상한.** 재기는 했다 — 전수로 훑는 시험 **열여덟**이 기본 5초를 나머지
  1900여 건과 나눠 쓰고 있고, 가장 무거운 둘이 **3.2초·4.4초**로 상한의 3분의 2를 혼자
  쓴다. 붐비는 날 먼저 넘어가는 까닭은 제 잘못이 아니라 **옆자리 부하**이고, 같은 사연이
  이미 `regression.test.ts` 에 적혀 있다(절입일 시험이 그래서 제 시간을 들게 된 자리다).
  **고치는 것은 이 변경과 다른 일이라 안 켰다** — 「재어 보고 안 켠 것을 값으로 남긴다」.
  켤 때 들 값은 `POPULATION_TIMEOUT_MS` 한 자리이고, 열여덟이 제 시간을 들면 기본 상한에
  남는 가장 느린 시험은 **0.8초**다.

- **`e2e/match.spec.ts:392`(키보드만으로 요청·수락·차단) 의 flaky.** 이 변경의 `authed` 에서
  60초 상한을 넘겼다가 **재시도로 통과**했다(110 통과 · 1 flaky · 2 건너뜀). 이 변경이 닿는
  자리가 아니므로 **안 고치고 관찰만 남긴다** — 같은 자리가 또 나오면 그때 잡는다.
