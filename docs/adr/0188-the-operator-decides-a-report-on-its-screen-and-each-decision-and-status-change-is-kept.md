# 운영자는 신고 상세에서 판단 근거와 함께 처분하고, 처분마다 이력이 쌓이며, 계정 상태는 공통 함수 하나로만 바뀐다

> **근거** — 간극 대장 G-111 ②(`docs/product/gaps/records/g-111.md` 「정한 것 (2026-10-16)」 G-111-6 · 7 · 9 · 10, 「② 신고 처분 —
> 신고 상세」 · 「실행 전 확인」 · 「③ 정지 · 해제」의 공통 함수 · 트리거). 운영자가 #730 에서 답했다. 이 ADR 은 ADR 0107 의
> 「검토는 문 하나가 적는다」를 넓힌다 — 그 문이 공통 함수가 되고, 화면의 문과 런북의 검토 문이 같은 함수를 지난다. ADR 0103 의
> 「관리자 화면은 읽기만 하는 열람대」는 신고 상세에서 처분을 적는 만큼 옮겨진다.

## 잰 것 — 만들기 전에

- 런북의 검토 문(`review_report`, 마지막 정의 `20261020090000`)은 신고 행을 id 로만 골라 결과를 조건 없이 덮어썼다 — 앞 결과가
  어디에도 안 남았고, 두 운영자가 나란히 처리하면 늦게 누른 쪽이 말없이 이겼다.
- 정지는 `app_user.status` 를 직접 UPDATE 했다(검토 문 안에서도, 런북의 정지 · 해제에서도). 누가 왜 바꿨는지가 남지 않았다.
- 이용 정지 결정을 다른 결과로 바꿔도 계정 정지는 풀리지 않는다 — 운영자가 이것은 고칠 결함이 아니라고 정했다(기록 「② 신고 처분」).

## 정한 것

1. **신고 상세에서 처분한다.** `/ops/reports/<id>` 의 처분 칸 — 결과 넷(조치 없음 · 추가 확인 필요 · 경고 · 이용 정지 결정), **판단
   근거는 넷 모두 필수**(G-111-7, 500자). 경고 · 정지에는 제재 대상(신고의 두 계정 중 하나, 기본은 신고받은 계정)이 있어야 하고,
   경고의 갈래는 기본이 신고 사유다. 문(`operator_review_report`)은 `authenticated` 에 열고 안에서 `is_operator()` 로 닫는다 —
   **서버 열쇠에는 열지 않는다.** 실행자는 부른 사람(`auth.uid()`)이다. 신고 id 복사 단추와 「검토 문으로 적습니다」 줄은 걷었다.
2. **처분 이력이 쌓인다.** `report_review_entry` — 처분 한 번이 한 줄(신고 · 버전 · 결과 · 판단 근거 · 제재 대상 · 경고 갈래 ·
   실행자 · 요청 번호(유일) · 시각). 줄은 고치지 않는다. 신고 행은 지금 결과를, 이 표는 지금 것까지 모든 결과를 든다. 이미 검토된
   신고는 마이그레이션이 지금 결과를 「기록 이전」 한 줄(버전 1)로 옮겼다 — 두 신고 표 모두.
3. **처리 버전 = 그 신고의 이력 줄 수.** 처음 0, 적을 때마다 +1. 화면은 읽은 버전을 함께 내고, **DB 의 지금 버전과 같을 때만**
   적는다 — 다르면 `55000` 으로 거절하고 화면이 지금 결과를 다시 그린다. 「처분 바꾸기」도 같은 검사다. 화면의 문은 읽은 버전이
   비었거나 음수면 거절한다 — 견주지 않는 길(`null`)은 누구에게도 안 열린 공통 함수(런북)뿐이다.
4. **처분의 공통 함수 하나**(`write_report_review`) — 화면의 문과 런북의 검토 문(`review_report`)이 이것을 지난다. 신고마다
   자물쇠(`report:review:<id>`) 안에서 **같은 요청 번호를 먼저 찾고**(있으면 첫 결과 — 그 사이 신고가 보관으로 옮겨졌어도), 새
   처분일 때만 신고 · 버전을 잰다. 같은 번호에 다른 내용이면 거절한다. `review_report` 의 인자 · 돌려주는 값 · 거절 코드는 그대로이고
   버전을 견주지 않는다(지금 것을 덮어쓴다) — 덮어쓴 앞 결과는 이제 이력에 남는다.
5. **계정 상태는 공통 함수 하나로만 바뀐다**(`change_account_status`) — 사유 갈래 · 메모 · 실행자 · 관련 신고 · 요청 번호를 받는다.
   바꿀 수 있는 것은 셋: 이용 중 → 정지(`report` · `policy` · `payment` · `eligibility` · `other`), 정지 → 이용 중(`appeal` ·
   `mistake` · `other`), 탈퇴 대기 → 이용 중(`deletion_withdrawn`). **운영자 계정은 정지하지 않는다**(G-111-10). 신고의 이용 정지
   결정은 같은 트랜잭션에서 이 함수로 정지한다(갈래 `report`) — 이미 정지면 그대로 둔다. 누구에게도 열지 않고, ③ 의 회원 화면 문과
   런북이 부른다.
6. **계정 상태 이력**(`account_status_change`)은 트리거가 적는다 — `app_user.status` 가 바뀔 때마다 한 줄. 공통 함수가 같은
   트랜잭션의 설정 값으로 실은 변경이면 그 갈래 · 메모 · 실행자로, 이용자 스스로의 탈퇴 신청이면 `deletion_request` 로(알리지 않음),
   **그 밖(직접 UPDATE)은 실행자 · 사유가 빈 줄과 장애 알림**(`notify_ops`, 종류 `account-status:<줄 id>`) 한 줄이다. 실은 값은 정지 ·
   해제로 바뀔 때만 받는다 — 이용자가 값을 실어도 제 탈퇴 신청을 운영자의 일로 적지 못한다.
7. **정지는 처분을 바꿔도 풀리지 않는다.** 이용 정지 결정을 다른 결과로 바꾸면 반영 결과에 「계정은 아직 이용 정지 상태입니다 —
   해제는 회원 화면에서.」가 서고(상세 문의 `held_suspension_side`), 해제는 ③ 에서 사유 · 실행자와 함께 따로 한다.
8. **목록은 급한 순**(G-111-6) — 처리 필요 안에서 괴롭힘 · 위협 → 기한 지남(접수 다음 날부터 평일 셋을 넘김, 서울 날짜 —
   `report_is_overdue`, 런북의 3영업일 질의와 같은 셈) → 접수가 오래된 것. 줄에 「괴롭힘 · 위협」 · 「기한 지남」 딱지.
9. **대상 회원 요약**(`operator_report_target`) — 신고의 두 계정마다 지금 상태 · 운영자 계정인가 · **현재 신고 기준** 최근 12개월
   경고 수 · 처분 이력 최근 셋, 그리고 「회원 열기」(`/ops/members?q=<계정 id>`). 경고를 고르면 「이번이 N회째」를 보이는데, 이
   신고에 이미 경고가 적혀 있으면 그 건을 한 번만 센다(`warned_here`). 떠난 사람의 신고(`retention.report`)는 세지 않는다(G-110 의 경계).
   보상 단추는 신고 화면에 두지 않는다 — 회원 화면에서 사유를 이어 지급한다(ADR 0187).
10. **실행 전 확인** — 지금 확인창 한 벌(ADR 0166). 대상(닉네임 · 계정 id 앞 8자) · 처분 전 → 후 · 판단 근거 첫 줄 · 결과(「대화방이
    닫히고 모든 이용이 막힙니다」 · 「이용자에게 갈래와 안내번호가 갑니다」), 단추는 구체적인 실행명(「경고로 처분」 · 「이용 정지」 ·
    「경고로 바꾸기」…). 창을 연 순간의 값 · 읽은 버전 · 요청 번호를 고정해 그대로 낸다. 분명한 거절이면 고정본을 버리고 다시 읽고,
    응답을 못 받았을 때만 같은 요청 번호를 다시 쓴다(ADR 0187 의 7 과 같다). 액션은 거절이어도 화면을 다시 그린다(`report-reviewed`).
11. **접속기록** — 쓰기 `reports.review`(신고 id 칸 · 거른 조건 칸 `version=<n>`, 재시도면 ` replayed`), 읽기 `reports.target`(신고 id
    칸 · `reported=<id> reporter=<id>`). 판단 근거 · 메모 · 닉네임은 적지 않는다(ADR 0105). 거절은 앱이 `note_operator_denial` 로.
12. **보존** — 처분 이력은 **신고를 따라간다** — 신고 id 를 외래키로 매지 않아 신고가 보관(`retention.report`)으로 옮겨져도 남고,
    보관된 신고가 파기될 때(처분일부터 6개월, ADR 0098) 함께 지운다 — 판단 근거를 신고보다 오래 두지 않는다. 계정 상태 이력은
    **계정과 함께 지워진다**(`on delete cascade`, 지급 장부 ADR 0187 의 12 와 같다) — 신고로 정지한 것은 신고의 처분 이력이 따로 남는다.
    새 보관 표는 만들지 않는다.

13. **운영자 권한은 이용 중인 계정만**(`is_operator()`) — 운영자 표에 있고 계정이 `active` 일 때만 운영자다. 전에는 표의 줄만
    보아서, 스스로 탈퇴를 신청했거나 직접 UPDATE 로 정지된 운영자도 처분 · 지급을 했다(검수 2026-10-17). 운영자를 내릴 때는
    여전히 표의 줄을 먼저 지운다(`docs/ops/runbook/operators.md`).
14. **재시도는 같은 사람의 것만** — 처분 · 상태 · 무상 지급의 공통 함수 셋 모두, 같은 요청 번호가 다른 실행자에게서 오면 거절한다
    (`22023`). 남의 요청 번호를 들고 와 그 결과를 제 「성공」으로 받거나 접속기록에 제 이름의 재시도를 남기지 못한다. 무상 지급의
    공통 함수(`book_reading_credit_grant`, ADR 0187)도 처분 · 상태와 같이 실행자가 운영자인지 잰다(`42501`) — 몸은 그대로 다시 정의했다.
15. **경고를 옮기면 새 안내다** — 경고로 들어올 때뿐 아니라 경고의 제재 대상 · 갈래가 바뀌어도 확인 · 발송 칸을 비운다. 앞 사람이
    확인한 경고를 다른 사람에게 옮기면, 새로 경고받은 사람에게 안내가 다시 선다(전에는 「확인함」을 물려받아 안 섰다).
16. **처분 이력 최근 셋**은 신고의 경고 · 이용 정지 결정과 계정 상태 이력을 섞되, 신고의 정지 결정이 건 정지(갈래 `report`)는 신고
    줄 하나로만 센다. 탈퇴 대기의 해제는 「탈퇴 대기 해제」로 읽힌다 — 정지 해제가 아니다.

마이그레이션 `20261215090000` · pgTAP `99_operator_report_review` · 화면 `app/ops/reports/`.

## 버린 것

- **처리 버전을 신고 행의 칸으로** — 두 신고 표에 칸을 더하고 옮길 때 함께 옮겨야 한다. 이력 줄 수로 세면 칸이 없고, 이력과
  버전이 어긋날 수 없다.
- **처분을 바꾸면 정지를 자동으로 푼다** — 운영자가 결함이 아니라고 정했다. 해제는 제 이력 줄(사유 · 실행자)을 가져야 한다.
- **런북의 검토 문도 버전을 받게** — 인자를 바꾸면 G-24 검증 ⑨ 와 `52_report_review_door` 가 함께 바뀐다. 런북은 SQL 실행 전
  확인이 지키고, 덮어쓴 앞 결과는 이력에 남으므로 견주지 않는다.
- **직접 UPDATE 를 막는다** — 탈퇴 흐름 · break-glass 가 막힌다. 트리거가 빈 줄과 알림으로 드러내는 안전망이면 충분하다.
