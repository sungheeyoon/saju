# 기다리는 화면은 몇 번째 절을 쓰는지 보인다 — 제출한 응답을 서버가 스트림으로 따라 읽는다

> **운영자 결정 2026-09-29(조율자 세션, 흐름 시안 g 채택)** — 풀이 생성 중 화면은 초 세기 대신 **목차 항목이 하나씩
> 「완료」**되는 모양으로 간다. 진행은 **실제 서버 신호**여야 하고 가짜 타이머로 채우지 않는다. 문구 「쓰는 중」 · 「완료」는
> 시안 g 의 것으로 승인. 궁합은 소제목을 모델이 정하므로 「n번째 이야기」로만 보이고, 목차 끝에 「마지막 검토」 칸을 둔다
> (조율자 브리프). 프롬프트는 고치지 않는다 — 프롬프트 실험 보류(2026-09-15).

## 잰 것 (2026-09-29, 코드에서)

- 제출은 `responses.create({ background: true })` 한 번이다(`app/me/reading/model.ts` `submitBackgroundReading`). 완성본은
  webhook · 복구기가 가져와(`collect.ts`) **받은 뒤 통째로** 검사한다(`checkReading`). 만드는 동안 서버가 아는 것은 얼린 작업의
  상태 다섯(`frozen · preparing · submitting · submitted · retrieving`)뿐이고, 화면이 받는 것은 그것도 아닌 시도의
  `running · succeeded · failed` 셋이다(`my_last_reading_run`). 그래서 화면은 초를 셌다 — `panel.tsx` 의 `LoadingState` 주석이
  「시간만 보고 단계를 지어 보이면 그건 꾸며 낸 진행」이라고 적어 둔 자리다.
- **background 응답은 만들 때 `stream: true` 가 아니면 나중에 스트림으로 못 읽는다.** OpenAI 문서(Background mode, 2026-09-29
  에 읽음): 「You can only start a new stream from a background response if you created it with `stream=true`」. 그러니
  「제출 뒤 같은 응답을 다시 스트림으로 연다」는 안 되고, **제출 자체를 `background: true, stream: true` 로** 해야 한다. SDK
  (`openai` 7.8.0)는 `responses.create` 가 그때 사건 스트림을 내고, 첫 사건(`response.created`)이 응답 id 를 든다.
- `store: false` 와 background 는 함께 쓸 수 있다(같은 문서 — 비동기 실행을 위해 잠시 보관한다). 지금 설정 그대로다.
- 모델의 출력은 JSON(구조화 출력)이고 본문은 그 안의 `markdown` 문자열이다. 스트림의 조각(`response.output_text.delta`)은
  JSON 글자 그대로라 줄바꿈이 `\n` 두 글자로 온다 — 소제목을 세려면 그 문자열만 풀어 읽어야 한다.
- 자기 풀이 · 다른 사람 풀이는 프롬프트가 절 아홉을 이름으로 시킨다(`prompt.ts` `expertSelfSections`, 소제목 `##`). 두 궁합은
  `needs-v1` 이라 「소제목의 수와 차례는 네가 정한다」 — 이름을 미리 알 수 없다. 두 판 다 본문 뒤에 `### 근거` 절이 선다.
- 생성을 떠나보내는 `after()` 는 누른 화면의 라우트 `maxDuration`(풀이 화면 300초) 안에서 돈다.

## 정한 것

1. **제출을 스트림으로 한다** — `background: true, stream: true`. 첫 사건에서 응답 id 를 받아 지금처럼 이름표를 적고
   (`adopt_reading_job`), 그 뒤 **같은 `after()` 안에서** 남은 사건을 따라 읽는다. 완성본을 가져와 검사 · 저장하는 길은
   그대로 webhook · 복구기다 — 따라 읽는 쪽은 글을 한 자도 적지 않는다.
2. **절 번호만 적는다.** 본문 문자열에서 줄머리 `## ` 를 셀 때마다, 그리고 `### 근거` 가 서거나 본문이 닫힐 때(「본문을 다
   썼다」) 열쇠 문 `note_reading_progress` 로 두 값만 적는다. 값은 올라가기만 한다. 검사 전의 글은 어디에도 안 나간다.
3. **끊기면 진행만 멈춘다.** 스트림이 끊기거나 함수가 `maxDuration` 에 닿아도 background 응답은 provider 쪽에서 계속 돌고
   완성은 webhook 이 받는다. 화면은 마지막으로 적힌 절에 머물다가 결과로 넘어간다.
4. **화면은 적힌 값만 그린다** — 목차 줄마다 「완료」 · 「쓰는 중」 · 기다림, 끝에 「마지막 검토」. 시작한 절이 k 이면 앞의 k−1
   절이 완료, k 번째가 쓰는 중이다(다음 머리가 서야 앞 절이 끝난 것이다). 「본문을 다 썼다」거나 작업이 `retrieving` 이면 절은
   다 완료이고 「마지막 검토」가 검토 중이다. 검토가 끝나 시도가 닫히면 화면은 결과로 다시 읽힌다. 자기 풀이 · 다른 사람
   풀이는 프롬프트의 절 이름(`selfSectionTitlesOf`)을, 두 궁합은 「n번째 이야기」를 쓴다. 시간으로 단계를 짓지 않는다.
5. **보는 사람은 그대로다.** `my_last_reading_run` 이 세 칸(작업 상태 · 시작한 절 · 본문을 다 썼는가)을 더 낸다 — 그 시도의
   상태를 이미 보던 사람에게만. 얼린 작업은 시도가 끝나면 지워지므로(`clear_reading_job`) 이 값도 도는 동안만 산다.

## 값

- **토큰이 나가는 호출의 수는 그대로다** — 호출 하나를 스트림으로 받을 뿐이다. 달라지는 것은 **함수가 붙들린 시간**이다.
  앞서 `after()` 는 제출 왕복 하나로 끝났고, 이제 모델이 본문을 다 쓸 때까지(재어 본 적 없음 — 생성 문턱은 240초) 스트림을
  붙든다. Vercel Fluid 는 기다리는 동안의 CPU 는 안 세고 메모리 시간은 센다 — 운영 베타의 풀이 수(하루 상한 안)에서는 작다.
  공개 출시 뒤 풀이 수가 크게 늘면 다시 잰다.
- 절 머리를 셀 때마다 DB 왕복 하나 — 풀이 하나에 열 번 남짓.
- 모델이 시킨 것보다 소제목을 적게 · 많게 쓰면 화면의 줄과 어긋난다. 많으면 마지막 줄에 머물고, 적으면 「본문을 다 썼다」가
  나머지를 한꺼번에 닫는다 — 둘 다 **적힌 값보다 앞서 가지는 않는다.**
