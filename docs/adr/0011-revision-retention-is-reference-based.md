# 판본은 조회가 아니라 수정에서 생기고, 보존은 참조를 기준으로 한다

`PersonChartRevision` 은 출생정보를 고칠 때마다 Person 을 덮어쓰지 않기 위해 생겼다
(ADR 0004). 그러나 그 말이 곧 **모든 이전 입력을 영구 보존하거나 사용자에게 판본 목록을
보여 준다**는 뜻은 아니다. 과거 동의와 결과를 재현하는 데 필요한 판본과, 더는 아무 사건도
가리키지 않는 이전 입력은 수명이 다르다.

## 판본은 저장한 입력이 실제로 달라질 때만 생긴다

- 사주·궁합·Match 결과를 **조회하는 것만으로는 판본을 만들지 않는다.**
- 사용자가 Evidence 관련 입력을 저장했고 현재 판본과 fingerprint 가 다를 때만 새 판본을
  만든다. 같은 값을 다시 저장하면 새 행을 만들지 않는다.
- 이름·메모·공개 프로필처럼 계산을 바꾸지 않는 수정도 판본을 만들지 않는다.

따라서 과거 결과를 볼 때마다 생년월일시를 다시 복제하는 구조가 아니다. 판본은 계산 기록이
아니라 **실제로 달랐던 계산 입력**이다.

## 사용자 화면은 현재 입력 하나를 기준으로 한다

자기 명식과 직접 관리하는 Person 의 수동 궁합은 현재 판본으로 계산한다. 일반 화면에 판본
선택기나 무한한 수정 이력을 만들지 않는다. 입력이 바뀌면 다음 사실만 알린다.

> 출생정보가 변경되었습니다. 현재 사주와 궁합은 새 입력으로 계산되므로 이전에 본 결과와
> 다를 수 있습니다.

과거 결과를 보존해야 하는 명시적 사건이 없었다면 예전에 본 사주·수동 궁합 결과 자체는
저장하지 않는다.

## 보존은 개수보다 참조가 먼저다

한 Person 에 대해 다음 규칙을 적용한다.

1. **현재 판본**은 항상 보존한다.
2. 살아 있는 pending 요청과 Match·Reading 이 참조하는 판본은 각 사건의 보존 수명 동안
   보존한다. 이 판본들은 아래 개수 제한에서 제외한다. 지우면 동의 대상이나 이미 본 결과의
   근거가 끊긴다.
3. 위 사건들이 참조하지 않는 **이전 판본은 최근 두 개까지만** 보존한다. 현재 판본까지
   합치면 일반적인 미참조 입력 보존의 상한은 세 개다.
4. 세 번째 미참조 이전 판본이 생기면 가장 오래된 미참조 판본을 정리한다.

즉 전체 표에 무조건 세 행만 허용하지 않는다. 여러 Match 가 서로 다른 입력을 정당하게
붙들고 있으면 참조된 판본은 셋을 넘을 수 있다. hard cap 으로 그것을 지우는 대신, 아무
기록도 가리키지 않는 입력만 제한한다.

## 요청 상태와 참조 수명

- pending 요청은 수락 여부를 결정할 때까지 양쪽 판본을 붙들며 개수 제한에서 제외한다.
- accepted 요청의 판본은 Match 가 이어받아 보존한다.
- rejected·invalidated·cancelled 요청은 사건·시각·reason snapshot·입력 fingerprint 를
  남길 수 있지만, 그 요청만을 위해 정확한 과거 출생 입력을 영구 보존하지 않는다.
- terminal `MatchRequest` 는 판본 FK 를 놓는다. 대신 요청은 **두 지문**을 든다 — 무엇에
  대한 요청이었는지는 남고, 그 요청 하나 때문에 정확한 과거 출생 입력이 남지는 않는다.
- 정리 작업은 참조를 먼저 검사하고, Match·Reading 의 매인 판본을 절대 orphan 으로 만들지
  않는다.

## Match 와 Reading 은 예외가 아니라 명시적 기록이다

성립한 Match 는 양쪽이 동의한 입력으로 난 공유 결과다. 이후 한쪽이 입력을 고쳐도 기존
Match 를 현재 판본으로 다시 계산하지 않는다. 새 입력으로 함께 보려면 새 요청과 새 동의가
필요하다.

Reading 도 당시 redacted Evidence 와 `match-v0` snapshot 을 보존한다. 이 두 사건이 판본을
붙드는 것은 무한 수정 이력을 제공하기 위해서가 아니라, **이미 공유된 결과를 조용히 다른
입력으로 바꾸지 않기 위해서**다.

## Consequences

- 이 수명주기는 `20260825180000_revision_retention.sql` 이 구현한다. 무엇이 참조인지는
  표 이름을 적어 두는 대신 `person_chart_revision` 을 가리키는 **FK 자체**에서 읽는다 —
  Reading 이 붙는 날(PRD 9단계) 이 함수를 다시 보지 않아도 그 판본이 지켜져야 하기
  때문이다. 정책은 「누가 FK 를 드는가」로 적히고, terminal 요청이 판본을 놓는 것이 곧
  「그 요청은 더 이상 참조가 아니다」라는 선언이 된다.
- 놓는 일을 호출부가 기억하지 않는다. 요청이 terminal 로 가는 자리가 넷이라(거절·거둠·
  무효·차단) 넷 다에 적으면 언젠가 하나만 안 고쳐지고, 안 고쳐진 쪽은 언제나 더 오래
  붙드는 쪽이다. 트리거가 놓고, 검사식이 「terminal 인데 판본을 든」 상태를 만들 수
  없게 한다.
- 쌓인 차례가 판정에 쓰이게 되면서 `person_chart_revision.created_at` 의 기본값이
  `clock_timestamp()` 로 바뀌었다. `now()` 는 트랜잭션이 열린 시각이라 한 트랜잭션 안에서
  쌓인 둘에게 같은 값을 주고, 그러면 「가장 오래된 것을 지운다」가 아무것이나 지우는 일이
  된다.
- 삭제는 데이터 크기보다 참조 무결성과 개인정보 최소 보존을 함께 본다.
- 사용자에게 쓰는 말은 `현재 입력`, `이전 입력으로 교체됨`, `동의 당시 입력`이다.
  `무효`는 pending 요청 상태에만 쓰고, 과거에 정상적으로 사용된 판본을 무효라고 부르지
  않는다.
