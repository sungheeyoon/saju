# 인연 궁합 입력은 두 판으로 짓고 견준다 — 운영은 제한형 A 다

## 무엇이 틀려 있었나

`shareEvidence` 는 명식에서 키 몇 개를 빼고 `compatibility` 를 **통째로** 남겼다. 그래서
동의 화면이 「열리지 않는다」고 적은 것이 모델에 가고 있었다.

- 각자의 **억부 후보와 그 역할**(`eokbuMatch.*.element·role`) — 역할이 신강/신약을 그대로 드러낸다
- **지장간 가중 오행 세력**(`elementSupport.*.weakest`)
- 두 사람 사이 쟁합에 딸린 **원국 안 경쟁자** — 곧 「그 사람 원국 안에 같은 합이 있다」
- **성별**, **조자시/야자시 계산 옵션**, 절입 시각, 절기·시각 경계 문장
- 계약의 `withheld` 는 「억부·오행 세력은 빠진다」고 적고 있었다 — 자료와 다른 말이었다

## 결정

**견줄 두 판은 넣을 필드를 적어서 새 객체로 짓는다**(`MATCH_INPUT_FIELDS`).

**2026-09-15 — 운영을 제한형 A 로 올렸다.** 실험(1~5라운드, 본인 명식 한 쌍과 테스트 표본)을 마치고
A 입력과 궁합 읽는 법 4판(`pairReading: 'guide-v4'`)을 한 세트로 모든 사용자의 새 인연 궁합 생성에
적용했다. 계정별 분기는 없다. 옛 컷(`legacy-v0`)은 원복용으로 코드에 남는다 — `LEGACY_PAIR_ASSEMBLY`.

- 판본: 궁합(`match`·`private`)은 `reading-prompt-v11`(`READING_POLICY.pairVersion`), 개인 풀이는
  `reading-prompt-v10` 그대로다. 저장된 옛 풀이는 그대로 남는다.
- **비공개 궁합은 입력을 줄이지 않았다** — 두 사람 분석 자료를 그대로 싣고, 같은 4판 지시를 쓴다.
  읽는 법의 경로 안내는 실제로 실린 자료만 설명한다(`guideFor('private')`).
- 4판은 사람·자리·방향을 똑같이 읽고, **장면만 사이를 탄다** — 인연 궁합은 「아직 서로를 잘 모르는
  두 사람」, 비공개 궁합은 고른 사이(가족 / 친구·동료 / 연인·배우자 / 모름). 고정 목차는 아니다.
- 원복: `CONTROL` 의 `matchInput`·`pairReading` 을 `LEGACY_PAIR_ASSEMBLY` 값으로 되돌리고
  `pairVersion` 을 새 이름으로 올린다(또는 이 변경 커밋을 되돌린다). 생성기(`readingInputOf`)는 자료의 판도
  같은 조립에서 읽으므로 **`CONTROL` 두 칸이 스위치의 전부다** — 처음 올린 커밋에서는 자료가 따로 기본값
  (`DEFAULT_MATCH_INPUT`)을 읽어, 이대로 원복하면 자료와 지시가 갈려 인연 궁합 생성이 멈췄다. 시험이 옛 조립으로
  생성 입력을 지어 잰다(`generator.test.ts`).

| | A 제한형 `limited-v1` | B 확장형 `extended-v1` |
|---|---|---|
| 위치 | **운영**(2026-09-15) | **실험 전용** — 테스트 명식·동의한 본인 명식으로만 부른다 |
| 여덟 글자·자리·시각 입력 여부 | 싣는다 | 싣는다 |
| 두 사람 사이 관계·함께 이룬 구조 (참여자·완성·방향·순환) | 싣는다 | 싣는다 |
| 쟁합 경쟁자 | **다른 원국 것만** | 원국 안 것까지 |
| 오행 보완 | 글자 수로 센 `missing·supplied·stillMissing` | + 가중 세력 `weakest` |
| 두 일간 사이 십성 | 싣는다 | 싣는다 |
| 각자의 신강신약·억부 후보·오행 세력 | 없다 | `charts.*.analysis.{strength,eokbu,elements}` 일부, `eokbuMatch` |
| 개인 신살·격국·조후·12운성·대운·지금 운 | 없다 | 없다 |
| 성별·계산 옵션·절입·경계 문장 | 없다 | 없다 — 경계는 「기둥이 달라질 수 있다」 한 문장 |
| 점수표 「용신을 상대가 가졌다」 | 없다 | 있다 |

**자료와 지시는 같은 값을 든다.** `readingEvidenceOf(…, matchInput)` 과 `PromptAssembly.matchInput`
이 어긋나면 `readingPromptOf` 가 멈춘다. 점수표·범위 절·절 목록은 자료에 실린 근거만 가리킨다.

**검사는 두 판 모두 본문의 `억부` 를 막는다.** 한때 이 낱말을 풀어 두었던 까닭은 자료에 실렸고
절이 시켰기 때문이다(check.ts). 이제 A 에는 값이 없고, B 는 판정의 이름을 본문에 안 쓰게 한다.
B 가 그 선을 얼마나 넘는지는 견주는 실험이 규칙 위반으로 센다.

## 기존 정책과 B 가 다른 곳

ADR 0008·0012 와 동의 화면(`MATCH_DISCLOSURE`)은 상대 원국 하나에 대한 판정 — 신강신약·억부 —
을 **열지 않는다**고 적었다. **B 는 그것을 모델 입력에 넣는다.** 모델에 넣은 판정은 두 사람이
함께 읽는 글에 드러날 수 있고, 「넣지만 글에는 절대 안 나온다」는 보장은 없다.

옛 컷도 이 점에서는 B 와 같았다 — `eokbuMatch` 와 가중 세력을 싣는다. A 를 운영으로 올리면서
새 인연 궁합 입력에서는 빠졌다. 옛 컷은 원복용으로만 남는다.

그래서 B 는 운영에 올리지 않는다. B 가 낫다고 나와도 올리려면 **동의 문구와 이 ADR 을 먼저
고쳐야 한다** — 결과만으로 동의 범위를 넓히지 않는다.

## 어느 판이 나은가

A 를 운영판으로 정했다(위). 표본이 작아 판의 우열을 일반화하지는 않는다. 견주는 법은
`docs/analysis/match-input-comparison.md` 에 있다. 9/1 자리 색인 실험은 **입력 범위 비교가 아니므로**
이 우열의 근거로 쓰지 않는다.

## 함께 바뀐 것

- A·B 의 `한눈에` 는 절입·사주년을 안 적는다 — 자료에 없다. 옛 컷은 그대로 적는다
- 인연 궁합 지시가 **넘겨받은 사이**를 쓸 수 있다(실험이 연인으로 고정할 때). 운영은 사이를 안 넘기므로
  성립 방식 문장 그대로다 — 「인연 찾기에서 만나 서로 상세 궁합에 동의한 사이다. 아직 서로를 잘 모르는 두 사람이다」
- 검사는 자료가 든 판(`contract.matchInput`, 없으면 옛 컷)을 읽어 `억부` 를 옛 컷에서만 풀어 둔다
- 판본 이름은 궁합 `reading-prompt-v11`, 개인 풀이 `reading-prompt-v10` 이다(`promptVersionOf`)
- 개인 풀이의 자료와 지시는 그대로다. 비공개 궁합은 자료는 그대로, 지시는 4판이다 — 시험이 잠근다
- 자리가 붙은 사실 목록은 두 궁합에만 싣는다. 한 줄 요약은 본문 뒤에 받는다(`writesSummaryLast`)

## 실험 코드를 걷었다(2026-09-15)

운영에 올린 뒤 실험판 코드를 지웠다 — 읽는 법 1~3판(`guide-v1`~`v3`), 주장·근거 연결판(`pairWriting`·`claims`
출력 스키마·`checkClaims`), 2~5라운드 변형. 남은 것은 운영 4판·원복 조립(`plain-v1` + `legacy-v0`)·입력만 견준
1라운드 두 판이다. **운영 두 궁합과 원복 조립의 프롬프트는 바이트 단위로 그대로다.** 지운 판의 프롬프트는 커밋
`e586152` 에서 재현한다 — `.reading-live/` 산출물의 해시도 그 커밋 기준이다.

## 남은 것

- 옛 인연 궁합 풀이의 원문 근거가 당사자에게 열려 있던 문은 ADR 0068 이 닫았다(2026-09-15 프로덕션 적용).
- 확장형 B 를 올리려면 동의 문구와 이 ADR 을 먼저 고쳐야 한다.
