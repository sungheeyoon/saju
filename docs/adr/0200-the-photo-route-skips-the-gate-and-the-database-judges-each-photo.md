# 사진 주소는 관문을 안 지나고, 한 장마다 DB 가 판정만 한다

> **제안**(2026-10-22) — 결정 점검표의 「누가 무엇을 볼 수 있는가 · 할 수 있는가」(관문) 줄이라 운영자가 머지 전에 답한다.
> 운영자 지시는 「다 알아서 진행하고 보고해」이고, 이 결정은 그 아래에서 PR 만 만든다. 판본 · 캐시 기간은 이 결정에 안 든다 —
> 보존 · 접근 경계라 G-119 로 따로 묻는다.

## 잰 것 (2026-10-22, `origin/main` `3eb5cae2`, 코드로 셈)

**사진 한 장에 드는 왕복** — 관문 matcher `'/me/:path*'` 가 `/me/photo/**` 도 잡았다.

| 차례 | 자리 | 왕복 |
| --- | --- | --- |
| 1 | 관문 `getUser` | Auth `/auth/v1/user` 1 (토큰이 만료됐으면 `/token` 갱신 1 더) |
| 2 | 관문 계정 · 일정(나란히) | PostgREST `app_user` 1 + `current_beta_schedule` 1 |
| 3 | 라우트 `photo_at` | PostgREST 1 (바이트를 base64 로 싣는다 — 한 장 상한 512KB) |

한 장 = Supabase 요청 **넷**(Auth 1 · REST 3), 차례로 세 물결, 관문 실행 하나와 라우트 실행 하나. 관문의 셋은 쓰는 데가 없었다 —
`gateFor` 는 `/me/photo/` 를 안 보고(`src/lib/consent/gate.ts`), GET 이라 활동도 안 적고(ADR 0118), 라우트는 `signedInUser` 를 안
부른다. 접근 판정은 처음부터 `photo_at` → `may_see_photo` 가 했다(ADR 0040).

**한 화면이 여는 사진** — 같은 주소는 한 화면에서 한 번만 받는다.

- 인연 탭(덱 6명, 되돌리면 잠시 7): 사람마다 대표 `/me/photo/{id}/1` 하나(덱 카드 · 다음 카드 · 궤도 지도 · 닫힌 ⓘ 시트 안 지도가 같은
  주소를 쓴다 — 시트는 `<dialog>` 라 닫혀 있어도 그린다) **6** + 지금 카드의 다음 장 미리 받기(`card-photos.tsx`) **1** + 받은
  요청의 아바타(`/me/photo/{id}` — 대표와 다른 주소) **요청 수**. 카드를 한 장 넘길 때마다 미리 받기 1.
- 대화 목록: 방마다 아바타 **1**(`room-list.tsx`). 받은 사주풀이 책장의 인연 궁합 표지도 짝마다 1.

그래서 인연 탭을 한 번 열면 사진에만 Supabase 요청이 약 7×4 = **28**(요청이 있으면 그 수 × 4 더), 고친 뒤 **7**. `max-age=60` 이라
1분 뒤 다시 열면 같은 수를 다시 낸다. Supabase Egress · Vercel 호출 한도와 맞물린다는 말은 **잰 값이 없다** — 이 수는 코드로 센 것이다.

## 정한 것

matcher 의 `'/me/:path*'` 를 `'/me'` · `'/me/((?!photo/).*)'` 둘로 가른다. `/me/photo/` 로 시작하는 주소만 관문을 안 지나고,
`/me` 아래 나머지(이웃 이름 `/me/photos` · 그 자리 `/me/photo` 포함)는 그대로다. 정규식은 Next 가 쓰는 함수(`getMiddlewareMatchers`)로
지은 값으로 시험이 잰다.

한 장 = PostgREST 1, 한 물결, 라우트 실행 하나.

## 경계 — 빼도 그대로인가

`may_see_photo`(`20261030090000`)는 `auth.uid()` 가 있고 `is_active_account()`(베타가 안 끝났고 내 `app_user.status = 'active'`)일 때만
참이고, 남의 사진은 상대도 `active` 이고 덱 · 지나친 인연 · 진행 중인 요청(차단 없음) · 보이는 Match(차단 없음) 중 하나일 때만 연다.
`photo_at` 은 `anon` 에게 grant 가 없어 로그인 안 한 요청은 `42501` → 404 다.

| 누가 | 주소 | 기대 | 전(관문 지남) | 뒤(관문 안 지남) |
| --- | --- | --- | --- | --- |
| 정지된 사람(`suspended`) | 남의 사진 · 제 사진 | 404 | 관문은 안 막음 → `is_active_account` 거짓 → 404 | 같다 — 404 |
| 탈퇴 신청한 사람(`deletion_requested`) | 같음 | 404 | 같은 갈래 → 404 | 같다 — 404 |
| 계정이 지워진 사람(토큰은 아직 서명이 맞음) | 같음 | 404 | 관문이 403 `user_not_found` 로 쿠키를 걷음 → anon → 404 | `auth.uid()` 는 남지만 `app_user` 가 없어 `is_active_account` 거짓 → 404 |
| 베타 종료 뒤(`/closed`) | 같음 | 404 | `gateFor` 가 사진 주소를 안 봄 → `beta_is_over()` → 404 | 같다 — 404 |
| 로그인 안 한 사람 | 같음 | 404 | `photo_at` grant 없음 → 404 | 같다 — 404 |
| 차단한 · 차단당한 사람 | 상대 사진 | 404(브라우저 캐시 1분 안이면 옛 바이트) | DB 판정 → 404 | 같다 |
| **다른 기기에서 나간 세션의 쿠키**(`session_not_found`) | 볼 수 있던 사진 | 404 | 관문이 쿠키를 걷음 → 404 | **토큰이 만료될 때까지(로컬 `jwt_expiry` 3600초, 운영 값은 확인 전) 그 사람이 볼 수 있는 사진이 열린다** |
| 볼 수 있는 사람 · 토큰 만료 · 갱신 토큰 유효 | 볼 수 있는 사진 | 200 | 관문이 갱신하고 걷은 · 새 쿠키를 응답에 실음 | 라우트의 클라이언트가 `photo_at` 전에 갱신하고(`_getAccessToken` → `getSession`) 라우트는 쿠키를 쓸 수 있어 응답에 실음 → 200 |

달라지는 줄은 하나다 — **끊긴 세션의 토큰으로 사진이 최대 토큰 수명만큼 열린다.** 그 토큰은 같은 시간 동안 Supabase 의 PostgREST 에
직접 `photo_at` 을 불러도 열린다(ADR 0117 「DB 는 이미 서명만 본다」 — 로컬에서 `logout` 한 토큰으로 `/rest/v1` 이 200). 그러니
새로 열리는 능력은 없고, 우리 도메인의 쿠키로도 같은 것이 열리게 될 뿐이다. 볼 수 있는 범위는 그 계정이 원래 볼 수 있던 사진이다.

**세션 갱신을 관문이 하던 것이 빠지면** — 사진 요청이 만료된 토큰을 들고 오면 라우트가 갱신한다. 같은 화면의 사진 여럿이 나란히 오면
요청마다 갱신하는 것은 전에도 같았다(관문이 요청마다 돌았다) — 회전된 갱신 토큰의 재사용 창(`refresh_token_reuse_interval`, 로컬 10초)이
그것을 받는다. 화면 요청은 사진보다 먼저 관문을 지나 갱신하므로 사진이 만료 토큰을 드는 일은 드물다. 지워진 계정의 쿠키는 사진
요청에서는 안 걷히고 다음 화면 요청에서 관문이 걷는다.

**관문이 던지는 실패**(예: `supabaseEnv`)는 더 이상 사진을 500 으로 세우지 않는다.

## 고르지 않은 것

- **관문 안에서 사진 주소면 곧장 넘기기** — 관문 실행 자체(Vercel 호출 하나)는 남는다. matcher 로 빼면 실행이 없다.
- **사진 주소를 `/me` 밖(`/photo/…`)으로 옮기기** — 같은 효과인데 주소를 쓰는 자리(아바타 · 카드 · 편집 칸 · 시험 · 점검
  스크립트)을 다 옮기고, 옛 앱 · 열린 탭의 옛 주소가 깨진다.
- **라우트가 `signedInUser`(서명 확인)를 먼저 부르기** — 관문 밖에서 그것을 부르는 것은 ADR 0117 이 막은 길이고(경계 시험이 붉다),
  판정은 어차피 `photo_at` 이 한다.
