# 앱은 계정마다 비공개 채널 하나로 스스로 갱신한다 — 채널은 「바뀌었다」만 알리고 내용은 읽는 문이 준다

> **운영자 결정 2026-10-08**(대화에서, 나이트 세션 지시) — 「채팅 안전 베타의 “실시간이 아니다” 정책을 변경하는 것을 승인한다.
> 앱 내 자동 갱신, 탭·기기 동기화, 외부 메시지 통보를 구현하는 방향을 승인한다. 실시간 접속 여부·타이핑·상대 읽음 표시는
> 이번 필수 범위가 아니다. 필요한 유료 서비스나 플랜 업그레이드는 도입할 의향이 있다. 다만 실제 구매·결제·계정 변경·프로덕션
> 배포의 포괄 승인은 아니다.」 같은 날 「운영 db push 는 밤사이 하지 않는다(머지 · 배포와 함께)」고 답했다.

PRD 「앱 내 채팅」의 「실시간이 아니다」(2026-09-23)와 §7.2 의 「실시간으로 올리지 않는다」 가운데 **앞의 것만** 바꾼다.
접속 상태(§7.2)는 그대로 화면을 다시 읽을 때 바뀐다 — 이번 범위가 아니다. 외부 통보는 ADR 0156 이 든다.

## 수용 기준 (이 ADR 의 시험이 잰다)

1. **채팅** — 두 계정이 같은 방을 열고 있으면 상대 메시지가 전송 성공(서버 커밋) 뒤 **2초 안에** 나타난다. 중복 · 누락 없이
   서버 순서(`seq`)로 선다. 수신과 갱신이 쓰던 입력 · 초점 · 과거를 읽던 스크롤을 건드리지 않는다. **지금 보이는 메시지까지만**
   읽음으로 남기고, 숨겨진 탭은 읽음으로 남기지 않는다. 최근 200건 앞의 메시지를 더 불러올 수 있다.
2. **목록 · 딱지 · 인연 · 소식** — 새 메시지 · 마지막 메시지 · 안 읽은 수 · 새 대화방이 스스로 갱신된다. 요청 도착 · 수락 · 거절 ·
   취소 · 만료 · 무효와 인연 궁합 완료 · 실패가 관련 화면과 딱지에 스스로 선다. 딱지만 바뀌고 목록이 옛 상태로 남지 않는다.
   같은 계정의 다른 탭 · 기기에서 읽거나 풀이권을 쓰면 따라 바뀐다.
3. **안전과 복구** — 차단 · 정지 · 탈퇴로 방이 닫히면 상대 화면도 바뀌고 전송이 막힌다(차단 사실 비공개는 그대로 — 닫힌 까닭의
   문장은 지금 `my_chat_rooms` 가 정한 것뿐). 남의 방 · 메시지 · 이벤트는 구독도 읽기도 안 된다. 끊김 · 재연결 · 절전 · 앱 복귀 뒤
   서버 상태를 다시 대조해 빠진 변경을 메운다. 채널이 실패해도 재시도와 **제한된** 대체 조회로 갱신이 영영 멈추지 않는다.
   계정 전환 · 로그아웃 · 화면 이동 때 구독을 걷는다. 기존 RLS 와 RPC 를 우회하거나 원본 표를 공개하지 않는다.

## 정한 것

### 채널 — 계정마다 하나, 비공개, 내용 없음

- **Supabase Realtime Broadcast 의 비공개 채널**(Realtime Authorization)이다. 주제(topic)는 `user:<auth.uid()>` 하나다.
  Postgres Changes 를 쓰지 않는다 — 그것은 원본 표에 `select` RLS 를 열어야 하고, 이 저장소의 표는 읽는 문(RPC)으로만 읽힌다(ADR 0091).
- **누가 듣나** — `realtime.messages` 의 RLS 정책 하나: `authenticated` 가 `realtime.topic() = 'user:' || auth.uid()` 이고
  `extension = 'broadcast'` 인 줄만 `select` 한다. **클라이언트의 `insert`(보내기) 정책은 없다** — 브라우저는 듣기만 하고, 보내는 것은
  DB 트리거뿐이다. 남의 주제를 구독하면 채널이 거절된다(시험이 잰다).
- **보내는 것은 「무엇이 바뀌었나」뿐이다.** 이벤트 이름 `changed`, 실은 것:

  ```json
  { "area": "chat" | "requests" | "notifications" | "credits", "match_id": "<uuid>|null", "seq": <bigint>|null }
  ```

  (그리고 `realtime.send` 가 스스로 붙이는 메시지 `id`.) 본문 · 닉네임 · 상대 id · 닫힌 까닭 · 차단 여부는 **싣지 않는다.** 받은 쪽은 그 갈래의 읽는 문(`my_chat_rooms` ·
  `my_chat_messages` · `my_match_requests` · `my_notifications` · 풀이권 문)을 다시 불러 **서버의 진실**을 읽는다. 그래서 채널이
  새도 내용이 새지 않고, 비공개 규칙(닫힌 방의 문장 · 차단 비공개)은 읽는 문 하나가 계속 든다.
- **누가 보내나** — DB 트리거(`realtime.send`)다. 앱 서버 액션이 아니다 — 크론 · 운영 SQL · 처분처럼 앱을 안 지나는 변경도 같이
  알린다. 트리거는 전이 표를 든 **문장 단위**(`for each statement`)라 크론이 한 문장으로 요청 여럿을 접어도 (사람 · 갈래 ·
  match_id) 하나에 한 번만 보낸다. 보내는 자리:

  | 바뀐 것 | 받는 주제 | area · 실은 값 |
  | --- | --- | --- |
  | `chat_message` 가 생겼다 | 방의 두 참여자(보낸 사람 포함 — 다른 탭) | `chat` · match_id · 그 문장의 가장 큰 seq |
  | `chat_read` 가 움직였다 | 읽은 사람 자신(다른 탭 · 기기) | `chat` · match_id |
  | `chat_room` 이 생겼다 | 두 참여자 | `chat` · match_id |
  | `chat_room` 이 닫혔다 · 참여자가 비었다 | 방의 남은 참여자 | `chat` · match_id |
  | `match_request` 가 생겼다 | 보낸 사람과 받은 사람 | `requests` |
  | `match_request` 의 상태가 바뀌었다(수락 · 거절 · 취소 · 만료 · 무효) | 보낸 사람과 받은 사람 | `requests` · match_id(그 요청의 Match 가 이미 있으면) |
  | `match` 가 섰다 — 수락은 요청을 먼저 고치고 Match 를 나중에 넣어, 요청의 트리거는 Match 를 못 본다 | 두 사람 | `requests` · match_id |
  | `notification` 이 생겼다 · 읽음이 바뀌었다 · 지워졌다(cascade) | 그 소식의 주인 | `notifications` |
  | 풀이권 잔액을 세는 표 셋(`reading_credit_grant` · `reading_bundle` · `reading_credit_use`)의 insert · update · delete | 그 계정 | `credits` |
  | 인연 궁합(`reading_run` 의 `kind = 'match'`)이 `running` 에서 벗어났다 — 끝났다 · 실패했다 | 그 Match 의 두 사람 | `requests` · match_id |

  요청의 **만료도 쓰기다** — 크론 `match-request-expiry` 가 `expire_match_requests()` 로 `status = 'expired'` 를 적으면 위의
  `match_request` 줄이 알린다. 그래서 `expires_at` 이 지난 뒤 화면이 바뀌기까지의 늦음은 그 크론의 간격이다 — 만료 크론을
  1분마다로 당겨 늦음을 1분 안으로 둔다.

  **보내기의 실패가 원래 쓰기를 무르지 않는다** — 트리거는 `realtime.send` 의 예외를 삼킨다(채널은 부속이다, ADR 0078 의 결).
  복구는 아래 「다시 대조」가 든다.

### 브라우저 — 구독 하나, 갱신의 책임은 갈래마다 하나

- **구독은 앱 전체에 하나다.** 로그인한 세션이 확인되면(`useBrowserSession`) 루트에 선 라이브 층이 `user:<uid>` 하나를 열고,
  사용자 id 가 바뀌거나(계정 전환) 로그아웃하면 걷는다. 기능마다 채널 · 타이머를 따로 열지 않는다.
- **받은 이벤트는 지금 있는 창 신호로 옮긴다** — `CHAT_UNREAD_MOVED` · `NOTIFICATIONS_UNREAD_MOVED` · `REQUESTS_TO_ANSWER_MOVED` ·
  `READING_CREDITS_MOVED`(머리글이 이미 듣는다), 그리고 방 · 목록이 듣는 채팅 신호 하나(match_id · seq 를 싣는다).
  서버가 그리는 목록 화면(인연 탭 · 요청함 · 소식 · 대화방 목록)은 그 갈래가 바뀌었을 때만 `router.refresh()` 를 **묶어서 한 번**
  (짧은 debounce) 부른다 — 페이지 새로고침(`location.reload`)은 쓰지 않는다.
- **방 안은 클라이언트가 메시지를 든다.** 서버가 첫 200건을 그려 넘기고, 이벤트의 `seq` 가 가진 것보다 크면 브라우저 클라이언트로
  `my_chat_messages` 를 다시 읽어 `message_id` 로 합치고 `seq` 로 세운다(중복 · 순서). 빈 자리는 **돌아온 쪽이 가득 찼는가**로
  가른다 — 가장 최근 한 쪽(50건)을 읽어 그 쪽이 가득 찼고 그 가장 작은 seq 가 가진 가장 큰 seq 보다 아직 크면 그 앞을 더 읽는다.
  `seq` 는 표 전체의 identity 라 한 방 안에서 2 이상 뛰는 것이 빈틈이 아니다 — 두 seq 의 차이로는 가를 수 없다. 끊긴 동안
  쌓인 수백 건도 이렇게 다 온다. 입력 칸과 초점은 다시 그려지지 않는다(입력이 방 상태와 따로 산다). 과거를 읽는
  중이면 스크롤 자리를 지키고 「새 메시지」 알림을 세운다.
- **앞 메시지 더 보기** — `my_chat_messages(p_before_seq)` 가 이미 있다. 맨 위에 「이전 메시지 더 보기」를 세우고 200건씩 읽는다.
  스크롤 자리를 지킨다.
- **읽음은 본 것까지만** — `mark_chat_read(p_match_id, p_up_to_seq)` 로 바꾼다. 옛 한 칸 서명은 이 배포에서
  남긴다(넓히기 — 떠 있는 옛 앱 · 열린 브라우저 · 롤백이 부른다). 차례는 마이그레이션 → RPC · 캐시 확인 → 앱 배포다 — 새 앱이 먼저 가면 없는 새 서명을 부른다. 걷는 좁히기는 옛 호출이 0 임을 잰 뒤 따로다(G-77). 문서가 보이고
  (`visibilityState === 'visible'`) 상대의 말풍선이 화면에 들어온(IntersectionObserver) 가장 큰 seq 까지만 남긴다. 함수는 그 방에 실제로
  있는 seq 까지만, 그리고 앞으로만(`greatest`) 움직인다. 숨겨진 탭은 부르지 않고, 다시 보이면 그때 잰다. 못 남겼으면
  `online` · 다시 대조 · 다시 보임에 다시 부르고, 보이는 동안 2s → 30s 뒤물림으로 다섯 번까지 스스로 다시 부른다(`read-retry.ts`).

### 다시 대조 — 정상은 채널, 복구는 재조회

- **다시 대조(resync)** = 머리글의 딱지 넷을 다시 세고, 지금 화면이 든 갈래를 다시 읽는다(방이면 메시지와 방 상태, 목록이면
  `router.refresh()`). 부르는 때:
  - 채널이 `SUBSCRIBED` 로 처음 서거나 **다시** 섰을 때(끊긴 동안의 변경). 처음 선 때도 목록을 다시
    그린다 — 서버가 그린 뒤 채널이 서기 전의 변경은 어느 사건으로도 안 온다. 그 다시 그리기는 표지를 실어 활동이 아니다(G-76,
    2026-10-08 리뷰로 고침)
  - 문서가 다시 보일 때(`visibilitychange`) · 네트워크가 돌아올 때(`online`) · bfcache 복귀(`pageshow` persisted)
  - 토큰이 새로 났을 때(`TOKEN_REFRESHED` — 채널 인증도 새로 건다)
- **대체 조회(fallback)** — 채널이 `SUBSCRIBED` 가 아닌 동안만, 문서가 보일 때만, **30초**마다 다시 대조한다. 채널은 지수 뒤물림
  (1s → 2s → … 최대 60s)으로 다시 붙는다. 채널이 서면 대체 조회는 멈춘다. 숨겨진 탭은 조회하지 않는다 — 돌아오면 한 번 대조한다.
- **수치의 근거** — 2초: 운영자의 수용 기준. 30초: 1,000명이 모두 끊겨도 초당 33회 × 문 넷 ≈ 초당 130 RPC 로 지금 Supabase 가
  받는 수준이고, 끊긴 사람이 보는 늦음이 대화로 견딜 만한 끝이다. 60초 상한: Supabase 의 재접속 폭주를 피한다.

### 로컬 · CI

- `npm run db:start` 가 realtime 을 띄운다(지금은 `-x realtime` 으로 뺀다). 로컬에서 비공개 채널과 정책을 잴 수 있게 한다.
- CSP 의 `connect-src` 에 Supabase 의 `wss:` 주소를 연다.

## 하지 않는 것

- 접속 상태 · 타이핑 · 상대 읽음 표시(운영자: 이번 필수 범위 아님). §7.2 는 그대로다.
- Postgres Changes · 원본 표의 `select` 공개 · 채널에 본문 싣기.
- 기능마다 채널 · 폴링 타이머.

## 치르는 값

- Realtime 연결이 사용자 탭마다 하나다. 무료 플랜의 동시 연결 한도(Free 200)가 동시 접속자의 상한이 된다 — 수와 비용은 PR 본문의 추정 표,
  플랜과 운영의 「Allow public access」 끄기는 간극 대장의 줄이 든다.
- 트리거가 쓰기마다 `realtime.messages` 에 줄을 남긴다(Realtime 이 날마다 파티션을 걷는다).
- 이벤트 하나에 읽는 문 하나 이상을 다시 부른다 — 내용을 싣는 방식보다 요청이 많다. 그 대가로 권한 판정이 읽는 문 한 곳에 남는다.
- **사람이 내지 않은 요청은 활동으로 적지 않는다**(2026-10-08 조율자 결정 — G-76 을 닫았다). ADR 0118 의 「미리 받기는 활동이 아니다」와
  같은 결이다. 라이브 층의 목록 다시 그리기(`router.refresh()`)는 짧게 사는 표지 쿠키(`live-redraw`, 5초 · 다시 그리기가 끝나면
  걷는다)를 싣고 화면(`signedInUser`)이 그것을 보면 활동을 건너뛴다. 자동 읽음(`mark_chat_read`)과 딱지 · 방 다시 읽기는 브라우저
  클라이언트로 곧장 불러 관문을 안 지나고, 서비스 워커의 구독 갱신 주소(`/me/push/subscription`)는 관문이 뺀다. 그래서 화면을 열어
  둔 채 자리를 비운 사람이 상대의 메시지 · 대체 조회 때문에 「지금 활동 중」으로 남지 않는다 — `e2e/live.spec.ts` (8) 이 잰다.
  치르는 값: 표지가 사는 몇 초 사이 같은 브라우저에서 사람이 연 화면도 활동에서 빠질 수 있다 — 그 사람의 다음 요청이 다시 적는다
  (늦어야 몇 초, ADR 0092 의 1분 억제보다 작다). 서버 액션(누름)은 관문이 적으므로 빠지지 않는다. 사람이 표지를 손으로 세워 얻는 것은
  제 활동을 숨기는 것뿐이다.

480~610ms 였다 — 받는 쪽은 이 결정 그대로 빠른데, 보낸 사람의 말이 서버 액션 한 번 · 제 말을 읽는 문 한 번이 끝나야 섰고 그동안
칸이 잠겨 글자가 남아 있었다.

- **누르는 순간 흐린 말풍선으로 선다**(`app/me/chat/[matchId]/pending.ts`). 칸은 곧장 비고 잠기지 않는다. 서버 액션은 브라우저가
  하나씩 차례로 보내므로 연달아 보내도 순서가 지켜진다.
- **진짜 말이 자리를 잇는다** — 보낼 때 가진 가장 큰 차례 뒤에 읽혀 온 **내** 말 가운데 본문이 같은 것이 짝이다(진짜 말 하나에
  흐린 말 하나). 맞추는 것은 화면뿐이다 — 읽음 · 스크롤 자리 · 권한 판정은 그대로 진짜 말만 본다. 이 결정의 「채널은 바뀌었다만
  알리고 읽는 문으로 다시 읽는다」는 바뀌지 않는다.
- **못 보내면 걷고 글을 돌려준다** — 한도 · 오류 · 닫힘이면 흐린 말풍선을 걷고, 칸이 비어 있으면 쓰던 글을 되돌리고 앞 판과 같은
  문장을 세운다. 새 글자는 없다(「보내는 중…」 읽는 이름은 걷었다 — 단추가 잠기지 않는다).
- **잰 것**(로컬 dev, 2026-10-08): 누른 뒤 내 화면 29~55ms, 진짜 말로 바뀌기까지 220~366ms, 세 번 연달아 보내도 순서 그대로 · 중복
  없음. 받는 쪽은 그대로다 — 운영 480~610ms(#529). 서버 액션 대신 브라우저에서 곧장 보내 받는 쪽을 더 줄이는 것은 이 덧 밖이다
  (관문 · 활동 적기와 닿는다).
