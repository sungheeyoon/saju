# 입력은 저장하고 명식은 저장하지 않으며, 현재 AI 결과는 생성 자료와 함께 둔다

명식은 `computeSaju(입력, 옵션)`의 결과라 순수 함수의 파생 뷰다. 저장하면 진실이 두 벌이
되고 엔진을 고칠 때 저장된 값이 조용히 어긋나므로, **Person은 입력만 든다** — 생년월일시,
출생지, 성별, 그리고 결과를 가르는 옵션(자시 규칙·시간 기준)까지. 옵션은 설정이 아니라
입력의 일부다. 이미 주소창이 「기본값도 빼지 않고 전부」 싣는 것과 같은 이유이고, 같은 값이다.

AI 결과는 성격이 다르다. 사용자에게 보이는 출력은 모델 호출의 결과이므로 현재 결과가
무엇을 근거로 만들어졌는지 확인할 수 있어야 한다. 그래서 대상별 **현재 Reading**에 출력과
실제 redacted Evidence, prompt, 모델·provider·생성 파라미터를 한 벌로 저장한다. 자기 풀이의
출력은 해석이고, 두 사람 궁합의 출력은 점수와 해석이다.

Reading은 과거 사건을 쌓는 이력 테이블이 아니다. 화면을 다시 여는 것은 현재 값을 읽을
뿐이고 AI를 호출하지 않는다. 사용자가 같은 대상에서 결과 생성 요청을 실행하고 생성과
검사가 성공하면 한 벌 전체를 원자적으로 교체한다. 이전 점수·해석·근거·prompt·모델 설정은
제품에서 보존하거나 UI·AI·엔진이 참조하지 않는다. 실패한 요청은 직전 성공 결과를 바꾸지 않는다.

## Considered Options

- **Reading을 생성할 때마다 새 행으로 쌓는다** — 과거 결과 재현에는 유리하지만 사용자가
  원하지 않는 점수 이력과 버전 선택 문제를 만든다. 채택하지 않았다.
- **점수·해석만 저장하고 근거와 prompt는 현재 코드로 복원한다** — 작지만 지금 보이는
  결과가 실제로 무엇을 입력받아 만들어졌는지 확인할 수 없다. 채택하지 않았다.
- **Evidence만 저장하고 결과는 화면을 열 때마다 다시 생성한다** — 조회만으로 비용과 결과가
  달라진다. 채택하지 않았다.

## Consequences

- `viewedAt`은 현재 결과 생성에 사용되는 **입력**이다. `EVIDENCE_CONTRACT.fortune:
  'current-only'`라 운은 생성 시점의 「지금 도는 칸」만 실린다. 결과 생성 요청이 성공하면 새
  `viewedAt`과 새 결과가 함께 현재 Reading으로 들어간다.
- 현재 두 사람 근거가 무압축 약 91KB여도 조합별로 한 벌만 저장하므로 저장 비용이 해석
  이력 수에 비례해 계속 커지지 않는다.
- 입력이나 엔진·prompt가 바뀌어도 단순 조회는 현재 결과를 바꾸지 않는다. 새 조건을 반영할지는
  사용자의 결과 생성 요청이 결정한다.
- 새 결과가 이전과 다른 점수여도 비교·병합하지 않는다. 예를 들어 76점이 82점으로 교체되면
  현재 값은 82점 하나이고, 76점은 이후 계산이나 설명의 입력으로 쓰지 않는다.
- `Reading.evidence`는 현재 결과 생성 때 모델에 보낸 직렬화 문자열 그대로 둔다. Evidence
  안에는 정확한 출생 원문과 출생지를 넣지 않으며, 대상에 맞는 chart revision id가 원본
  입력과의 연결을 맡는다(ADR 0004·0008).
