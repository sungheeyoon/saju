# 앱을 안 보는 사람에게 새 메시지를 웹 푸시로 알린다 — 본문 없이, 켠 기기에만

> **운영자 결정 2026-10-08**(대화에서) — 「앱을 보고 있지 않은 사용자에게 새 메시지를 알려주는 경로를 하나 완성한다. 제공자는
> 최신 공식 문서·비용·모바일 지원·설정 난도를 조사해 선정하라. 잠금 화면 등에 메시지 본문이나 민감정보를 기본 노출하지 마라.」
> 제공자 선정은 조율자에게 맡겼다(「알아서 선정」). G-26 의 첫 줄(「새 메시지 통보부터」)이 이 길로 선다 — 운영에 켜는 것은
> 설정 · 처리방침 한 줄 뒤다(간극 대장).

## 정한 것

- **제공자는 표준 웹 푸시(Web Push · VAPID)다.** 가입 · 계약 · 건당 요금이 없고, 브라우저 회사의 푸시 서비스(FCM · Mozilla ·
  Apple)가 나른다. 안드로이드 Chrome · 데스크톱 Chrome/Edge/Firefox/Safari 는 그대로, iOS/iPadOS 는 16.4 이상에서 **홈 화면에
  추가한 앱**으로 열었을 때만 된다. 서버는 `web-push`(npm)로 암호화해 보낸다. 견준 것과 근거 · 비용은 PR 본문(조사)이 든다.
- **켜는 것은 사람이다.** 설정의 「새 메시지 알림」 한 줄에서 누름(사용자 제스처)으로 브라우저 권한을 묻고, 받으면 이 기기의 구독을
  서버에 남긴다. 끄면 이 기기의 구독을 지우고 브라우저 구독도 푼다. 권한을 거부한 브라우저에는 「브라우저 설정에서 허용해야 한다」는
  한 줄만 선다. **기본은 꺼짐**이다. 구독은 기기마다 하나이고 계정에 매인다. **계정마다 구독은 10개까지**다 — 넘치면 가장 오래
  안 쓰인 것을 지운다(거절하면 기기를 바꿔 온 정상 사용자가 언젠가 막힌다). 메시지 하나가 만드는 배달 줄의 상한이기도 하다.
- **로그아웃 · 계정 전환** — 로그아웃은 이 기기의 구독을 서버에서 먼저 지운다. 다른 계정이 같은 브라우저에서 켜면 그 endpoint 는 새
  계정으로 옮긴다(endpoint 는 유일하다). 그래서 한 기기가 앞 사람의 메시지 통보를 받지 않는다.
- **무엇을 보이나** — 제목은 서비스명, 본문은 「새 메시지가 왔어요」 한 줄(문구는 승인 대기). **닉네임 · 본문 · 사진을 싣지 않는다**
  — 페이로드에도 없다(푸시 서비스도 못 본다). 실은 것은 이동할 주소(`/me/chat/<matchId>`)와 묶음 표(`tag`)뿐이다.
- **누르면 그 방으로** — 서비스 워커가 열린 창이 있으면 그 창을 앞으로 가져와 그 주소로 옮기고, 없으면 새 창을 연다. 로그인이
  풀렸으면 로그인 뒤 그 방으로 돌아온다(지금의 `next` 흐름).
- **언제 보내나 — 중복 막기**
  - 메시지가 저장되면 DB 가 받는 사람의 구독마다 배달 줄(`push_delivery`)을 **방 하나에 대기 줄 하나**로 남긴다
    (같은 방의 다음 메시지는 대기 줄을 새로 만들지 않는다). 배달 문이 줄을 잡는 순간 받는 사람이 상대의 마지막 메시지까지 이미
    읽었으면 보내지 않고 접는다(`skipped`) — 방이 닫혔거나 구독의 주인이 그 방의 참여자가 아니어도(옮겨 간 endpoint) 같다.
  - 같은 방은 보낸 뒤 **60초** 안에 다시 보내지 않는다(그 사이 메시지는 다음 배달로 묶인다). 브라우저 쪽에서도 `tag` 가 방이라
    알림이 쌓이지 않고 바뀐다. 푸시 서비스에는 `Topic`(방)으로 아직 안 간 것을 바꾼다.
  - **서비스 워커는 푸시마다 알림을 반드시 세운다.** 앱이 그 방을 보이는 채로 열고 있으면 같은 `tag` 로 조용히(`silent`) 세운다 —
    소리 · 진동만 끈다. Safari 는 알림 없이 끝난 푸시(조용한 푸시)를 몇 번 보면 그 사이트의 푸시 권한을 거두고, Chrome · Firefox 도
    `userVisibleOnly` 를 어기면 대신 알림을 세운다. 보고 있는 방의 메시지는 대개 위의 「이미 읽었으면」이 먼저 거른다.
- **어떻게 나르나 — 보내기와 다시 보내기**
  - 배달 줄이 생기면 DB 가 `pg_net` 으로 앱의 배달 문(`POST /api/push/dispatch`, `Authorization: Bearer` 비밀)을 깨운다 — 커밋
    뒤에 나간다. 배달 문은 202 로 먼저 답하고 같은 함수 시간 안에서 보낸다.
  - 배달 문은 기한이 된 대기 줄을 한 번에 50개까지 잠그고(`for update skip locked`) 동시 6개로 보낸다. 송신의 머리는
    `TTL` 3600초(기기에 못 닿은 채로 한 시간 넘게 들고 있지 않는다 — 기본 4주는 쓰지 않는다) · `Urgency: high` ·
    `Topic` = matchId 의 하이픈을 뺀 16진 32글자다.
  - 답 → 닫는 말: `2xx` → 보냈다. `404`/`410` → **그 구독을 지운다**(끄는 칸은 따로 없다 — 배달 줄도 cascade 로 간다).
    그 밖 전부(`429` · `5xx` · 연결 실패 · 10초 시간 초과, 그리고 `400` · `403` · `413`) → 다시 보낸다. `403` 등을 「구독이 끝났다」로
    읽지 않는 것은 그것이 대개 우리 쪽 설정(구독 때와 다른 VAPID 열쇠)이라, 설정 실수 하나가 모든 구독을 지우지 않게 하려는
    것이다. `429` 의 `Retry-After` 는 따르지 않고 배달 줄의 뒤물림이 대신한다.
  - 뒤물림은 실패 뒤 1분 · 5분 · 30분 · 2시간이고, **다섯 번째 실패**에 접는다(`gave_up`). 5분 넘게 `sending` 에 멈춘 줄(배달 문이
    죽었다)은 다시 잡을 때 실패 한 번으로 센다 — 배달 문이 그 줄에서 매번 죽어도 영영 돌지 않는다. 다시 보내려는 줄의 같은 방에
    새 대기 줄이 이미 섰으면 되돌리지 않고 접는다(`skipped`) — 새 줄이 같은 소식을 나른다.
  - **다시 보내기**는 `pg_cron` 이 1분마다, 기한이 된 줄이나 멈춘 줄이 있을 때만 배달 문을 한 번 깨운다(Vercel Hobby 의 크론은
    하루 한 번이라 DB 가 깨운다 — `supabase_wakes_the_recovery_not_vercel` 과 같은 길).
  - Vault 의 주소 · 비밀이 없으면 DB 는 깨우지 않고 조용히 지나간다. VAPID 열쇠가 없는 배포면 배달 문은 보내지 않고 줄마다
    「설정 안 됨」(`unconfigured`)으로 닫는다 — DB 는 시도 수를 올리지 않고 5분 뒤로 미룬다. 잃지 않는다(어댑터).
- **보존** — 배달 줄은 보낸 · 접은 뒤 7일에 걷는다. 구독은 끄거나 · 로그아웃하거나 · 404/410 이거나 · 계정의 10개를 넘쳐 밀려나거나 ·
  탈퇴 처분 때 지운다.

## 하지 않는 것

- 이메일 · 카카오 알림톡 · 앱 스토어 앱(G-26 의 나머지 줄로 남긴다).
- 요청 · 소식의 외부 통보 — 이번은 새 메시지 하나다.
- 잠금 화면 미리보기를 켜는 설정 — 필요하면 별도 결정이다.
- 조용한 푸시(알림 없는 푸시) — 위 「반드시 세운다」.
- 서비스 워커의 화면 캐시 · 오프라인 지원 — 워커는 푸시만 든다(`fetch` 처리기가 없다).

## 치르는 값

- iOS 는 홈 화면에 추가해야 받는다 — 그 안내 문구가 화면에 든다(승인 대기).
- 그 방을 보고 있을 때도 알림 서랍에 조용한 알림이 하나 남을 수 있다(같은 `tag` 라 쌓이지는 않는다) — 권한을 잃는 것보다 낫다.
- 새로 받는 개인정보가 하나 는다 — 기기의 푸시 endpoint 와 열쇠. 처리방침(`/privacy`)에 한 줄이 들어가야 운영에 켤 수 있다
  (문구 · 고지 판 승인 대기, 간극 대장).
- 설정이 잘못되면(`403` 이 이어지면) 배달 줄이 다섯 번 실패하고 접힌다 — 구독은 남으니 설정을 고치면 다음 메시지부터 간다.
- 운영에 켜려면 사람이 VAPID 열쇠 · 배달 비밀을 Vercel 과 Supabase(Vault)에 넣어야 한다 — 절차는 runbook 「웹 푸시를 켠다」.
