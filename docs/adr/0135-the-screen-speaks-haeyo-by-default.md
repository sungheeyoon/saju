# 화면 말투는 해요체가 기본이다

> **운영자 결정 2026-09-29.** 기준은 「사용자가 평소 앱에서 듣는 자연스러운 존댓말인가」(토스 · 쿠팡 라이팅 원칙 참고).
> 「설명 · 도움말 · 빈 화면은 해요체를 기본으로 합니다. 법적 · 금전적 결과, 개인정보 처리, 이용 제한, 삭제 · 보존 및
> 되돌리기 어려운 결과를 정확히 고지하는 문장은 합니다체를 쓸 수 있습니다. 문장 끝만 기계적으로 바꾸지 않고 화면의
> 역할과 뜻을 함께 확인합니다.」 제목 · 버튼 · 상태는 종결어미 변경 대상이 아니고, 오류는 「무슨 일인지 + 무엇을 하면
> 되는지」를 함께 보며, 운영자가 확정한 문구는 자동 변경하지 않는다. 같은 개념의 이름은 통일하되 라벨이 문맥을 이미
> 주면 축약을 허용한다. 한 줄 도움말의 마침표는 일괄 강제하지 않고, 완결된 문장이거나 두 문장 이상일 때 쓴다.

## 잰 것 (2026-09-29, 이 PR 전)

- `CONTEXT.md` §8 은 「앱 대부분은 합쇼체」라 적고 오류 · 404 · 매칭 참여 오류 세 자리만 해요체로 뺐다(2026-09-28).
  마침표는 자리 표(제목 · 라벨 · 버튼 없음 / 설명문 있음)가 정했다.
- 실제 화면은 이미 섞여 있었다 — 맛보기 · 첫 화면 쪽은 해요체, 소식 · 알림 · 설정 쪽은 합쇼체. 같은 사용자가 한 흐름에서
  두 온도를 번갈아 들었다. 받은 요청 띠의 한 줄(「답하면 궁합이 열린다」)은 해라체였고, 거절해도 「답」이라 사실과도 달랐다 — 궁합을 여는 것은 수락이다(`수락하고 궁합 열기`).

## 정한 것

1. **§8 의 말투 규칙을 위 문장과 자리 표로 바꾼다.** 처음 안은 「결제 · 동의 · 탈퇴 · 개인정보 고지만 합니다체」였는데
   범위가 좁아 같은 날 「고지하는 문장」으로 넓혔다. 버튼 규칙(동작명 · `취소` · `작성 그만두기`)과 「~ 중…」은 그대로다.
2. **마침표는 문장이 정한다** — 라벨 · 버튼 · 짧은 상태에는 없고, 한 줄 도움말은 완결 문장이거나 두 문장 이상일 때만.
3. **한 사실 한 표기에 축약 하나를 연다** — `출생 시각` 칸 아래의 `모름` 처럼 라벨이 문맥을 이미 주는 자리.
4. **이번 PR 이 고치는 문구는 운영자가 준 목록뿐이다** — 받은 요청 띠 · 저장한 사람 링크(`저장한 사람 관리`) · 로그인 전
   임시 저장 실패 · 맛보기 두 곳의 안내 줄 · 궁합 맛보기의 점수 안내 · 시각 모름 곁말 · 저장 폼의 첫 화면 안내 · 풀이 목차의
   `작성 중…` · `검토 중…` · 빈 점선 표지(`내 사주 등록하기` · `사주풀이 받기`) · 인연 궁합 소식 넷(완성 · 실패, 이름 있고
   없고). 인연 궁합 실패는 「지금 보이는 글은 그대로」를 걷고 「인연 궁합 화면에서 다시 시도해 주세요」로 말한다 —
   수락 직후 처음 만들어지므로 처음 실패에는 보이는 글이 없다. 같은 함수의 자기 풀이 · 직접 궁합 소식은 합쇼체 그대로다.

## 안 한 것

- **기존 합쇼체 문구를 일괄로 바꾸지 않는다.** 소식 · 설정 · 신고 쪽의 합쇼체는 그대로 두고, 고칠 줄은 운영자에게 따로
  표로 묻는다 — 규칙이 바뀌었다고 에이전트가 문구를 지어 넣지 않는다(`docs/agents/code-rules.md` 「화면 문구」).
- 운영자가 그대로 두기로 한 것: 현관의 「…바로 보여 드려요.」, 선택지 「다른 사람의 사주예요」, 폼의 「모름」, 매칭 참여
  오류의 「확인하고 다시 시도해 주세요」.
