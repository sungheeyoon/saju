# 음력은 계산하지 않고 표를 생성해 커밋한다

한국에서 부모 세대는 생일을 음력으로 아는 경우가 흔하다. 폼이 양력만 받으면 상당수가
음력 날짜를 양력 칸에 그대로 적고, 그러면 **틀린 사주가 나오는데 화면은 아무 말도 하지
않는다.** 경계 31건 골든 스냅샷도 절기 1e-4° 자체 검증도 입력 한 칸에서 무의미해지므로,
음력 입력을 MVP 에 넣는다.

변환은 **런타임 계산이 아니라 생성해 커밋한 표**로 한다. `astronomy-engine` 이 이미
있으니 삭(朔) 시각은 직접 구할 수 있지만, 한국 음력은 그 시각을 **KST 기준 어느 날에
배정하느냐**를 한국천문연구원이 정하고 윤달 배치도 그 규칙을 따른다. 직접 계산하면
경계에서 공식 음력과 어긋난다 — 표준시 이력을 손으로 짜면 1955~60 년에서 반드시
어긋났던 것과 같은 문제이고, 같은 답을 쓴다(`scripts/generate-zone-history.mjs` →
`scripts/generate-lunar-table.mjs`, 1900~2100).

**Person 은 사용자가 넣은 원본 형식과 변환된 양력을 둘 다 든다.** 「음력 1965년 3월
12일(평달)」을 저장해야 사용자가 나중에 자기 입력을 알아보고, 변환표를 고쳤을 때 무엇이
바뀌는지 되짚을 수 있다. `calendarType` 은 여기서 비로소 읽는 곳이 생긴다 —
`computeSaju` 는 여전히 양력만 받고, 변환은 그 앞에서 끝난다.

## Consequences

- `Person.timezone` 은 두지 않는다. 국내 출생만 지원하고 `Asia/Seoul` 이력만 커밋되어
  있어, 필드가 있으면 해외 출생을 받는다는 잘못된 신호가 된다.
- 표 밖(1900 이전·2100 이후)은 변환하지 않고 거절한다. 지어낸 값을 내지 않는다.
- 변환표 자체가 검증 대상이 된다 — 절기·일주 앵커처럼 외부 자료와 대조하는 테스트가
  붙어야 한다.
