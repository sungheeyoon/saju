# G-23 기록

표의 줄: [간극 대장 「공개 출시」의 G-23](../../gaps.md#공개-출시)

표의 「G-23」 줄 메모 칸에 쌓였던 실행 기록이다 — 문장은 그대로 옮겼다(2026-10-05). 줄을 닫으면 이 절도 함께 걷는다.

**정한 것(2026-09-23):** 외부 모의해킹은 결제가 운영에 들어간 뒤 따로 한다. 빗장은 앱 메모리가 아니라 **DB 에서 원자적으로** 센다. **점검표** — ① 운영 의존성 취약점: `npm audit --omit=dev`
가 high 이상 0 이고 CI 가 그것을 잰다 — **닫힘(2026-09-23)**: Next 16.3.1 → 16.3.6(critical 셋 · sharp high)은 `1e1f6c8`, 2026-09-23 값은
운영 46개에 0. CI 차선 `audit`(`npm audit --omit=dev --audit-level=high`)이 **의존성 목록을 바꾼 PR** 의 머지를 막고, 새 advisory 는 main 푸시 ·
하루 한 번의 일정이 잡아 `ci-main-red` 가 「`audit` 만 붉다」고 적는다(ADR 0104). 증거: `ci-plan.test.ts` 「운영 의존성 감사」 · `main-red.test.ts`,
`1e1f6c8` 전 잠금 파일에서 차선 명령이 1 로 끝남. 절차: `docs/ops/runbook/security.md` 「운영 의존성 취약점」 ② 보안 헤더 — **CSP 강제(2026-09-23)**: 한 정책
`Content-Security-Policy` 가 `default-src 'self'` · Supabase 하나에만 연 `connect-src` · `frame-src`/`object-src 'none'` ·
`base-uri`/`form-action 'self'` · `frame-ancestors 'none'` 을 막고, `X-Frame-Options: DENY` · `nosniff` ·
`Permissions-Policy` 가 함께 선다(`next.config.ts`). `Report-Only` 는 걷었다. 운영 화면이 부르는 출처는 브라우저로 재어 전부 제 출처였다(Vercel Analytics
· 툴바 없음). 어긴 자리를 받는 `report-uri` 는 두지 않았다 — 되돌리는 법은 `docs/ops/runbook/deploy.md` 「CSP 가 화면을 막을 때」. 증거: e2e `security-headers.spec.ts`(강제 헤더,
바깥 이미지를 `enforce` 로 막는 것)와 CSP 자동 손잡이 — 익명 spec 은 `anon.ts`, 로그인 · 관문 spec 은 `session.ts` 를 지나 **시험 전부**에서 위반 0, dev 와
운영 빌드 둘 다. **`script-src` · `style-src` 의 `'unsafe-inline'` 을 뺄 것인가 — 정했다(2026-09-24, 운영자): ⓒ 지금은 유지하고, 결제 ·
본인인증(PortOne V2 + KCP)을 샌드박스로 연동한 뒤 nonce 전환을 다시 검토한다** — 아래 출처와 `form-action` 이 그때 재어져야 모양이 정해진다. `next.config.ts` 는
그대로다. 잰 값: ⓐ nonce: 돈다(운영 빌드 e2e 전부 위반 0). 정적 넷(`/` · `/_not-found` · `/auth/denied` · `/me/discovery`)이 전부 동적이 되고 proxy
가 모든 화면 요청에 돈다 — 운영에서 잰 첫 바이트 정적 63ms · 동적 118ms(중앙값), 콜드 1.35초 ⓑ SRI(`experimental.sri`): 정적은 지키나 Next 의 인라인 조각에 해시가 없어
홈만 열어도 위반 4, 화면이 안 선다 — 대안이 못 된다 ⓒ 지금처럼 둔다. PG · 본인인증(PortOne V2 + KCP)은 `cdn.portone.io`(script) ·
`checkout-service.prod.iamport.co`(frame · connect) 외 `connect-src` 넷을 더 연다 — 샌드박스에서 재야 확정. 값과 목록은

시험. **문과 시험이 섰다, 가맹 샌드박스에서 한 번 재면 닫힌다(2026-09-24)**: `POST /api/portone/webhook`(`app/api/portone/webhook/`)이 PortOne V2
의 알림을 받아 ⓐ Standard Webhooks 서명(`webhook-id` · `webhook-timestamp` · `webhook-signature`, 앞뒤 5분 — SDK 없이 `node:crypto`)을
검증하고 ⓑ `Transaction.Paid` 만 다루며 ⓒ 금액은 알림 본문이 아니라 PortOne 결제 단건 조회(`GET /payments/{paymentId}`)에서 받아 상태 `PAID` · 우리 상점 ·
`KRW` 를 본 뒤 ⓓ 결제 번호(`rdo_…`)에서 주문을 되짚어 `approve_reading_order(주문, transactionId, 받은 금액, webhook-id)` 를 부른다 — 금액 대조와 「같은

못 닿으면 503 으로 재전송을 부른다. 켜는 값 셋(`PORTONE_WEBHOOK_SECRET` · `PORTONE_API_SECRET` 비밀, `PORTONE_STORE_ID` 설정)이 없으면 503 이고 판매
스위치는 그대로 꺼져 있다. 증거: 단위 `signature.test.ts`(규격의 공개 시험 벡터 · 본문 한 바이트 · 5분 창 · 빈 비밀) · `settle.test.ts`(금액은 PortOne 에서 · 같은

정할 것 — 거래 번호로 `transactionId` 와 `pgTxId` 중 무엇을 남기나, 환불 번호가 주문 사이에 겹치나. **DB 쪽이 먼저 고쳐졌다(2026-09-24, `20261013090000`)**:
`approve_reading_order` 는 금액이 다르면 던지지 않고 `(refused, null)` 을 돌려줘 거절한 알림이 `payment_event` 에 남는다(전에는 되감겼다). 웹훅은 이 결과를 읽는다. **떠날

알림이 계정과 함께 사라졌다. 이제 거절 알림이 하나라도 있으면 `retention.refused_reading_payment` 에 주문 번호 · 계정 내부 번호 · 제공자 · 가맹점 주문 번호 · 주문 금액 ·
주문 시각 · 거절 알림(번호 · 종류 · 받은 금액 · 받은 시각 · 결과)만 옮겨 마지막 거절 알림부터 5년 둔다 — 이메일 · 주문 열쇠 · 묶음 · 상태는 없다. 같은
크론(`payment-retention-purge`)의 같은 문이 두 표를 함께 지우고, 앱은 못 읽는다. 증거: pgTAP `54_refused_payment_retention`(고치기 전 13 중 9 붉음 —
칸을 하나 더하거나 두 번째 표의 지우기를 빼면 붉다). 법적 범위는 변호사 검토 B-8(`docs/legal/counsel-request.md`). **같은 알림 번호의 재시도는 같은 요청일
