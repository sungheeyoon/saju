## 운영자가 정한 범위 (2026-10-16)

| 자리 | 필요한 동작 | 처리 기준 |
| --- | --- | --- |
| 회원 상세 | 풀이권 추가 지급 | 수량 · 사유 입력. 장애 보상인지 운영 지급인지 기록 |
| 회원 상세 | 지급한 풀이권 회수 | 미사용분만 회수. 유료 구매분 환불과 구분 |
| 회원 상세 | 풀이권 이력 | 구매 · 사용 · 환불 · 운영 지급 · 회수를 한곳에서 확인 |
| 신고 상세 | 조치 없음 · 추가 검토 · 경고 · 이용 정지 | 판단 근거를 남기고 화면에서 바로 처리 |
| 신고 상세 | 대상 회원 열기 | 현재 상태 · 이전 경고 · 처분 이력 확인 |
| 회원 상세 | 이용 정지 해제 | 해제 사유와 실행자 기록 |

- 신고 처리는 목록에서 급한 건 확인 → 신고 당시 근거 확인 → 같은 화면에서 처분 → 반영 결과 확인으로 끝난다. 지금은
  UUID 를 복사해 `review_report` SQL 을 돌린다(`app/ops/reports/[reportId]/page.tsx`, `docs/ops/runbook/moderation.md`).
- 풀이권 보상은 신고 화면에 붙이지 않고 대상 회원을 열어 사유를 이어 지급한다 — 신고 처분과 피해 보상을 따로 정확히 적는다.
- 차례: ① 풀이권 지급 · 회수 · 이력 → ② 신고 처분 → ③ 정지 · 해제.
- **지급 · 회수 · 처분 · 정지 · 해제 모두 사유와 실행자 이력이 남는다**(운영자 2026-10-16).
- 회원 화면의 경고 수는 `public.report` 만 센다 — 탈퇴한 신고자의 `retention.report` 경고는 범위를 밝히고 따로 확인한다(G-110
  결정). 처분 이력도 같은 경계를 지킨다(운영자 2026-10-16).
- 참고(외부 리뷰, 2026-10-16): 제재 화면은 통지 · 소명 · 해제까지 잇는다 — 카카오 비즈니스 운영정책
  <https://kakaobusiness-policy.kakao.com/OPERATIONPOLICY/>.

## 이 범위 밖으로 남긴 것

- 웹훅이 오지 않았거나 처리되지 못한 결제를 찾는 결제 대조 — G-110 ④ 는 웹훅이 온 결제의 이상만 알린다. [G-112](g-112.md) 로 뗐다.
- 탈퇴 대기의 해제 — 런북 「이용 정지와 해제」의 SQL 그대로다(탈퇴의 흐름은 `docs/ops/runbook/erasure.md`).
- 떠난 사람의 신고(`retention.report`)의 처분 — 목록에 서지 않으므로 지금처럼 런북 SQL 이다.
- 기한이 있는 정지 — 해제는 사람이 누른다(정한 것 G-111-8).
- 운영자 권한의 회수 — 지금 절차(`docs/ops/runbook/operators.md`) 그대로다. 화면은 운영자 계정을 정지하지 않는다(정한 것 G-111-10).

## 요구사항 (2026-10-16, 구현 전)

G-110 의 PR 넷(#725 오늘의 숫자 · #726 결제 이상 알림 · #727 주문 · 환불 · #729 회원)이 같은 DB 함수 · 접속기록 동작 목록을
고치는 중이라 **이 절과 아래 「화면 설계」는 요구사항만 적는다** — 마이그레이션 · 문 · 앱 코드는 그 넷이 머지된 뒤다. 그 PR 들의
지금 모양(회원 화면 `/ops/members?q=`, #729 의 ADR · 환불의 확보 → 확정 → 준비 취소, #727 의 ADR)에 맞췄다. ADR 은 구현 PR 이
쓴다(번호가 G-110 과 겹치지 않게).

### 모두에 걸리는 것

- **운영자만 한다.** 화면은 지금 운영 화면과 같은 경계다 — 자료를 청해 거절당하면 404(ADR 0103). 쓰는 문은 `authenticated` 에
  열고 안에서 `is_operator()` 로 닫는다(#727 의 ADR 의 4 와 같은 모양). 운영자가 아니면 `42501` 이고 앱이 `note_operator_denial` 로
  같은 동작 이름을 따로 적는다. **서버 열쇠(`service_role`)에는 열지 않는다** — 열쇠가 새도 풀이권을 나눠 주거나 계정을 세우는
  문이 되지 않게(ADR 0043 의 까닭 그대로).
- **실행자는 부른 사람이다.** 문이 `auth.uid()` 를 실행자로 적는다 — 인자로 받지 않는다(지금 `review_report` 는 운영자 UUID 를
  인자로 받는다). 내부 기록은 운영자 UUID, 화면은 운영자 닉네임이다(G-111-9).
- **사유는 갈래 하나 + 메모.** 갈래는 DB 가 받는 닫힌 목록이고, 메모는 짧은 자유 글(지급 · 회수 · 정지 · 해제 200자, 판단 근거는
  지금처럼 500자)이다. 메모에는 이메일 · 실명 · 연락처를 적지 않는다 — 칸 아래 한 줄로 말한다. 이용자에게는 갈래만 간다.
- **같은 요청은 한 번만 반영한다.** 쓰는 문(지급 · 회수 · 처분 · 정지 · 해제)은 화면이 폼을 열 때 만든 **요청 고유 번호**를 받고,
  DB 가 그 번호에 유일 제약을 건다. 응답이 끊겨 다시 눌러도 두 번째는 첫 번째의 결과를 돌려줄 뿐 새 줄을 만들지 않는다. 같은 번호에
  다른 내용(수량 · 갈래 · 대상)이 오면 거절한다(#727 의 「같은 취소 번호로 다시 눌러도 한 번만」과 같은 모양).
- **이력은 지우지 않는다.** 지급 · 회수 · 정지 · 해제는 덮어쓰지 않고 줄이 쌓인다. 신고 처분만 신고 한 건의 결과를 덮어쓰되(이의
  제기 인정 등, ADR 0107), 덮어쓰기 전 결과도 이력 줄로 남긴다.
- **접속기록에 남는다** — 쓰는 문마다 같은 트랜잭션에 한 줄. 거른 조건 칸에는 **id 만**(계정 · 신고 · 이력 줄) 적는다 — 메모 ·
  판단 근거 · 닉네임은 적지 않는다(반출본은 지울 수 없다, ADR 0105 결정 2). 거절된 시도는 줄과 함께 되감기고 거절 기록이 따로 남는다.
- **경고 · 처분의 경계는 G-110 그대로다** — 회원 화면이 세는 경고 · 처분 이력은 지금 계정의 신고(`public.report`)뿐이다. 신고한
  사람이 떠나 옮겨진 경고(`retention.report`)는 화면이 읽지 않고, 「탈퇴한 신고자의 분리 보관 경고는 런북 SQL 로 따로 셉니다」 한 줄이
  늘 선다(#729 의 ADR 의 3). 이 판의 처분 이력 · 신고 상세의 대상 회원 요약 · 「이번이 N회째」 문장도 **「현재 신고 기준」** 을 단다.

### 실행 전 확인 (운영자 규칙 2026-10-16)

**원칙 — 확인 창은 실수를 줄이고, 최종으로 막는 것은 서버 · DB 의 검사다. 둘 다 갖춘다.**

- **붙이는 자리** — 무상 풀이권 지급 · 회수, 경고, 이용 정지 · 해제, 신고 처분과 그 변경(「처분 바꾸기」). 환불의 세 걸음은 #727 이
  같은 규칙으로 구현한다. **조회 · 찾기 · 거르기 · 화면 이동에는 붙이지 않는다.**
- **창은 지금 것 한 벌** — `app/ui/confirm-dialog.tsx` 의 확인 창(ADR 0166)을 그대로 쓴다. 새 창 모양을 만들지 않는다.
- **창이 보이는 것** — ① 대상 회원: 닉네임 + 계정 id 앞 8자(닉네임이 비슷한 다른 사람과 가르게) ② 수량 또는 처분(「무상 풀이권 3장」 ·
  「경고 → 이용 정지 결정」처럼 바뀌기 전 → 뒤) ③ 사유 갈래(와 메모 첫 줄) ④ 실행 결과(이용자에게 무엇이 가고 무엇이 닫히는가 —
  「대화방이 닫히고 모든 이용이 막힙니다」 · 「이용자에게 수량과 사유가 안내됩니다」 · 「현금 환불 대상이 아닙니다」).
- **단추는 구체적인 실행명** — 「3장 지급」 · 「3장 회수」 · 「이용 정지」 · 「정지 해제」 · 「경고」 · 「경고로 바꾸기」 · 「조치 없음으로
  바꾸기」. 「확인」 · 「예」는 쓰지 않는다. 닫는 쪽은 「취소」.
- **창을 연 순간의 값을 고정해 낸다** — 창을 열 때 폼의 값(대상 · 수량 · 처분 · 사유 · 메모 · 읽은 버전 · 요청 고유 번호)을 한 묶음으로
  얼리고, 창이 그 묶음을 보이고, 실행 단추가 **그 묶음 그대로** 서버에 낸다. 창이 떠 있는 동안 뒤 폼이 바뀌어도 낸 값은 창에 보인 값이다.
- **처리 중 · 실패 · 성공** — 누르면 단추를 잠그고 「처리 중…」(두 번 눌러도 한 번). 실패하면 창을 닫고 폼의 입력을 그대로 두며 실패 줄을
  보인다. 성공하면 서버에서 **다시 읽은 실제 반영 결과**(새 잔액 · 새 상태 · 새 처분과 실행자 · 시각)를 보인다 — 화면이 셈한 값이 아니라.
- **서버 · DB 가 다시 검사한다** — 운영자 권한 · 대상의 지금 상태(이용 중인가 · 운영자 계정인가) · 잔액(회수할 수 있는 수) · 처리 버전 ·
  요청 고유 번호(같은 요청은 한 번만). 창에 보인 값과 지금 DB 가 다르면 거절하고 화면이 지금 값을 다시 그린다.
- **응답이 끊기면** — 같은 요청 고유 번호로 결과를 묻거나 같은 번호로 다시 낸다. 두 번째는 첫 번째의 결과를 돌려줄 뿐이다.
- **SQL 로 할 때** — 확인 창은 SQL 을 지켜 주지 못한다. 런북 `docs/ops/runbook/moderation.md` 「SQL 실행 전 확인」(대상 select →
  검사가 든 한 블록 → 사유 · 실행자)을 밟는다.

### ① 풀이권 지급 · 회수 · 이력 — 회원 상세

자리는 회원 화면(`/ops/members?q=<계정 id>`, #729)의 찾은 결과다. 다른 화면에서 회원을 열 때도 이 주소로 간다 — 계정 id 로 찾으면
한 명이라 새 주소를 세우지 않는다. 지급 · 회수의 수량은 「장」, 실제 풀이에 쓴 것은 「회」로 부른다.

#### 출처 셋 — 지금 있는 것을 그대로 쓴다

풀이권의 출처는 셋이다 — **가입 무료**(`free`) · **운영 무상 지급**(`grant`) · **유료 구매**(`bundle`). 넷째 `outside`(몫 밖 — 지운
대상의 시도로 셈이 되돌려 준 자리, ADR 0106)는 출처가 아니라 어느 몫에도 안 든 쓰임이다. 지금 코드가 이미 가르는 것(2026-10-16
조율자 확인, 마이그레이션 `20261011090000` 으로 다시 봤다):

- 쓰임 장부 `reading_credit_use.share` 가 줄마다 `free` · `grant` · `bundle` · `outside` 를 들고, `bundle` 이면 묶음 id 를 함께 든다
  (`bundle_share_names_the_bundle`).
- 쓰는 순서는 `pick_reading_credit_share` 의 무료 → 운영 지급 → 산 때가 이른 묶음이다. **바꾸지 않는다.**
- 실패한 풀이(실패 · 유효시간 넘김 · 요청 거절 · 만료)는 그 쓰임 줄이 `released` 가 되어 **그 출처의 자리**가 돌아온다 — 출처별 「살아 있는
  쓰임 수」에서 빠지기 때문이다. 줄의 `share` 는 바뀌지 않는다.
- **환불 셈은 묶음만 센다** — `refund_reading_order` 는 그 주문의 묶음에 매인 쓰임(`bundle_id = 묶음`)만 세고, 환불 셈의 입력
  (`operator_reading_refund_basis`)도 묶음별이다. 무료 · 운영 지급 쓰임은 셈에 들어갈 길이 없다(확인함). 이 판도 그대로 둔다.
- **없는 것** — 운영 지급은 `reading_credit_grant.extra` 숫자 하나(계정당 한 줄)뿐이라 지급 · 회수 이력이 없다. 아래 지급 장부가 그 자리를 채운다.

**회원 상세의 풀이권 칸은 출처별 표로 바꾼다** — 2026-10-17 에 먼저 섰다(마이그레이션 `20261214080000`, ADR 0185 추기): 맨 위의
잔액은 본인 화면과 같은 셈(`reading_credits_for`)이고 출처별 받은 · 사용 · 남은과 예약 중 · 환불 확보 중은 장부다. 지급 장부가 서면
운영 지급의 받은 수를 그 합으로 잇는다.

| 출처 | 받은 수 | 사용(확정) | 예약 중 | 남은 수 |
| --- | --- | --- | --- | --- |
| 가입 무료 | 한도(`reading_credit_limit()`) | `free` 확정 | `free` 예약 | 받은 − 사용 − 예약 |
| 운영 무상 지급 | 지급 합 − 회수 합 | `grant` 확정 | `grant` 예약 | 받은 − 사용 − 예약 (= 회수할 수 있는 수) |
| 유료 구매 | 묶음의 산 수 − 환불로 걷은 수 | `bundle` 확정 | `bundle` 예약 | 받은 − 사용 − 예약 − 환불 확보 중 |
| **전체 잔액** | | | | 셋의 합 — 이용자 화면의 잔액과 같아야 한다 |

- 몫 밖(`outside`) 쓰임이 있으면 표 아래 한 줄 「몫 밖 N회(지운 대상의 풀이)」.
- 유료 구매 줄 아래 주문 번호마다 주문 · 환불 화면(`/ops/orders?order=`)으로 가는 링크. 금액은 거기서만(G-111-5).

#### 지급 장부 — `extra` 와의 관계

- 줄마다 한 건인 지급 장부(지급 · 회수, 위 「남는 칸」)를 세운다. **`reading_credit_grant.extra` 는 장부의 합이 된다** — 지급 · 회수 문이
  장부 줄과 `extra` 를 같은 트랜잭션에서 함께 고친다(`extra = Σ지급 − Σ회수`, 0 이면 행을 지운다 — 지금 표의 `extra > 0` 규칙 그대로).
  그러면 한도를 읽는 자리(`reading_credit_shares`)와 실시간 갱신 트리거(ADR 0155)는 손대지 않는다. 장부의 합과 `extra` 가 같은지는
  pgTAP 과 런북의 대조 질의가 잰다. (장부만 두고 `extra` 를 걷어 `reading_credit_shares` 가 합을 읽게 하는 것도 되지만, 트리거 · 셈의
  자리를 옮기므로 구현 PR 이 고른다.)
- **옮김** — 지금 `extra` 가 있는 계정마다 「기록 이전」 지급 한 줄(수량 = `extra`, 갈래 `operator`, 메모 = 지금 `note`, 실행자 · 관련 신고
  비움, 시각 = `granted_at`, 요청 고유 번호 = 옮김 표지)을 만든다. 옮긴 뒤 장부 합 = `extra` 를 마이그레이션이 확인한다. 옮긴 줄의 이미 쓴
  몫은 쓰임 장부에 그대로 있으므로 회수할 수 있는 수가 맞게 나온다.
- 유료 구매분의 기준은 지금 그대로 주문 · 결제 · 환불 장부(`reading_order` · `reading_bundle` · `reading_order_refund`)다. 지급 장부는
  유료 구매분을 들지 않는다.

#### 사용분과 보상 — 이번 범위에는 복구 단추가 없다 (운영자 결정 2026-10-16)

- **실패한 풀이의 자동 반환은 그대로다** — 실패 · 유효시간 넘김 · 요청 거절 · 만료는 쓰임 줄이 `released` 가 되어 같은 출처로 자리가 돌아온다.
  운영자가 따로 누를 것이 없다.
- **정상 완료됐지만 제공 내용에 문제가 있는 유료 풀이는 지금의 환불 절차로** — 주문 화면(`/ops/orders?order=`, #727)과 런북의 `failure`
  환불(쓴 회차라도 돌려준다, ADR 0148)이다. 회원 화면에 따로 복구 단추를 두지 않는다.
- **추가 보상은 별도의 무상 풀이권 지급으로 기록한다** — 위 「무상 풀이권 지급」(사유 `outage`) 한 건이다.
- **유료분 반환을 환불 불가 무상 지급으로 대신하지 않는다** — 유료 풀이에 문제가 있으면 돈으로 돌려주는 길(환불)이 기준이고, 무상 지급은
  그 위에 더하는 보상일 뿐이다.

#### 다음 — 원래 출처로 사용분을 되살리기 (후속 ADR)

이번 범위 밖이다. 정상 완료된 사용분을 원래 출처(`share` · `bundle_id`)로 되살리는 기능은 **출처 · 잔액 · 환불 수량을 함께 되돌리는**
후속 ADR 로 남긴다. 그때 볼 것:

- 잔액은 성공한 시도를 센다(ADR 0021) — 쓰임 장부는 셈의 입력이 아니다(런북 「장부가 셈과 맞는가」). 확정 쓰임 줄만 `released` 로
  바꾸면 **잔액이 돌아오지 않고** 장부와 셈이 갈린다. 시도를 지우거나 상태를 바꾸는 것은 ADR 0043 이 막은 길이다 — 셈이 「되살린
  시도」를 빼는 표지와 장부 줄의 되돌림을 한 트랜잭션에서 해야 한다.
- 유료 묶음의 사용분을 되살리면 환불 셈(묶음별 안 쓴 수)이 그만큼 늘어난다 — 환불 수량과 함께 맞물려야 한다.
- 이미 `released` 인 줄은 받지 않고, 같은 줄을 두 번 되살리지 못하며, 사유 · 실행자 · 요청 고유 번호를 남긴다.
- 그때 접속기록 동작 `credits.restore`(거른 조건 칸 `user=<id>` · 쓰임 줄 id)를 더한다.

#### 이력 · 검증

- 쓰는 순서는 지금 그대로다 — 무료 → 운영 지급 → 산 때가 이른 묶음(ADR 0106). 그래서 「지급분에서 쓴 것」은 장부의 `grant` 몫이다.
- 구현 때 pgTAP 로 잠근다 — 무상분 회수가 유료 잔액(묶음별 남은 수)과 환불 셈에 영향이 없다 · 실패 반환이 원래 출처를
  유지한다(`share` · `bundle_id` 불변) · 회수와 사용(풀이 시작 · 인연 요청)이 동시에 와도
  남은 수를 넘지 않는다(같은 계정 자물쇠) · 같은 요청 고유 번호는 한 줄 · 장부 합 = `extra` · 출처별 남은 수의 합 = 이용자 잔액.
- **사용 줄은 차감인 것만 「−1장」이다**(증감은 「장」, 「회」는 풀이 횟수에만 — 2026-10-17 구현 때 고쳤다). 확정은 「−1장 · 풀이 사용」, 예약은 부호 없이 「예약 중」(차감 아님), 풀림(실패 · 유효시간 넘김 · 요청
  거절 · 만료)은 「반환 · 차감 없음」으로 적고 수에 부호를 달지 않는다.
- 이력의 사용 줄은 **무엇을 풀었는지 적지 않는다** — 날짜 · 몫 · 상태만(풀이 대상 · 출생정보는 회원 화면의 경계 밖, #729 의 ADR 의 2).
- 구매 · 환불 줄은 수량과 주문 번호 링크만, 금액은 주문 화면(G-111-5).
- 지급 · 회수로 바뀐 잔액은 이용자 화면에 곧 선다 — 풀이권 표 셋의 변화가 이미 그 계정의 `credits` 갈래로 간다(ADR 0155).

골라 `reviewed_at` · `reviewed_by` · 결과 · 근거 · 제재 대상을 그대로 새 값으로 바꾸고, 앞 결과를 어디에도 남기지 않는다 — 두

유지), 이용 정지 결정에서 다른 결과로 바꿔도 **계정 정지는 풀리지 않는다**(정지는 결과가 `suspension` 일 때 거는 것만 있다).
**정지가 남는 것은 이 판도 그대로 둔다 — 고칠 결함이 아니다.** 처분을 바꿔도 자동으로 해제하지 않고, 남은 정지를 반영 결과에
보이며, 해제는 ③ 의 회원 화면에서 사유 · 실행자와 함께 따로 한다(해제가 제 이력 줄을 갖게). 고치는 것은 덮어쓰기와 앞 결과가
안 남는 것(아래 버전 검사 · 이력 줄)뿐이다. 지금 운영의 런북에도 이 한 줄을 경고로 두었다(`docs/ops/runbook/moderation.md`
「신고와 차단」).

| 정지 | **신고와 무관한 정지만** — 신고로 정지하는 것은 ② 의 처분이다(기록과 정지가 함께). 이용 중인 계정만, 운영자 계정은 거절(G-111-10). 갈래 `policy`(운영정책 위반) · `payment`(결제 부정) · `eligibility`(이용 자격 — 만 19세 미만 정황 등) · `other`. 메모 필수. 이용자에게는 정지 안내에 사유 갈래와 소명 경로(고객 문의 이메일)를 보인다(G-111-8) | 계정 · 바뀌기 전 · 뒤 상태 · 갈래 · 메모 · 관련 신고 · 요청 고유 번호 · 실행자 · 시각 |
| 해제 | 이용 정지인 계정만. 갈래 `appeal`(소명 인정) · `mistake`(잘못 정지) · `other`. 메모 필수. 「이용 정지 결정」 신고 기록은 그대로 남는다 | 같은 칸 |
| 처분 이력 | 신고 처분(경고 · 이용 정지 결정 — 지금 「경고 이력」 칸)과 계정 상태 이력(정지 · 해제)을 한 목록에 | 읽기 — 접속기록 한 줄 |

- **계정 상태를 바꾸는 길은 공통 처리 함수 하나다.** 화면의 문 · `review_report` 의 정지 · 런북의 정지 · 해제가 모두 사유 갈래 · 메모 ·
  실행자를 받는 같은 함수를 부른다. 런북의 `update public.app_user set status …` 는 그 함수 호출로 바꾼다(실행자는 운영자 UUID 인자,
  break-glass 대장 번호를 메모에).
- **트리거는 안전망이다.** `app_user.status` 가 바뀔 때마다 계정 상태 이력 한 줄을 적는다 — 공통 함수를 거치지 않은 변경(직접
  UPDATE)은 실행자 · 사유가 빈 줄로 남고, 화면은 그 줄에 「실행자 · 사유 없음」 딱지를 달며, 장애 알림 길로 한 줄을 보낸다. 탈퇴
  흐름의 변경은 제 갈래로 적어 알림을 보내지 않는다 — 이용자의 탈퇴 신청은 `deletion_request`, 운영자의 탈퇴 대기 해제는 `deletion_withdrawn`(이용자 스스로 취소하는 길은 없다).

#### ③ 이 남긴 것 (2026-10-17)

- **정지된 이용자의 안내**(G-111-8) — **섰다**(2026-10-17, ADR 0190). 운영자가 본문 문구(후보 C 이용제한형)와 갈래 낱말을 확정했다 —
  제목 「이용이 제한된 계정이에요」, 본문 「{닉네임} 님은 {갈래} 사유로 이용제한 중이에요. 저장된 자료는 그대로 있어요. 이의가 있으면 {고객 문의 이메일}으로 소명해 주세요.」(대장
  `all-03` — 조사 · 띄어 쓰기 · 갈래 낱말 둘 · 제목은 같은 날 PR #740 의 물음에 답한 것). 본인의 문 `my_suspension` 이 지금 정지인 사람에게만 닉네임과 갈래를 내고(메모 · 실행자 · 관련 신고는 안 냄), 갈래가 없는
  정지는 갈래 구를 빼고 선다. **신고로 정지된 사람(갈래 `report`)도 같은 안내다.** 운영 화면의 「이용 정지」는 내부 낱말로
  그대로다. 회원 화면의 확인창이 이용자 안내를 약속하게
  할지는 따로다(운영 화면 문구).
- **`operator_member_warnings` 걷기** — 화면은 더는 안 부른다. 지금 운영의 앱이 부르므로 앱이 운영에 든 뒤의 마이그레이션이 걷는다.
- **정지된 이용자의 탈퇴 신청** — **정했다 · 섰다**(R-1, 운영자 결정 2026-10-17, ADR 0190). 화면은 그대로 막고(`request_account_deletion` 의
  `42501`), 고객 문의로 받아 운영자가 본인 확인 뒤 공통 함수로 정지 → 탈퇴 대기(갈래 `deletion_request`)로 옮긴다. 그 해제는 정지로
  돌아간다. 절차는 `docs/ops/runbook/erasure.md` 「정지된 계정의 탈퇴 요청」.

### 데이터 모양 — 구현 때 정할 것 (스케치)

- **지급 · 회수 장부** — 위 ① 「지급 장부 — `extra` 와의 관계」. 줄이 쌓이는 표(계정 · `grant`/`revoke` · 수량 · 갈래 · 메모 · 관련
  신고 · 요청 고유 번호(유일) · 실행자 · 시각)를 세우고 `extra` 는 그 합이 된다. 떠난 계정의 이 줄을 함께 지울지 분리 보관할지는 그때 정한다.
- **처분 문** — `review_report` 를 감싸는 운영자 문(실행자 = `auth.uid()`, 읽은 버전 · 요청 고유 번호를 받는다). 신고 두 표에 처리
  버전 칸, 앞 결과를 남길 이력 표. 런북의 `review_report` 호출도 버전을 받게 할지(받지 않으면 「지금 것을 덮어쓴다」를 명시)는 구현 때.
- **계정 상태 이력** — 공통 처리 함수 + 트리거(위 ③). 문은 같은 트랜잭션의 설정 값으로 갈래 · 메모 · 실행자를 건넨다.
- **이력 읽기** — 회원 화면의 문이 다섯 갈래(구매 · 사용 · 환불 · 지급 · 회수)를 줄마다 출처 · 증감 사유와 함께 한 목록으로
  내준다. 사용 줄이 많을 수 있어 30줄씩. 출처별 표(받은 · 사용 · 예약 중 · 남은)도 같은 문이 낸다.
- **알림** — 지급 알림은 `notify_ops` 의 새 갈래(계정 id · 수량 · 갈래만). 이용자 알림은 앱 안 소식의 새 갈래 둘(지급 · 회수) — 문구는
  구현 PR 이 표로 묻는다.
- **시험** — pgTAP: 운영자만 · 같은 요청 고유 번호는 한 줄 · 회수가 지급분의 안 쓴 것을 넘지 못함 · 회수와 풀이 시작이 마지막 한 장을
  다툴 때 한쪽만 · 산 몫은 회수로 줄지 않음 · 버전이 다르면 처분 거절 · 처분과 정지가 한 트랜잭션 · 직접 UPDATE 가 빈 실행자 줄을
  남김 · 접속기록 줄 · 거절의 되감김. 화면은 단위 시험(갈래 · 셈)과 그림.

## 화면 설계 (2026-10-16)

시안 그림(390 · 1280)은 저장소 밖에 두었다 — 경로는 PR 본문. 문구는 운영자 전용 설명(`/ops/**`, ADR 0103)이고 이용자에게 가는
글자(지급 · 회수 · 정지 안내)는 구현 PR 이 표로 묻는다.

### 회원 상세 (`/ops/members?q=<계정 id>`)

차례: 계정 → 풀이권 → 풀이권 이력 → 처분 이력.

- **계정 칸** — 닉네임 · 상태 딱지 · 계정 id(지금 그대로). 상태에 따라 단추 하나: 이용 중이면 「이용 정지」(붉은 글자 단추),
  이용 정지면 「정지 해제」. 탈퇴 대기면 단추 없이 「탈퇴 대기 — 해제는 런북」 한 줄. 운영자 계정이면 정지 단추 없이 「운영자 계정」 딱지.
  - 누르면 칸 안에 폼이 펼쳐진다 — 사유(갈래 고르기) · 메모(필수, 200자) · 관련 신고(신고에서 넘어왔을 때만, 딱지) · 실행 단추.
  - 확인 창(위 「실행 전 확인」): 제목 **「이용 정지할까요?」**, 본문 넷 — 대상 「<닉네임> · 3f2a9c1e」 · 처분 「이용 중 → 이용 정지」
    · 사유 「결제 부정 — <메모 첫 줄>」 · 결과 「대화방이 닫히고 모든 이용이 막힙니다. 이용자에게 사유 갈래와 소명 경로가 안내됩니다.」
    단추 「이용 정지」(위험) · 「취소」. 해제는 제목 **「정지를 풀까요?」**, 처분 「이용 정지 → 이용 중」, 결과 「닫힌 대화방은 다시 열리지
    않습니다.」(방의 닫힘은 상태라 해제가 되살리지 않는 것으로 읽힌다 — ADR 0091, 구현 때 재어 문구를 맞춘다) 단추 「정지 해제」 · 「취소」.
  - 결과: 상태 딱지가 바뀌고 칸 아래 완료 줄 「이용 정지했습니다」, 처분 이력 맨 위에 새 줄이 강조되어 선다.
- **풀이권 칸** — **출처별 표**(① 의 표): 줄 셋(가입 무료 · 무상 지급 · 유료 구매) × 칸 넷(받은 · 사용 · 예약 중 · 남은)과 맨 아래
  「전체 잔액」. 무상 지급 줄에 「현금 환불 대상 아님」 딱지, 유료 구매 줄 아래 주문 번호 링크(주문 · 환불 화면). 폰에서는 출처마다
  한 덩어리(제목 + 넷)로 쌓는다. 단추 둘: 「무상 풀이권 지급」(주 단추) · 「무상 지급분 회수」(보조). 회수할 것이 0 이면 회수 단추를
  잠그고 곁에 「회수할 무상 지급분이 없습니다」(예약 중이 있으면 「예약 중 N장은 풀린 뒤 회수」). 탈퇴 대기 계정이면 지급 단추를
  잠그고 곁에 「탈퇴 대기 계정이라 지급할 수 없습니다.」(DB 의 거절과 같은 말, R-7 · 2026-10-17).
  - **지급 폼** — 수량(1 ~ 10장, 고르기) · 사유(「장애 보상」 · 「운영 지급」 마디 둘) · 메모(필수, 「이용자에게는 보이지 않습니다」) ·
    관련 신고 딱지(신고에서 왔을 때). 폼 위 한 줄 「무상 지급분은 현금 환불 대상이 아닙니다.」 단추는 수를 말한다 — 「3장 지급」.
    누르는 동안 단추를 잠근다. 확인 창 제목 **「무상 풀이권을 지급할까요?」**, 본문 넷 — 대상 「<닉네임> · 3f2a9c1e」 · 수량 「무상
    풀이권 3장 (잔액 5회 → 8회)」 · 사유 「장애 보상 — <메모 첫 줄>」 · 결과 「현금 환불 대상이 아닙니다. 이용자에게 수량과 사유가
    안내됩니다.」 단추 「3장 지급」 · 「취소」.
  - **회수 폼** — 수량(1 ~ 회수할 수 있는 수) · 사유(「잘못 지급」 · 「중복 지급」 · 「기타」) · 메모(필수). 폼 위 한 줄 「무상 지급분만
    회수합니다. 구매분 환불은 주문 화면에서.」(주문 화면 링크). 확인 창 제목 **「무상 지급분을 회수할까요?」**, 본문 — 대상 「<닉네임> · 3f2a9c1e」 · 수량
    「무상 지급분 2장 (회수할 수 있는 5장 → 3장)」 · 사유 「잘못 지급 — <메모 첫 줄>」 · 결과 「이용자에게 수량과 사유가 안내됩니다.」
    단추 「2장 회수」(위험) · 「취소」.
  - 결과: 수가 바뀌고 완료 줄 「지급했습니다」, 이력 맨 위에 새 줄. 끊겼다 다시 눌러 같은 요청이면 「이미 지급했습니다」로 같은 결과를 보인다.
  - 실패: 폼 아래 실패 줄 — 「회수할 수 있는 지급분보다 많습니다.」(그 사이 이용자가 썼을 때) · 「지급하지 못했습니다. 다시 시도해
    주세요.」. 운영자가 아니면 404.
- **풀이권 이력 칸** — 거르기 마디 넷: 「전체」 · 「구매 · 환불」 · 「지급 · 회수」 · 「사용」. 줄마다 시각 · 종류 딱지 · **출처 딱지**
  (가입 무료 · 무상 지급 · 유료 구매) · 수(지급 +3장 · 회수 −1장 · 구매 +5장 · 사용 −1장, 반환 · 예약은 부호 없이) · 증감 사유와
  내용(주문 번호 링크 · 사유 · 메모) · 실행자(지급 · 회수 · 환불만).
  30줄씩, 아래 「더 보기」. 빈 상태 「풀이권 이력이 없습니다.」 · 실패 「이력을 읽지 못했습니다.」(다시 시도).
- **처분 이력 칸** — 지금 「경고 이력」 칸의 자리. 제목 곁 「현재 신고 기준 최근 12개월 경고 N회」, 아래 분리 보관 한 줄(그대로).
  줄마다 시각 · 종류(경고 · 이용 정지 결정 · 이용 정지 · 정지 해제) · 갈래 · 메모(정지 · 해제만) · 실행자 · 「신고 내용 보기」(신고에서
  온 줄만). 실행자가 빈 줄은 「실행자 · 사유 없음」 딱지. 빈 상태 「현재 신고와 계정에 적힌 처분이 없습니다.」.

### 신고 상세 (`/ops/reports/[reportId]`)

넓은 화면은 두 열 — 왼쪽 근거(신고 칸 · 신고 당시 대화), 오른쪽 처분(대상 회원 요약 · 처분 폼, 스크롤해도 붙어 선다). 폰은 신고 →
근거 → 대상 회원 → 처분 차례로 한 열. 머리의 신고 id 복사 · 검토 문 안내 줄은 걷는다.

- **대상 회원 요약** — 신고받은 계정: 닉네임 · 지금 상태 · 「현재 신고 기준 최근 12개월 경고 N회」 · 처분 이력 최근 셋 · 「회원
  열기」(신고 id 를 들고 간다). 신고한 계정은 닉네임 · 상태 · 「회원 열기」 한 줄. 분리 보관 한 줄.
- **처분 폼**(처리 필요일 때, 「처분 바꾸기」를 눌렀을 때)
  - 결과 넷을 고르는 칸(조치 없음 · 추가 확인 필요 · 경고 · 이용 정지 결정)
  - 경고 · 이용 정지 결정을 고르면 제재 대상 마디 둘(신고받은 계정 · 신고한 계정, 기본은 앞의 것). 경고면 갈래 고르기(기본 = 신고
    사유)와 「현재 신고 기준 이번이 N회째 경고입니다」 — 3회째부터 「이용 정지 결정을 검토하세요.」
  - 판단 근거(필수, 500자, 남은 글자 수, 칸 아래 「이메일 · 실명 · 연락처는 적지 않습니다.」)
  - 단추는 결과를 말한다 — 「조치 없음으로 처리」 · 「추가 확인으로 남기기」 · 「경고」 · 「이용 정지」.
  - 확인 창은 경고 · 이용 정지 결정과 **처분 바꾸기 전부**에(처음 적는 조치 없음 · 추가 확인 필요에는 없다). 본문 넷 — 대상 「<닉네임> ·
    앞 8자 · 신고받은 계정」 · 처분 「처리 필요 → 경고(괴롭힘이나 위협)」 · 사유 「<판단 근거 첫 줄>」 · 결과(경고: 「이용자에게 갈래와
    안내번호가 갑니다.」 / 정지: 「대화방이 닫히고 모든 이용이 막힙니다.」). 단추는 「경고」 · 「이용 정지」(위험), 바꿀 때는
    「경고로 바꾸기」 · 「조치 없음으로 바꾸기」 · 「이용 정지 결정으로 바꾸기」.
- **반영 결과**(처리한 뒤 · 이미 처리된 신고) — 처분 칸이 결과로 바뀐다: 「처리 완료 · 경고」 · 안내번호 · 제재 대상과 그 계정의
  **지금 상태** · 이용자 확인(확인 전 / 시각) · 판단 근거 · 실행자 · 시각. 단추 「다음 신고」(처리 필요 중 급한 순의 다음) · 「회원
  열기」. 이미 처리된 신고에는 「처분 바꾸기」(글자 단추) — 누르면 폼이 다시 서고(지금 버전을 들고), 확인 창이 「이미 적힌 결과를
  바꿉니다.」를 덧붙인다. 정지 결정을 다른 결과로 바꾸면 「계정은 여전히 이용 정지입니다 — 해제는 회원 화면에서.」
- **실패** — 폼 아래 실패 줄: 「탈퇴를 신청한 계정이라 정지할 수 없습니다.」 · 「운영자 계정은 정지할 수 없습니다.」 · 「판단 근거를
  적어 주세요.」 · 「처분을 적지 못했습니다. 다시 시도해 주세요.」. 버전이 달라 거절되면 「다른 운영자가 먼저 처리했습니다.」와 함께
  지금 결과를 다시 그린다.

### 화면 사이의 길

신고 목록 → 신고 상세 → (처분) → 「다음 신고」 또는 「회원 열기」 → 회원 상세 → (지급 · 정지 · 해제) → 처분 이력의 「신고 내용 보기」
→ 신고 상세. 회원 상세의 구매 줄 · 주문 번호 → 주문 화면(`/ops/orders?order=`, #727). 운영 머리의 「회원」은 #729 가 세운다.

## 운영 검토에서 고친 것 (2026-10-17, 운영 `fa0d43a` 읽기 검토)
