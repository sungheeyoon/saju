# G-112 기록

표의 줄: [간극 대장 「공개 출시」의 G-112](../../gaps.md#공개-출시)

## 왜 섰나 (2026-10-16)

G-110 ④(#726)는 **웹훅이 온 결제**의 이상(금액 불일치 · 돈은 들어왔는데 묶음 없음 · 처리 실패)만 알린다. 웹훅이 아예 안 왔거나,
PortOne 이 다섯 번 다시 보내다 그쳤거나, 운영자가 PortOne 콘솔에서 취소하고 장부에 안 적은 결제는 아무도 모른다. 운영자가 G-111 을
정하며 이 대조를 따로 세우게 했다 — **지금 PortOne 연동으로 할 수 있는 것부터**, PG 상품 · 결제수단이 정해진 뒤에야 잇는 것은
「PG 확정 뒤」로 묶는다(PG 는 미정 — KG파이낸셜 · KPN 문의 중). 환불의 PG 취소 대사(#727 의 ADR 가 「다음」으로 남긴 것)도 여기다.

구현은 G-110 의 PR 넷이 머지된 뒤다 — 같은 결제 이상 알림 문 · 접속기록 목록을 고친다.

## 지금 우리 쪽에 있는 것

- **결제 단건 조회** — 웹훅의 문(`app/api/portone/**`)이 `GET /payments/{paymentId}`(머리 `Authorization: PortOne <API Secret>`,
  `storeId`)로 상태 · 상점 · 금액 · 통화를 다시 받고 승인 문(`approve_reading_order`)에 넘긴다. 받는 알림은 `Transaction.Paid` 뿐이다.
- **주문 장부** — `reading_order`(대기 · 승인 · 닫힘 · 일부 환불 · 환불, 결제 번호 `rdo_…` = PortOne 의 `paymentId`) ·
  `reading_order_refund`(PG 취소 번호 `provider_refund_id`) · `payment_event`(알림 한 번만) · #727 의 환불 확보(`reading_refund_hold`,
  진행 중 → 확정 · 준비 취소).
- **알림 길** — `notify_ops` → `ops_alert_url`, #726 이 결제 하나 · 갈래 하나에 하루 한 줄로 연다(`report_payment_trouble`).
- **크론** — Vercel Cron 은 Hobby 라 하루 한 번(±59분)이고, 분 단위는 `pg_cron` 이 앱 주소를 `pg_net` 으로 깨우는 모양이다(풀이
  복구기, ADR 0020). PortOne 비밀 열쇠는 Vercel 에만 있으므로 PortOne 을 부르는 일은 앱 주소가 한다.

## PortOne V2 로 볼 수 있는 것 (2026-10-16 확인)

공식 OpenAPI(<https://developers.portone.io/schema/v2.openapi.json>, 1.16.0)와 가이드에서 읽었다.

| 무엇 | 쓰는 것 | 출처 |
| --- | --- | --- |
| 결제 단건 조회 `GET /payments/{paymentId}` | 상태(`READY` · `PAY_PENDING` · `VIRTUAL_ACCOUNT_ISSUED` · `PAID` · `FAILED` · `PARTIAL_CANCELLED` · `CANCELLED`) · `amount.total` · `amount.cancelled` · `paidAt` · `cancellations[]`(취소 id · `pgCancellationId` · 금액 · 시각) · `webhooks[]` | OpenAPI · <https://developers.portone.io/api/rest-v2/payment> |

| 결제 대용량 조회 `GET /payments-by-cursor` | 만든 때로 고른 기간의 결제 전부, 커서로 이어 받기, 한 번에 1,000 까지 | OpenAPI |

| 결제 취소 `POST /payments/{paymentId}/cancel` | `reason` 필수 · `amount`(빼면 전액) · `currentCancellableAmount`(남은 취소 가능 금액이 같을 때만 취소 — 두 번 취소를 막는 유일한 칸, 멱등 열쇠는 없다) · 응답 `cancellation.status` `REQUESTED` · `SUCCEEDED` · `FAILED` | OpenAPI · <https://developers.portone.io/opi/ko/integration/cancel/v2/readme.md> |

## 요구사항 — 지금 할 수 있는 것

**대조는 PortOne 이 말하는 결제 상태와 우리 주문 장부를 결제 번호(`rdo_…`)로 짝지어 견준다.** 찾은 어긋남은 「대조 결과」로 쌓이고,
운영자에게 알림이 가고, 화면에서 본다. 지금 판매는 닫혀 있고 심사 계정만 결제하므로 건수는 작다.

| 갈래(후보 이름) | PortOne | 우리 장부 | 하는 일 |
| --- | --- | --- | --- |
| `paid-not-approved` — 웹훅을 놓쳤다 | `PAID` | 주문이 대기 | 알림 · 화면. 반영 방법은 물을 것 1 — 제안은 **재전송 API 를 불러 지금 웹훅 길로 반영**(서명 · 금액 대조 · 한 번만이 그대로 선다) |
| `paid-after-close` — 닫힌 주문에 돈 | `PAID` | 주문이 닫힘(실패 · 버림 · 만료) | 알림 · 화면 — 운영자가 PG 에서 돌려준다(#726 의 `paid-without-bundle` 과 같은 일, 웹훅 없이 찾은 것) |
| `amount-differs` — 금액이 다르다 | `amount.total` ≠ 주문 금액 | 아무 상태 | 알림 · 화면 |
| `cancel-not-booked` — PG 에서 취소됐는데 장부에 없다 | `cancellations[]` 의 취소 id 가 `reading_order_refund` 에 없다 · `amount.cancelled` > `refunded_amount` | 주문 승인 · 일부 환불 | 알림 · 화면. 진행 중인 환불 확보가 있으면 그 확보와 짝지어 「장부에 적기」(#727 의 확정)로 바로 가게 한다 — 취소 번호를 채워 |
| `booked-not-cancelled` — 장부에는 환불인데 PG 는 안 취소 | `amount.cancelled` < `refunded_amount` | 일부 환불 · 환불 | 알림 · 화면 — 사람이 PG 콘솔에서 본다 |
| `hold-stale` — 환불 확보가 오래 진행 중 | 취소 없음 | 확보가 진행 중으로 하루 넘음(기준은 구현 때) | 화면만 — 확정하거나 준비 취소한다 |
| `pending-stale` — 오래된 대기 주문 | `READY` · `FAILED` · 없음 | 주문이 대기로 오래 | 화면만 — 닫힘 처리는 지금 길(있는지 구현 때 잰다)에 맡긴다 |

- **어디에 두나** — 셋 다다. ① **크론**: `pg_cron` 이 앱의 대조 주소를 깨운다(제안 1시간마다, 물을 것 2). 주소는 지난 확인 뒤 상태가
  바뀐 결제를 다건 조회(`timestampType = STATUS_CHANGED_AT`, 겹치게 몇 분 앞에서부터)로 받고, 대기 · 진행 중인 확보는 단건 조회로
  확인한다. ② **알림**: #726 의 결제 이상 문에 갈래를 더해 같은 길(결제 하나 · 갈래 하나에 하루 한 줄)로. ③ **화면**: 열린 대조
  결과의 목록과 「다시 확인」(그 결제를 지금 단건 조회) · 갈래에 맞는 다음 걸음(재전송 · 주문 화면 · 환불 확정)으로 가는 길(물을 것 3).
- **결과는 지우지 않는다** — 다시 확인해 맞으면 「맞춰짐」 시각을 적고 목록에서 내려간다. 실행자 · 시각이 남는다.
- **개인정보** — 대조 결과는 결제 번호 · 갈래 · 금액 · 시각만 든다. 계정 · 닉네임 · 이메일은 안 든다(주문 화면이 계정을 안 보이는 것과
  같은 선, #727 의 ADR).
- **접속기록 동작 이름 후보** — `payments.check_list`(목록 읽기) · `payments.recheck`(다시 확인) · `payments.resend`(재전송 부름).
  크론의 대조는 운영자의 열람이 아니라 접속기록에 안 남긴다 — 실행 이력은 크론 이력으로.
- **비밀** — 새 비밀은 없다. 크론 주소를 지키는 값은 지금 크론과 같은 방식(구현 때 `scripts/secret-env.mjs` 의 갈래를 본다).

### 데이터 모양 — 구현 때 정할 것 (스케치)

- 대조 결과 표 — 결제 번호 · 갈래 · PortOne 이 말한 상태 · 금액 · 우리 장부 상태 · 처음 찾은 때 · 마지막 본 때 · 맞춰진 때 · 맞춘
  사람. 같은 결제 · 갈래는 한 줄.
- 지난 확인 시각 — 다음 다건 조회의 `from`.
- 시험 — 대조 셈은 순수 함수로(가짜 PortOne 응답 × 장부 상태 → 갈래) 단위 시험, 표 · 문은 pgTAP. PortOne 실호출은 없다.

## PG 확정 뒤

PG 상품 · 결제수단이 정해져야 잇는 것이다 — 그때 이 절을 요구사항으로 옮긴다.

- **환불의 PG 취소 대사 · 묶기**(#727 의 ADR 「남은 것」) — 「장부에 적기」를 「PG 에서 취소하고 장부에 적기」로: 서버가 취소 API 를
  `amount` · `currentCancellableAmount`(조회의 `amount.total − amount.cancelled`) · `reason` 으로 부르고, 받은 취소 id 로 확보를
  확정한다. 취소는 됐는데 장부 쓰기가 실패한 갈래는 위 `cancel-not-booked` 가 줍는다. **부분 취소를 그 PG 가 받는가**가 먼저다 —
  우리 환불은 묶음의 일부 회차라 부분 취소다. 공식 문서에서 PG 별 부분 취소 목록은 찾지 못했다(2026-10-16) — PG 페이지
  (<https://developers.portone.io/opi/ko/integration/pg/v2/>)에서 확인한다.
- **비동기 취소** — 취소가 `REQUESTED` 로 오고 나중에 `Transaction.CancelPending` → 끝나는 PG 면 확정을 언제 하는지.
- **결제수단별 갈래** — 가상계좌(`VIRTUAL_ACCOUNT_ISSUED` · 입금 기한 · 환불 계좌 필수 · 특약), 휴대폰 소액결제(같은 달 안에만 취소),
  간편결제의 취소 기한. 판매할 수단만 대조 표에 더한다.
- **콘솔 거래대사 · 정산 금액** — 정해진 PG 가 PortOne 거래대사 열둘에 드는지(지금 문의 중인 KG파이낸셜 · KPN 은 그 목록에 이름이
  없다 — 확인 거리). 안 들면 정산 금액(수수료) 대조는 PG 의 정산 파일로 사람이 한다.
- **웹훅 갈래 넓히기** — 취소 · 실패 알림(`Transaction.Cancelled` 등)을 받아 그 결제의 대조를 바로 한 번 돌릴지. 장부를 알림으로
  고치지는 않는다(웹훅 문의 원칙 그대로).

## 운영자에게 물을 것

1. **놓친 결제를 어떻게 반영하나** — ⓐ 크론이 찾으면 재전송 API 를 불러 웹훅 길로 바로 반영(제안) ⓑ 알림만 하고 운영자가 화면에서
   「반영」을 누른다 ⓒ 알림만 하고 운영자가 PortOne 콘솔에서 웹훅을 다시 보낸다.
2. **주기** — 1시간마다(`pg_cron` → 앱 주소, 제안)인지 하루 한 번(Vercel Cron)인지. 웹훅의 다시 보냄이 약 5.7시간까지 이어지므로
   그 사이에 찾은 대기 주문은 「아직 다시 보내는 중일 수 있음」으로 보인다.
3. **화면 자리** — 오늘의 숫자 화면(`/ops/today`, #725)에 「결제 대조 N건」 칸을 두고 새 화면 `/ops/payments` 로 잇는지, 주문 화면
   안에 두는지.
4. **PG 취소를 화면이 부를지** — PG 확정 뒤의 일이지만, 정해지면 「장부에 적기」를 대신할지 곁에 둘지.
