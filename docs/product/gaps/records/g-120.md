## 2026-10-23 — 대장에 올림 (사진 저장소 준비, 나이트 라운드 B)

사진은 지금 `profile_photo.bytes`(bytea)에 산다 — 긴 변 512px · 한 장 512KB(`src/lib/profile/index.ts` 의 `PHOTO_MAX_EDGE` ·
`PHOTO_MAX_BYTES`, `app/me/profile/photo-shrink.ts`, ADR 0040). 운영자가 정한 저장 자리는 **AWS S3 서울**(감사 버킷과 같은 계정 ·
다른 버킷 · 다른 권한)이다. 이 라운드는 DB 의 장부 · 올리기 · 청소기 · 옮기는 도구까지 **꺼진 채로** 넣고, 열람 방식 하나만 결정으로
남긴다. **이미 512px 로 줄여 저장된 사진은 옮겨도 화질이 돌아오지 않는다** — 새로 올리는 사진부터 아래 규격이다.

### 3. 추천 규격 — 하나

| 벌 | 긴 변 | 상한 | 쓰는 자리 | 근거 |
| --- | --- | --- | --- | --- |
| `card` | 480px | 160KB | 아바타 · 편집 칸 · 궤도 지도 | 위 표의 작은 자리 최대(456)를 화소 비 3 에서 덮는다 |
| `large` | 1440px | 720KB | 인연 카드 · 상대 시트 | 넓은 화면(1,110)을 다 덮고, 세로 3:4 이면 1080×1440 — Instagram 의 가로 1080(보조 자료, 확인 전)과 같은 폭. 폰의 화소 비 3 카드(1,800)는 80% 다 |

- **상한 · 두 번째 품질은 잠정이다** — 160KB · 720KB 는 잰 사진 크기가 아니라 셈이다: 두 벌의 합이 서버 액션의 본문 한도(1MB)에서
  여분 64KB 이상을 남기도록(시험이 잰다) 나눴고, 넓이 비(480² : 1440² ≈ 1 : 9)보다 작은 벌에 넉넉히 줬다(작은 사진은 압축이 덜 된다).
  두 번째 품질 0.72 도 잠정 — 처음(0.85)보다 한 단계 낮게만 잡았다. 켜고 나서 실제 거절 수를 보고 고친다
- **형식** — 브라우저가 WebP(품질 0.85)로 굽고, 못 구우면 JPEG(같은 품질)로 물러선다 — 지금의 `shrink` 와 같다. 큰 벌이 상한을 넘으면 품질
  0.72 로 한 번 더 굽고, 그래도 넘으면 거절한다. 두 벌의 상한 합(880KB)은 서버 액션의 본문 한도(Next 기본 1MB,
  `node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/serverActions.md`)에 든다 — 한도를 안 올린다.
- **원본을 안 둔다** — 저장소에 서는 것은 다시 구운 두 벌뿐이다. 다시 구우면 사진의 메타데이터(촬영 위치 등)가 따라오지 않는다.
- **사용자에게 하는 안내는 그대로다** — 한국 서비스가 px 를 안내하지 않고, 우리도 고른 사진을 브라우저가 줄인다(ADR 0040 「작게 만들어
  오세요는 브라우저가 할 수 있는 일을 사람에게 미루는 말」). 장 수는 지금처럼 여섯(Bumble 6 · Hinge 4~6 과 같은 폭, 보조).
- **1800px 이 아닌 까닭** — 바이트가 대략 두 배가 되어 본문 한도를 올려야 하고, 보조 자료의 가장 큰 서비스도 가로 1080 에 멈춘다.

비용의 단가(AWS 공식 가격표, ap-northeast-2, 확인 2026-10-23): S3 Standard 저장 GB-월 $0.025(첫 50TB) · PUT 1,000건 $0.0045 · GET
10,000건 $0.0035 · 인터넷으로 나가는 전송 GB $0.126(첫 10TB, 모든 서비스 합쳐 월 100GB 는 무료) · **같은 리전의 AWS 서비스로 가는 전송은
무료**(<https://aws.amazon.com/s3/pricing/>, 수치는 공개 가격표
<https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonS3/current/ap-northeast-2/index.json>). 올리기 한 번은 PUT 둘이고 하루 한도는
한 사람 스무 번이다(ADR 0125). 인원 · 사진 수의 어림은 하지 않는다.

### 4. 결정으로 남긴 것 — 열람 방식

저장소에 사는 장을 어떻게 내주나. 지금 열쇠 줄은 404 다(`app/me/photo/photo-response.ts`). 서명 주소의 성질은 AWS 문서
(<https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html>, 확인 2026-10-23)에서: 「presigned URLs are bearer tokens
that grant access to those who possess them」 · 만료까지 여러 번 쓸 수 있다 · SDK 로 지으면 7일까지 · 만료 전에 끝내는 길은 지은 자격을
걷는 것(「expires when the credential you used to create it is revoked, deleted, or deactivated」)이다.

| 안 | 차단 반영 지연 | 공유 위험 | ADR 0200 과의 관계 | 비용 | 지연 |
| --- | --- | --- | --- | --- | --- |
| **A. 앱 경로가 중계** — 주소 그대로, 라우트가 `photo_at`(판정 + 열쇠) 뒤 S3 에서 읽어 바이트를 낸다 | **지금과 같다** — 다음 요청부터 막히고, 이미 받은 장은 브라우저 캐시(`max-age=60`)만큼 | **지금과 같다** — 주소는 로그인 쿠키가 있어야 열린다 | 그대로 — 한 장마다 DB 판정 | S3 GET + 바이트가 함수를 지난다(Vercel 함수 시간 · 전송). S3 → 함수 전송은 같은 리전이면 무료일 수 있다 — Vercel `icn1` 함수가 AWS 서울에서 도는지는 확인 전 | DB 1 + S3 1 이 차례로 — 지금보다 S3 한 번 |
| **B. 판정 뒤 짧은 서명 주소로 넘김** — 라우트가 판정하고 302 로 60초짜리 서명 주소 | 새 요청은 바로 막지만 **이미 내준 주소는 만료(60초)까지 열린다** + 브라우저 캐시 | **만료 전 주소를 가진 누구나** 로그인 없이 연다(bearer) | 판정은 한 장마다 남지만 「볼 수 있는 사람」이 「주소를 가진 사람」으로 넓어진다 | S3 GET + 인터넷 전송 $0.126/GB(월 100GB 넘으면). Vercel 은 302 만. CSP `img-src` 에 버킷 주소를 더해야 한다 | 왕복 하나 더(302), 바이트는 S3 서울에서 바로 |
| **C. 화면에 서명 주소를 직접 싣기** — 목록을 그릴 때 장마다 서명(분 ~ 시간) | 화면을 다시 그리고 **만료까지** — B 보다 길다 | B 보다 크다(만료가 길다) | **약해진다** — 판정이 화면을 그릴 때 한 번이고 한 장마다가 아니다 | B 와 같고 Vercel 호출이 없다. 서명이 매번 달라 브라우저 캐시를 못 쓴다 | 가장 짧다 |

**권고 — A.** 차단 · 공유가 지금과 같고 ADR 0200 을 그대로 둔다. 바뀌는 것은 비용의 자리(DB Egress → 함수 · S3)뿐이고, 그 양이
재어져 문제가 되면 그때 B 를 다시 견준다. A 의 구현은 **draft PR** 에 있다(머지 · 운영 적용 안 함). CloudFront 서명 쿠키는 새 서비스라
견주지 않았다. **→ 운영자가 A 를 골랐다(2026-10-23) — 아래 「2026-10-23 — 차단 → 지우기 → 0건 → 개방」, ADR 0204.**

## 2026-10-23 밤 — 옛 사진은 옮기지 않는다

> 「옛 장은 DB 에 남고 그대로 열린다」는 아래 절이 바꿨다(같은 날 운영자 결정). 옮기지 않는 것은 그대로다.

**옮기지 않는다 — 옛 장은 DB 에 남고 그대로 열린다(운영자 판단 2026-10-23, 베타).** 한 줄은 바이트 또는 열쇠를 들고, 바이트 줄은
저장소를 켠 뒤에도 지금 길로 열린다(`app/me/photo/photo-response.ts` 는 `base64` 가 있으면 그대로 낸다). 바꾸거나 새로 올리는 장부터
저장소에 산다. 옮기는 도구(#811 의 `photo-move.mjs`)와 문 셋(`photo_move_begin` · `photo_bytes_to_move` · `photo_bytes_moved`)을
`20261227150000` 이 걷었다 — 월 점검(`scripts/photo-verify.mjs` · `photo_object_keys`)은 남는다. 위 「대장에 올림」의 「옮기는 도구까지」는
그날의 기록이다. 결정의 자리는 ADR 0202 의 덧붙임.

## 2026-10-23 밤 — 옛 사진은 지우고 다시 받는다

> 「차례 — 켜기 → 안내 → 지우기」와 안내 시안의 「{날짜} 전에 바꿔 올린 사진은 그대로 남아요」는 아래 「2026-10-23 — 차단 → 지우기 →
> 0건 → 개방」이 바꿨다(같은 날 운영자 결정, ADR 0204). 지우고 다시 받는 것 · 대상 집계 · 사진이 조건이 아니라는 것은 그대로다.

**운영자 결정(2026-10-23): 「사진 저장소 전환 때 기존 사진은 이관하지 않고 삭제한 뒤 다시 등록받는다.」** 위 절의 「옛 장은 DB 에
남고 그대로 열린다」를 바꾼다. 결정의 자리는 ADR 0202 의 둘째 덧붙임, 절차는 `docs/ops/runbook/photo-store.md` 「사진 저장소로 바꾼다」(그날은 「켠 뒤 옛 사진을
지우고 다시 받는다」였다). **이 기록을 남긴 날에는 지우지 않았다.**

**대상(운영 DB 집계, 2026-10-23)** — 바이트 줄 2 · 그 사람 2 · 바이트 합 50,634(49 kB) · 열쇠 줄 0 · 가입한 사람 14. 이관 문 셋은 운영
DB 에도 없다(`20261227150000` 이 운영에 적용됨 — `photo%` 함수는 `photo_at` · `photo_focus_of` · `photo_object_keys` ·
`photo_sweep_tickets` · `photo_trash_batch` · `photo_trash_settle` 여섯).

**차례 — 켜기 → 안내 → 지우기(추천).** 켜기 전에 지우면 열람 방식이 정해지고 켤 때까지 사진이 비고, 그 사이 다시 올린 장도 DB 길로
가 또 지워야 한다. 켠 뒤라면 안내를 받고 먼저 바꿔 올린 사람에게는 빈 창이 없다.

**사진이 없는 사람** — 노출 · 매칭 · 가입에서 빠지지 않는다. 덱을 채우는 문은 사진을 안 보고, 사진은 선택이다(PRD 「이름과 얼굴」).
카드 · 아바타가 사진 없는 사람의 기본 표시로 설 뿐이다(runbook 의 「지우면 일어나는 것」).

**사용자 안내 — 자리와 시안.** 앱 안의 자리는 없다 — 소식은 갈래가 검사식(`notification_kind_check`)으로 닫혀 있어 새 갈래는
마이그레이션 · 화면이 들고, PRD 는 「사진은 선택이다 — 권유 화면 · 알림은 없다」(운영자 2026-10-11)라 앱이 다시 올리라고 권하면 그
결정을 다시 여는 것이다. 대상이 둘이라 **운영자가 직접 전한다**. 아래는 그 메시지의 시안이다 — 화면 문구가 아니라 대장(`docs/product/copy-ledger/`)에
넣지 않았다. **확인 전.**

> 사진 보관 방식이 바뀌어 {날짜}에 지금 올려 둔 프로필 사진이 삭제돼요. 삭제된 사진은 되돌릴 수 없어요.
> 프로필 화면에서 사진을 다시 올려 주세요. {날짜} 전에 「사진 변경」으로 바꿔 올린 사진은 그대로 남아요.

출처 — 「사진 저장 방식이 바뀌어 다시 올려 달라」는 한국 서비스의 공개 안내는 **찾지 못했다(실사례 없음, 확인 2026-10-23)**. 검색
「프로필 사진을 다시 등록해 주세요」 · 「서버 이전 공지 프로필 사진 다시 등록」에서 공식 공지가 나오지 않았다. 가장 가까운 것은 Indeed
한국 도움말의 사진 기능 안내(사진 업로드는 선택 — <https://kr.indeed.com/help/job-seekers/articles/27517857907853-uploading-a-profile-photo>)다.
말투는 대장 01(해요체 · 되돌리기 어려운 결과의 고지)을 따랐다.

**걷은 것(이 PR)** — `supabase/tests/99_photo_object_store.test.sql` 의 「옮기는 문 셋이 없다」 단언(32 → 31), `scripts/photo-verify.mjs` 머리말의 「DB 에
남는다」, runbook 의 「옛 사진은 DB 에 남는다」 절. **남긴 것** — 월 점검(`scripts/photo-verify.mjs` · `photo_object_keys`)은 열쇠 줄을 재는
도구라 이관 전용이 아니다. 걷은 마이그레이션(`20261227150000`)의 머리말은 그날의 기록이라 고치지 않는다.

## 2026-10-23 — 차단 → 지우기 → 0건 → 개방 (ADR 0204)

**운영자 결정(2026-10-23, 원문 요지)** — 열람은 **안 A**(앱 경로가 판정한 뒤 S3 를 중계, ADR 0200 유지). 기존 사진은 전부 지우고 다시
받으며 차례는 **업로드 차단 → 기존 사진 전체 삭제 → 0건 확인 → S3 업로드 개방**이다. 차단은 화면뿐 아니라 서버의 모든 올리는 문에
선다. 차단 중에는 까닭을 짧게 안내한다. **`db push` 만으로 차단 · 삭제 · 저장소 개방이 시작되면 안 된다.** Vercel Pro 는 이 전환의
선행 조건이 아니다(G-117 의 별도 결정). 운영 삭제 · 배포 · 켜기는 운영자가 따로 지시한다.

**들인 것(#812)** — 안 A 의 열람(`20261228150000`)과 올리기의 DB 스위치(`photo_upload_switch` — `db` · `paused` · `s3`, 기본 `db`,
`20261228140000`). 올리는 문 다섯이 매번 스위치를 보고 제 길이 아니면 거절한다 — 운영자가 SQL 한 줄로 바꾸고 배포 없이 듣는다. 화면은
같은 값을 읽어 멈춘 동안 사진 판 첫 줄에 안내를 세우고 올리는 자리를 거둔다. 절차 · 볼 값은 runbook 「사진 저장소로 바꾼다」.

**앞 절과 달라진 것** — 차단이 먼저라 지우는 동안 새 바이트 줄이 안 생기고, 지운 뒤 올리는 장은 모두 열쇠 줄이다. 그래서 「먼저 바꿔
올리면 남는다」는 없다. 지울 때 `key_rows` 가 0 이라(저장소 길이 한 번도 안 열렸다) 자리를 다시 붙일 일이 없다.

**막히는 흐름(코드로 잼, `origin/main` `8ad3f9b0`)** — 사진을 올리고 바꾸는 일뿐이다. 가입(`complete_signup` · 폼에 사진 칸 없음) ·
프로필 저장(`missingInProfile` — 닉네임 · 소개만) · 덱 채우기(`fill_discovery_deck` · `discovery_pair_eligible`) · 요청 · 채팅 · 풀이는
사진을 안 묻는다. 계정 관리의 「사진 추가」는 멈춘 동안에도 서고 누르면 프로필의 안내로 간다.

**화면 안내** — 「사진 보관 방식을 바꾸는 중이라 지금은 사진을 올릴 수 없어요.」(대장 `docs/product/copy-ledger/settings.md` settings-05,
확인 전). 출처: 「사진 업로드를 잠시 멈춘다」는 한국 서비스의 공개 안내는 **찾지 못했다(실사례 없음, 확인 2026-10-23)** — 검색
「사진 업로드 일시 중단 점검 공지」 · 「프로필 사진 변경이 일시 중단」에서 공식 공지가 나오지 않았다. 가장 가까운 것은 커뮤니티 다모앙의
운영 공지 「프로필 사진 저장 방식 변경」(<https://damoang.net/free/5084412>, 2025-10, 검색 요약으로 읽음 — 본문은 403)이다. 말투는 대장 01(해요체).

**운영자가 직접 전할 때의 시안(확인 전)** — 화면 문구가 아니라 대장에 넣지 않았다.

> 사진 보관 방식이 바뀌어 {날짜}에 올려 두신 프로필 사진이 모두 삭제돼요. 삭제된 사진은 되돌릴 수 없어요.
> {날짜} 뒤에 프로필 화면에서 사진을 다시 올려 주세요.
