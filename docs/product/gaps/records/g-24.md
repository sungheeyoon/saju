# G-24 기록

표의 줄: [간극 대장 「공개 출시」의 G-24](../../gaps.md#공개-출시)

표의 「G-24」 줄 메모 칸에 쌓였던 실행 기록이다 — 문장은 그대로 옮겼다(2026-10-05). 줄을 닫으면 이 절도 함께 걷는다.

**화면이 섰다(2026-09-24)**: `/ops/reports` · `/ops/reports/[reportId]`, 운영자 전용 문 셋(`20261009090000`), 읽기 전용. 증거: pgTAP
`45_operator_reports`(운영자만 · 반환형에 이메일 · 출생정보 · 방 실마리 없음 · 떠난 사람의 신고 안 나옴) · e2e `chat.spec.ts` 「운영자는 신고 목록에서 신고를 열어
…」(비운영자 404 · 누름 0) · `docs/ops/runbook/moderation.md` 「신고와 차단」. **남은 것: 프로덕션 운영 검증 한 번** — 아래. **검토 기록과 열람 기록이 섰다(2026-09-24, ADR 0105)**: 신고에
`reviewed_by` · 결과(조치 없음 · 경고 · 이용 정지 · 추가 확인) · 판단 근거 · 제재를 받은 쪽 · 실행한 사람이 붙고 runbook 의 검토 SQL 이 채운다. 상세가 그 칸을 읽는다(신고한
사람에게는 안 열린다). 화면을 여는 것마다 접속기록(G-23 ⑩)에 남는다. **닫는 검증 — 누구나 그대로 밟는 열네 걸음(2026-09-24):** `docs/ops/runbook/moderation.md` 「신고 열람대의 운영 검증 — G-24 를 닫는
열네 걸음」이 걸음마다 SQL 과 통과 조건을 든다. 전제 — 관련 마이그레이션(`20261009090000` · `20261010090000` · `20261010100000` · `20261010110000`)이
운영에 있다 · 최신 main 이 Production Ready 다(`docs/ops/runbook/deploy.md` 「묶음 배포 — 최신 main 을 Production 으로 한 번」) · 실제 개인정보 없는 전용 테스트 계정이다 · 테스트
메시지에도 실제 이름 · 연락처 · 출생정보를 안 쓴다. 걸음 — ① 테스트 계정 A · B ② 둘 사이의 테스트 대화와 신고할 메시지 ③ 신고 1건 ④ `/ops/reports` 목록에 보임 ⑤ 처리 상태 · 신고
사유 · 대화 근거 거르기 각각 ⑥ 상세의 신고 내용 · 스냅샷 ⑦ 고른 메시지가 정확하고 앞뒤 문맥이 차례대로 ⑧ 접속기록에 목록 · 상세 · 스냅샷 열람이 각각 ⑨ runbook 의 검토
문(`review_report`)으로 `조치 없음`(또는 시험용 결과 — 추가 확인 필요는 처리 필요에 남고, 이용 정지 결정은 같은 트랜잭션에서 계정을 정지한다) ⑩ 상세의 처리 상태 · 검토 결과 · 검토 운영자
· 판단 근거 · 당시 제재 대상이 DB 값과 같음 ⑪ 비운영자는 같은 주소에서 404 이고 거절 기록이 남음 ⑫ 배포 SHA · 신고 id · 실행 시각 · 접속기록 id · 검토 결과 · 화면 확인 결과를
이슈에(틀 `.github/ISSUE_TEMPLATE/ops-verification.md`) ⑬ 테스트 자료 정리 또는 보존 방식 기록(신고는 `retention.report` 에서 6개월 뒤 자동 파기, 접속기록
줄은 지울 수 없다) ⑭ **열셋이 모두 통과일 때만 닫는다.** 메시지 본문이 나오는 ⑦ 의 질의는 사람이 break-glass 로 돈다 — 에이전트는 질의를 건네기만 한다. **배포 한도 — 운영자
결정(2026-09-24, 2026-09-25 에 뒤집음):** `ignoreCommand` 는 빌드만 건너뛰고 배포 횟수(Hobby 24시간 100)는 줄이지 못한다. 2026-09-24 에는 Preview 편의를
우선해 Git 배포를 켜 두었으나, 2026-09-25 에 한도에 두 번 닿아 머지된 수정이 운영에 못 들었다 — Git 배포를 끄고 묶음마다 손으로 한 번 올린다(ADR 0110). 검증 전에 「묶음 배포」로 최신
main 을 올려 전제를 세운다. **검토는 문 하나가 적는다(2026-09-24, ADR 0107)**: runbook 의 UPDATE 둘을 `review_report` 하나로 모았다 — 검토한 사람이 운영자인지
묻고, 이용 정지 결정은 기록과 계정 정지를 한 트랜잭션으로 한다(적는 순간에만 — 해제해도 기록은 남는다). 결과와 제재 대상이 표의 제약으로 맞물리고(`sanction_follows_the_outcome`, 떠난
사람의 신고에도 논리 제약 다섯), 처리 필요 = 안 봤거나 추가 확인 필요(`report_is_open`)로 목록 · runbook 질의 · 월 점검이 같은 정의를 쓴다. 3영업일은 접수부터. 화면 글자는 처리
필요 / 처리 완료 · 이용 정지 결정 · 추가 확인 필요 · 당시 제재 대상. 증거: pgTAP `52_report_review_door` · e2e `chat.spec.ts` 「운영자 목록은 처리 필요와 처리
완료로 가르고 …」. 운영 DB 의 두 표는 그날 0줄이라 새 제약을 어긴 줄이 없었다. 경고를 이용자에게 알리는 길은 G-57. 1차판에서 뺀 것(검토 완료 누름 · 제재 누름 · 메모 · 운영 현황 집계 ·
실행한 운영자 표시)은 화면에 쓰는 누름이 필요해지는 날 새 줄로 연다

**2026-10-10 — 열람대를 다듬었다(화면 점검 C16 · C17).** #576: 운영 화면이 얇은 운영 머리(「운영」 표지 · 신고 · 설문)를 달고, 목록은 신고받은 계정을 앞에 세우며 그 쪽 안의 「처리 필요 N건」 딱지를 달고 폰에서 거르기를 접는다. 상세는 신고 id 값 복사 단추와 검토 절차 한 줄. #588: 대화 신고 줄에 고른 메시지 첫 줄의 한 줄 발췌(사본에서 60자), 목록 접속기록 한 줄에 그 쪽의 신고 id 들(`target_report_ids`, ADR 0105 추기). 열네 걸음의 ④ ~ ⑧ 이 보는 화면이 바뀌었다 — 걸음은 그대로이고, 밟는 날은 G-65 를 기다린다.
