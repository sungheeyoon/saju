# 매칭 구현 리뷰 — 2026-09-18

초기 리뷰 대상: `febd015`. 아래 원인과 줄 번호는 당시 소스 기준의 기록이다.

## 같은 날 후속 수정

사용자의 후속 구현 요청으로 아래 여섯 항목을 수정했다. `restore_passed_connection`이
자격 검사·스냅샷 앞자리 삽입·현재 요청 근거·보관 해제를 한 번에 수행한다. 화면은 사람 ID의
덱과 복원 이력을 사용하고, 실패 시 대상을 유지한다. 20명 표시·사진 권한·현재 명식 판본과
상호 성별 조건·동률 정렬도 함께 맞췄다. 서버 재검증은 현재 순서를 보존하면서 반영한다.

홈의 중복 후보 목록은 걷고 기존 자동 참여를 유지했다. 모바일 하단에 매칭을 넣었으며,
AI 예시 경로와 디자인은 유지했다. 배포된 최근 20명 보관 정책을 바꾸지 않았다.
설계 근거는 [ADR 0070](../adr/0070-matching-restores-the-person-not-the-position.md)에 있다.

검증·배포 결과는 이 문서 마지막에 기록한다. 아래 항목은 **현재 미완료 목록이 아니라
이번 변경이 해결한 문제의 기록**이다.

제품 기준은 [PRD §6](../prd.md#6-인연)에 있다. 기존 데이터로 실제 카드를 만드는 것과 AI 예시를 미리보기 경로에 유지하는 것은 양립한다. 디자인을 유지하면서 아래 연결과 상태 처리를 고칠 수 있다.

## 확인한 개선

- 지나침을 `discovery_passed`로 분리하여 기존 `discovery_hidden`과 별도로 저장한다.
- `my_passed_connections()`를 서버에서 읽어 매칭 화면 초기 보관 목록으로 전달한다. 새로고침 시 초기화되던 문제를 해결하는 연결이 있다.
- X 저장 성공 후 카드 이동을 시작하고, X·하트 처리와 드래그 완료에 저장 중 입력 방지가 있다.
- `cancelLeave()`는 예약된 이동과 시각 상태를 취소한다. 다만 아래 연속 복원 문제까지 해결한 것은 아니다.

## 초기 리뷰에서 확인한 항목

### P1 — 보관함 복원 버튼이 연결되지 않음

근거: `app/me/matching/passed-connections.tsx:123`. 「다시 만나보기」는 안내 문구만 바꾸며 서버 복원이나 덱 변경을 호출하지 않는다.

`restorePassed(id)` 호출과 목록 삭제만으로는 부족하다. 현재 덱에 없는 사람도 복원한 ID의 카드를 맨 앞에 삽입하고, 보고 있던 카드를 다음으로 유지해야 한다. 호출 실패 시 보관 목록을 유지하고 재시도해야 한다.

확인: 새로고침 후 보관함에서 현재 추천 덱에 없는 사람을 복원한다. 그 사람이 먼저 나오고 기존 현재 카드가 다음에 나오며, 다시 새로고침해도 보관함에서는 빠져 있어야 한다.

### P1 — 연속 되돌리기는 여전히 화면과 저장이 어긋남

근거: `app/me/matching/matching-experience.tsx:200` 및 `:240`. 마지막 사람 한 명만 `hidden`으로 기억한다. 첫 복원 뒤에는 `hidden`이 비어 다음 되돌리기가 `index - 1`만 수행한다.

A를 지나치고 B를 지나친 뒤 B, A 순서로 되돌리면 A의 카드는 보이지만 A의 서버 기록은 남을 수 있다. `findIndex`를 사용했다는 사실만으로 덱 전체가 ID 기반으로 바뀐 것은 아니다. 또한 찾는 ID가 없을 때 `setIndex(0)`은 해당 인물을 삽입하지 않고 다른 첫 카드를 선택한다.

확인: A·B 연속 지나침과 두 번의 되돌리기 후 화면·보관함·서버 기록을 대조한다. 서버 조회로 카드 배열이 바뀌는 경우도 포함한다.

### P2 — 복원 실패 시 재시도 대상이 사라짐

근거: `app/me/matching/matching-experience.tsx:203`. 서버 성공 전 `setHidden(null)`을 실행한다. 실패해도 대상을 복구하지 않아 같은 되돌리기를 재시도할 수 없고, 이후 버튼이 단순 위치 이동으로 바뀐다.

확인: 복원 요청을 실패시키고 재시도한다. 성공 전에는 보관 상태와 복원 대상이 유지되어야 한다. 복원 대기 중 연속 누름도 함께 확인한다.

### P2 — 화면 목록은 20명을 초과함

근거: `app/me/matching/matching-experience.tsx:157` 및 `:170`. 목록 앞에 추가하고 중복만 제거하며 20명으로 자르지 않는다. 서버 조회는 20명을 반환하므로 새로고침 전후 숫자가 달라진다.

확인: 20명이 저장된 상태에서 한 명을 더 지나친다. 화면에는 최신 20명만 보이되, 밀려난 사람의 서버 제외 기록은 24시간 정책을 위해 유지되어야 한다.

### P2 — 실제 회원도 예시로 표시되고 사진이 빠짐

근거: `app/me/matching/passed-connections.tsx:87`, `:103`, `:126`. 사진은 예시 `photoUrl`만 사용하고 실후보의 `hasPhoto`에 대응하는 조회 경로를 사용하지 않는다. 예시 프로필·예시 점수·예시 목록과 미연결 안내도 항상 노출한다.

확인: 사진 등록 회원, 미등록 회원, 예시 경로를 각각 확인한다. 실제 사진은 기존 인증된 사진 조회와 권한을 사용하고, 예시 딱지는 예시 경로에만 표시한다.

### P2 — 보관 조회의 현재 자격 확인이 추천 조회보다 약함

근거: `supabase/migrations/20260923090000_the_passed_are_kept_apart.sql`의 `my_passed_connections()`. 대상의 활성·참여와 `discovery_unavailable`은 확인하지만, `discovery_eligible()`에 있는 현재 명식 판본 일치 및 상호 성별 조건 확인이 빠져 있다. 보관 중 조건이 바뀌면 기존 요약의 점수나 현재 추천 불가한 상대가 계속 노출될 수 있다.

지나쳤다는 이유만 예외로 두고, 공개·추천 자격은 같은 기준을 사용해야 한다. 일반 추천 함수를 그대로 쓰면 지나친 사람 전부가 제외되므로 자격 검사와 지나침 검사를 구분해야 한다.

확인: 보관 뒤 명식 수정, 성별 조건 변경, 참여 중지, 차단 상황에서 조회와 복원 가능 여부를 대조한다.

## 초기 리뷰의 정책·검증 쟁점

- 현재 SQL은 최근 20명을 시간과 무관하게 보관한다. 20명 밖만 마지막 넘김부터 24시간이 지나면 제외가 풀린다. 앞서 제안된 모든 기록의 24시간 만료와 다르므로, 구현 사실과 정책 확정을 혼동하지 않는다.
- 목록은 공개 조건으로 거른 뒤 20명을 읽지만 제외 판정의 최근 20명은 전체 저장 행을 센다. 보관된 일부가 비공개가 되면 그 다음 사람이 목록에 보이면서도 제외 판정에서는 20명 밖일 수 있다. 목록의 20명과 보관 제외의 20명에 같은 순위 기준이 필요하다.
- 같은 `passed_at`의 행들은 제외 판정에서 동순위로 계산되고 목록은 동률 순서가 정해져 있지 않다. 20명 경계에는 일관된 보조 정렬 기준을 두고 검증한다.
- 홈의 기존 추천 목록은 아직 남아 있다. 매칭은 회원 메뉴에 있지만 모바일 하단 다섯 탭에는 없다. 「오늘의 인연을 매칭 탭으로 완전히 이전」한 상태로 보고하지 않는다.
- 사진 경로를 연결할 때 보관 대상에 대한 사진 조회 권한도 함께 확인한다. 이 리뷰에서는 실제 인증 사진 응답을 재검증하지 않았다.

## 초기 리뷰의 권장 작업 순서

1. 최근 20명 자체의 만료 정책을 맞추고 조회·제외의 순위 기준을 통일한다.
2. 현재 공개 자격을 검사한 복원 결과를 받아 실제 덱 앞에 넣는다. 보관함 버튼과 되돌리기가 같은 복원 흐름을 사용하게 한다.
3. 복원 실패·연속 입력·이동 타이머·배열 변경을 함께 처리한다.
4. 표시 한도, 실제 사진과 예시 표시를 연결한다. 기존 레이아웃과 모션은 유지한다.
5. 위 시나리오의 회귀 검증과 CI 결과를 확인한 뒤 PRD의 완료 상태를 갱신한다.
