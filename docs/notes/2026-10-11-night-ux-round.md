  확인 창 · 폼은 래퍼가 고칠 파일과 겹쳐 둘째 물결로 미뤘다. 래퍼가 먼저 들자 두 세션에 `SendMessage` 로 알려 제 파일의 부름을 래퍼로 옮기게 해, 잠금 시험의 「아직 안 받는 자리」가 라운드 안에 비었다.

## 헤맨 것 · 배운 것

- **충돌난 PR 은 CI 가 돌지 않는다 — 「CI 기다림」이 영원히 끝나지 않았다.** #627 이 #628 과 문구 대장 한 파일로 부딪혀 약 7시간 멈췄고, 에이전트는 오지 않을 알림을,
  조율자는 에이전트의 「기다림」을 믿었다. 운영자가 물어서 알았다. 에이전트가 기다림으로 멈추면 조율자는 `gh pr view <N> --json mergeable,mergeStateStatus` 를 먼저 본다.
- 나란히 도는 PR 이 「다음 빈 번호」(ADR · 대장 절 · G 줄)를 같이 노려 세 PR 이 번호를 두세 번 옮겼다.
- 대장 색인 한 줄로 reviewer 읽기량이 천장을 6바이트 넘어 #621 이 천장을 95,000 으로 올렸다(ADR 0164) — G-94 의 「올리지 않는다」와 어긋난다. 운영자 답 대기.
- 첫 `vercel deploy --prod` 가 `Not authorized` 로 끝났고 배포를 만들지 않았다(`vercel ls` 로 확인). 두 번째에 섰다.
- 감사 보고의 줄 번호 · 개수는 여러 번 틀렸다(액션 부름 38 → 실제 50, 가입 거절 330행 → 301행) — 브리프에 「가설, 코드에서 다시 확인」을 적은 것이 받쳤다.
- 에이전트가 프리티어를 돌려 파일을 다시 썼다가 되돌렸다 — 이 저장소는 포매터가 없고 린트만 있다.
